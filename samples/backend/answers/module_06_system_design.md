## Q1：CAP理论的理解？一般分布式业务系统使用哪两个原则？

### 考察点
候选人是否理解 CAP 的实际工程含义，能否在真实业务场景下做 trade-off，而不是背诵"三选二"。

### 解答思路
1. 先从数学定义切入（线性一致性、可用性、分区容错）并澄清常见的"CA 系统"误解。
2. 用 P（分区）必然发生的观点推导出 CP/AP 二选一的实际决策框架。
3. 结合注册中心、数据库、消息队列等常见组件说明 AP 才是大多数业务系统的默认选择。

### 参考答案

CAP 是 Eric Brewer 2000 年提出的猜想，Gilbert & Lynch 2002 年给出了形式化证明。先澄清三点常见误解：

**第一，P（分区容错）不是可选项。** 分布式系统中网络分区是客观存在的物理现实——交换机故障、光缆被挖断、机房断电。当你选择"放弃 P"时，你实际上选择的是一个单机系统，而不是一个分布式系统。所以 CAP 的决策本质上是：**发生网络分区时，你选择 CP 还是 AP？**

**第二，"CA" 分布式系统不存在。** 有人说 ZooKeeper 是 CA 系统，这是错的——ZooKeeper 在网络正常时提供 CP，网络分区时多数派集群仍然可用（CP）；少数派节点不可用，这是 CP 的体现。Eureka 是典型的 AP——网络分区时宁可返回过期数据也不拒绝服务。

**第三，一般分布式业务系统的选择是 AP + 最终一致性。** 原因很直接：
- 可用性直接影响用户体验和收入（Google 发现 500ms 延迟会让流量下降 25%）
- 强一致性的代价太高（Paxos/Raft 需要多数派确认，跨机房延迟 +30~50ms）
- 绝大多数业务场景允许一个收敛窗口内的数据不一致

具体选型表：

| 场景 | 选择 | 原因 |
|------|------|------|
| 用户下单 | AP | 下单不能因为网络抖动就失败 |
| 余额扣减 | CP | 不能超卖或透支 |
| 商品库存展示 | AP | 允许短暂显示不一致 |
| 分布式锁 | CP | 锁语义要求唯一性 |
| 配置中心 | AP（Eureka）或 CP（Zookeeper） | 取决于是"极致可用"还是"强一致" |

在生产中，主流互联网公司的架构倾向于 **AP + 最终一致性** 作为默认选择，仅在资金、库存、锁等关键路径上使用 CP 方案（如 TCC、Saga 的补偿逻辑本质上就是承认系统选择了 AP，但通过业务补偿来达到最终一致性）。

**加分项：** 提到 PACELC 理论（Daniel Abadi 2012）——发生分区时在 A/C 间选择，正常运行（无分区）时在 L（延迟）和 C（一致性）间选择。它能解释为什么即使没有分区，Cassandra 也允许放宽一致性以降低延迟。提到 Google Spanner 用 TrueTime（原子钟 + GPS）提供"外部一致性"，将 CAP 的约束从"不可能三角"变成了"硬件成本换一致性"的工程实践。

## Q2：CAP理论与BASE理论的核心要点？

### 考察点
能否将 CAP 和 BASE 理解为一套从"理论边界"到"工程实践"的完整决策框架，而非孤立地背诵两个缩写。

### 解答思路
1. 先理清 CAP 和 BASE 的关系——CAP 是理论边界（你不能同时拥有什么），BASE 是工程妥协方案（你实际选择了什么路径）。
2. 分别展开 CAP 的三个维度和 BASE 的三个维度（BA、S、E）的含义和工程体现。
3. 用具体中间件的选型来串联两个理论，展示完整的决策链路。

### 参考答案

**CAP 和 BASE 的关系是"理论边界 vs 工程方案"：**

CAP 告诉你分布式系统无法同时满足 C/A/P 三个属性——这是数学证明的约束。BASE 则告诉你：既然不能同时满足，那我们选择 **AP（放弃强一致）**，然后通过"基本可用 + 软状态 + 最终一致"来补偿"放弃 C"带来的问题。

**CAP 三个维度的工程含义：**

| 维度 | 工程含义 | 反例 |
|------|----------|------|
| C（强一致性） | 任意时刻所有节点读到最新写入值（线性一致性） | 主从 MySQL 读从库可能读到旧数据 |
| A（可用性） | 每个非故障节点必须在有限时间内返回响应 | ZooKeeper 的少数派节点不响应写请求 |
| P（分区容错） | 节点间消息可能丢失/延迟，系统仍能工作 | 单机 MySQL 主库，网络断了就不可用 |

**BASE 三个维度的工程含义：**

**BA（Basically Available，基本可用）：** 系统在出现故障时允许损失部分可用性，但不等于系统不可用。工程表现：
- 响应时间上的损失：正常 50ms 内返回，故障时间增加到 3s（如电商大促时搜索自动降级到核心 SKU）
- 功能上的降级：高峰期关闭晒单、评论等非核心功能，保证下单链路（典型做法——熔断/降级）
- 注意区分：降级不等于报错返回，而是"服务还在，只是变慢了/变少了"

**S（Soft State，软状态）：** 系统允许存在中间状态，且中间状态不影响整体可用性。工程表现：
- 订单状态从"已支付"到"已发货"之间有延迟（消息队列堆积导致），但不影响用户正常使用
- 副本之间数据同步存在窗口期（MySQL 主从延迟），但不拒绝读请求
- 关键设计：中间状态需要有**可观测性**（如显示"订单处理中"），让用户/系统知道当前不是最终态

**E（Eventually Consistent，最终一致性）：** 系统不保证任意时刻数据一致，但保证在没有新更新的情况下，数据最终会收敛到一致。工程保证手段：
- 对账机制：T+1 对账、小时级对账兜底
- 补偿操作：未成功的操作重试（指数退避），无法重试的进行逆向补偿
- 版本向量/向量时钟：解决并发写冲突时的因果关系追踪

**CAP → BASE 的完整决策链路（以订单系统为例）：**

```
CAP 约束 → 选择 AP（接受分区时可能不一致）
   ↓
BASE 方案落地：
├── BA: 下单服务过载时排队/降级，不直接返回 500
├── Soft State: 支付成功后订单状态"同步中"，允许短暂未落库
└── Eventually Consistent: 支付回调 + 定时对账确保订单状态最终一致
```

**加分项：** 提到 BASE 的"软状态"不等于"没有状态"——它要求系统能感知和追踪中间状态，否则就会变成"黑洞"。比如支付回调丢失时，如果没有定时对账，订单就永远停在"支付中"。这是生产中最常见的 BASE 实施坑——开发只做了异步化，没做兜底对账。提到 Amazon 的 Dynamo 论文（2007）是 BASE 实践的开山之作，其"永远可写"（always writable）的设计哲学至今影响几乎所有 AP 型存储（Cassandra、Riak、Voldemort）。

## Q3：分布式事务中2PC/3PC、TCC、SAGA、消息最终一致性的区别和适用场景？

### 考察点
能否从"一致性强度 vs 性能损耗"的光谱上准确定位每种方案，并给出生产级的选型理由。

### 解答思路
1. 先按"同步阻塞 / 异步补偿"两大类划分，再逐方案展开核心机制。
2. 用一张对比表串联所有方案的一致性强度、性能、复杂度、适用场景。
3. 重点讲 TCC 和消息最终一致性这两种互联网大厂最常用的方案。

### 参考答案

**2PC（两阶段提交）：**

- 机制：协调者先发 Prepare 让所有参与者预留资源并锁定，全部返回 YES 后发 Commit；任一返回 NO 则全部 Rollback。
- 致命缺陷：**协调者单点故障**——Prepare 完成后协调者宕机，参与者持有的锁无法释放（阻塞）。这是同步阻塞协议，锁持有时间长，性能极差。
- 工程现状：XA 协议基于 2PC，MySQL 支持 XA 事务，但生产上极少用于跨服务的分布式事务（只在单个数据库的多存储引擎场景使用）。

**3PC（三阶段提交）：**

- 改进点：在 2PC 中插入 CanCommit 阶段（询问能否提交但不锁资源），并引入参与者超时机制——协调者失联时参与者可自行 abort，降低了阻塞概率。
- 但 3PC 引入了一个新问题：**网络分区时可能出现数据不一致**——协调者发给部分参与者的 Commit 消息丢失，超时自断的参与者执行 Abort，导致部分提交、部分回滚。
- 工程现状：几乎无人使用。理论上试图同时解决阻塞和一致性问题，但实际牺牲了一致性保证，得不偿失。

**TCC（Try-Confirm-Cancel）：**

- 机制：业务层补偿事务，每个操作需提供三个接口：
  - Try：预留资源（冻结库存、预占金额），执行业务检查
  - Confirm：真正执行业务（扣减冻结库存）
  - Cancel：释放预留资源（解冻库存、退回金额）
- 核心思想：将 2PC 的资源锁下沉为**业务资源预留**，锁粒度更粗但持有时间更短，事务管理器可异步重试。
- 常见坑：空回滚（Cancel 先于 Try 到达）、悬挂（Cancel 后 Try 才到）、幂等（Confirm/Cancel 重试）。解决方式——业务表记录事务状态，基于状态机判断是否允许执行。
- 适用场景：资金、库存等需要强一致性的核心交易链路。

**Saga：**

- 机制：将长事务拆分为一系列本地事务 T1, T2, T3...，每个 Ti 对应一个补偿操作 Ci。失败时逆序执行补偿（C3 -> C2 -> C1）。
- 分两种模式：
  - 编排模式（Choreography）：服务间通过事件驱动，松散耦合
  - 编排模式（Orchestration）：由一个 Saga 管理器统一调度
- 适用场景：流程长、耗时久（跨小时甚至跨天）的分布式事务，如旅行预订（订机票 -> 订酒店 -> 租车，任一失败都需要取消前面所有）。

**消息最终一致性（事务消息/本地消息表）：**

- 核心思想：通过消息队列将"业务操作"和"异步后续操作"解耦，利用消息的可靠性投递机制（重试 + 死信）保证最终一致。
- RocketMQ 事务消息流程：half message（预发送） -> 执行本地事务 -> commit/rollback -> 消费（带幂等）
- 本地消息表的等价方案：业务表中增加 `event` 字段，定时任务扫描未成功的消息重试投递
- 适用场景：非实时一致性要求的场景，如订单创建后发积分、发通知、同步搜索索引。

**方案对比总结表：**

| 方案 | 一致性 | 性能 | 锁粒度 | 侵入性 | 适用场景 |
|------|--------|------|--------|--------|----------|
| 2PC | 强 | 极差 | 数据库行锁 | 低（数据库层） | 几乎不用 |
| 3PC | 近似强（有漏洞） | 差 | 数据库行锁 | 低 | 几乎不用 |
| TCC | 强（业务保证） | 中 | 业务资源预留 | 高（需实现三接口） | 资金、库存扣减 |
| Saga | 最终 | 好 | 无锁 | 中（需实现补偿） | 长流程（旅行、订单履约） |
| 消息最终一致 | 最终 | 好 | 无锁 | 低-中 | 非核心链路（积分、通知） |

**生产级实践建议：** 能用消息最终一致性的场景绝不用 TCC。TCC 的实现和维护成本远高于消息方案——每个业务操作的双向接口（Try/Cancel）本身就是出错重灾区。只有涉及资金和核心库存时才选择 TCC。

**加分项：** 提到 Seata 的 AT 模式——通过在数据库层自动生成 undo log（类似 MySQL 的 MVCC），实现了对业务代码零侵入的分布式事务，本质上是对 Saga/TCC 模式的自动化。AT 模式下 Seata 自动记录"修改前"和"修改后"的数据快照（全局锁 + 本地锁保证隔离），回滚时用 undo log 恢复。但它的局限性也很明显——仅支持 ACID 数据库，不适合有 Redis/MongoDB 参与的事务。提到 Uber 的 Cadence/Temporal 工作流引擎处理 Saga 时，通过 Workflow 代码的确定性重放实现了补偿逻辑的自动执行，代表了分布式事务编排的未来方向。

## Q4：谈一谈你对最终一致性的理解。TCC、Saga、本地消息表、事务消息的优缺点对比？

### 考察点
能否将"最终一致性"从一个概念落地为具体的工程保障机制集合，并理解不同方案之间的渐进式取舍。

### 解答思路
1. 先定义最终一致性的三个层次——理论承诺、工程实现、业务容忍度。
2. 用"写后读一致性"、"单调读一致性"这种会话级一致性来衔接"强一致"和"最终一致"的中间地带。
3. 横向对比四种方案的优缺点，给出选型决策树。

### 参考答案

**最终一致性的三层理解：**

**第一层——理论承诺：** 系统不保证任意时刻读到的数据都是最新的，但保证"如果没有新的更新，最终所有副本会收敛到相同状态"。这里有三个要素：(1) 收敛时间（多快能一致）；(2) 收敛保证（什么情况下会不收敛）；(3) 可观测性（系统能否告诉你当前的收敛进度）。

**第二层——工程实现：** 最终一致性不是"什么都不做等它自然一致"，而是一套主动保障机制：
- **重试策略：** 指数退避 + 最大重试次数 + 死信队列兜底
- **对账机制：** 定时任务逐条比对上下游数据，发现差异触发修复
- **补偿操作：** TCC 的 Cancel、Saga 的逆向补偿
- **监控告警：** 关注中间状态的停留时长，设置 P99 超时告警

**第三层——业务容忍度：** 最终一致性能否落地取决于业务能否接受收敛窗口。资金系统对不一致零容忍（必须强一致），但积分发放容忍 30s 延迟完全没问题。关键在于——业务方有没有被告知"最终一致意味着什么"？生产中最常见的坑不是技术实现，而是业务方以为数据是实时的，结果发现要等几分钟。

**会话级一致性——连接"强一致"和"最终一致"的桥梁：**

很多时候业务要的不是全局强一致，而是"自己写了自己能读到"（Read-Your-Writes）：
- 下单后立即跳到订单列表看不到刚创建的订单 → 用户投诉
- 解决方案：关键路径的"写后读"路由到主库，非关键路径接受从库延迟

**四种方案优缺点对比：**

| 维度 | TCC | Saga | 本地消息表 | 事务消息（RocketMQ） |
|------|-----|------|-----------|---------------------|
| 一致性强度 | 强（业务级原子性） | 最终（补偿可逆） | 最终（异步投递） | 最终（可靠投递） |
| 性能影响 | 中（资源预留有开销） | 低（异步执行） | 低（异步投递） | 低（异步投递） |
| 实现复杂度 | 高（三接口 + 状态机） | 中（补偿逻辑） | 低（定时扫描） | 中（需依赖 MQ 事务） |
| 代码侵入性 | 高 | 中 | 低 | 中 |
| 回滚机制 | Cancel 接口 | 补偿事务逆序执行 | 对账 + 人工介入 | 对账 + 人工介入 |
| 数据一致性风险 | 空回滚、悬挂、幂等 | 补偿失败需要人工介入 | 消息丢失（定时扫描 gap） | half message 未 commit 需回查 |
| 运维复杂度 | 高（事务协调器） | 中（编排引擎） | 低（单表扫描） | 中（MQ 集群） |
| 适用链路 | 资金/库存核心链路 | 长流程多步骤链路 | 非核心异步链路 | 非核心异步链路 |
| 典型场景 | 下单扣库存 + 扣余额 | 差旅预订（机票+酒店+租车） | 新用户注册后初始化数据 | 订单支付后异步发券 |

**选型决策树（从业务出发）：**

```
涉及资金/核心库存？
  ├── 是 → TCC（必须强一致）
  └── 否 → 流程是否超过 3 步且跨服务？
            ├── 是 → Saga（流程编排简化补偿）
            └── 否 → MQ 基础设施是否成熟？
                      ├── 是 → 事务消息（RocketMQ 半消息）
                      └── 否 → 本地消息表（最易落地）
```

**生产踩坑经验：**
1. **TCC 的最大坑：** Cancel 接口的幂等性比 Confirm 更难保证——因为 Cancel 可能在 Try 之前到达（空回滚），也可能在 Try 之后重试到达。标准做法是业务表记录事务 ID + 状态字段，所有操作基于状态机判断。
2. **Saga 的最大坑：** 补偿失败是常态而非异常——比如 Cancel 订机票时航司接口挂了，补偿事务就无法完成。必须设计补偿重试策略和人工介入入口。
3. **本地消息表的最大坑：** 定时扫描在数据量大时性能恶化，建议加时间索引 + 分批扫描 + 扫描间隔动态调整。

**加分项：** 提到 Microsoft 的 "Cosmos DB" 通过 5 种一致性模型（强、有限过期、会话、一致前缀、最终）开创了"一致性即服务"的思想——根据操作的业务语义选择不同的一致性级别而非全系统统一。提到美团分布式事务实践——在 TCC 的 Try 阶段通过"预占"而非"锁定"降低了锁冲突，并将 Confirm/Cancel 的幂等保证下沉到框架层，业务只需实现 Try 逻辑。

## Q5：设计一个分布式全局唯一ID生成器，你会考虑哪些核心要素？雪花算法 vs 号段模式各有什么优劣？

### 考察点
能否从前端、后端、数据库、扩容等多个维度系统化地评估 ID 生成方案，而非仅对比算法本身。

### 解答思路
1. 先列出 ID 生成器的核心设计要素（全局唯一、趋势递增、高可用、信息安全等）。
2. 分别深入分析雪花算法和号段模式的原理、优点、痛点。
3. 给出选型结论——大多数场景推荐号段模式，需要跨机房无状态的场景推荐雪花算法。

### 参考答案

**核心设计要素（按优先级排序）：**

1. **全局唯一（硬约束）：** 任何情况下不能产生重复 ID。这是唯一不可妥协的要求，所有其他的优化（性能、递增）都以不破坏唯一性为前提。
2. **趋势递增（软约束）：** 利于 MySQL InnoDB 聚簇索引的插入性能（减少页分裂）。严格全局递增（如 Redis incr）要求单点定序，性能瓶颈明显；趋势递增更实用——只要宏观上数字变大即可。
3. **高可用 & 低延迟：** ID 生成是业务入口的关键路径，延迟 P99 通常要求 < 2ms，可用性要求 99.99%。单点 ID 生成不可接受。
4. **信息安全：** 自增 ID 会暴露业务量（竞对可通过 ID 差值推算订单量），需要非连续递增。
5. **位数控制：** 前端 JS 的 MAX_SAFE_INTEGER = 2^53 - 1（约 9e15），超过此值的 ID 会丢失精度。这决定了 64 bits 方案是安全的（2^63 ≈ 9e18，JS 端必须用 String 传输）。

**雪花算法（Snowflake）：**

原理：64 bits = 1 bit 保留 + 41 bits 时间戳（ms，可用 69 年）+ 10 bits 机器标识（1024 台）+ 12 bits 序列号（每毫秒 4096 个/每机器）。

```
 0 - 0000000000 0000000000 0000000000 0000000000 0 - 0000000000 - 000000000000
[保留] [          41 bits 时间戳 (ms)            ] [10 bits 机器] [12 bits 序列]
```

优点：
- 本地生成，无网络开销，延迟极低（微秒级）
- 趋势递增，天然适合 InnoDB 聚簇索引
- 去中心化，无单点故障

痛点：
- **时钟回拨是致命问题：** NTP 时间同步、闰秒跳跃、系统管理员手动调整时间都可能导致时间戳倒退 → 产生重复 ID（Q6 专题展开）
- **机器 ID 管理复杂：** 需要给每台机器分配唯一机器 ID，扩容/缩容时需要配置管理（ZooKeeper、数据库）。K8S 环境中 Pod 频繁重建更是灾难。
- **QPS 上限：** 每台机器每毫秒 4096 个 = 单机 400w+ QPS，看起来很高，但实际并发下竞争序列号（自旋锁/CAS）会导致性能退化。

**号段模式（Segment/DB-based）：**

原理：从数据库批量取一段 ID 范围（如 [1001, 2000]），服务本地用 AtomicLong 分配，快用完了再去数据库取下一段（双 buffer 异步预取）。

优点：
- **无时钟问题：** ID 完全由数据库生成，不依赖机器时钟
- **效率高：** 号段缓存在内存中，分配延迟极低
- **保证递增（在单业务内）：** 同一号段内严格递增
- **容易实现容灾：** 多号段表或多数据库主备

痛点：
- **数据库是单点：** 需要一个外部存储分配号段（即使只在启动时访问）
- **扩容时可能存在 ID 空洞：** 不同机器拿到不同号段，ID 不是全局严格递增（但趋势递增是保证的）
- **平滑扩容需号段预留：** 加机器时不能立刻使用，需要提前在数据库新增号段入口

**对比总结：**

| 维度 | 雪花算法 | 号段模式 |
|------|----------|----------|
| 唯一性保证 | 依赖机器时钟不倒退 | DB 号段分配保证 |
| 延迟 | 微秒级（纯内存） | 微秒级（内存号段） |
| 趋势递增 | 是 | 是（段内递增） |
| 对外部依赖 | 无（仅需机器 ID 初始化） | 依赖 DB 分配号段 |
| 扩容复杂度 | 需要管理机器 ID | 需要新增号段 |
| 最大风险 | 时钟回拨导致重复 | DB 不可用导致服务启动阻塞 |
| 信息安全 | 好（非连续） | 一般（段内连续） |
| 实现复杂度 | 中（时钟回拨处理复杂） | 低 |

**生产级推荐：号段模式作为默认选择。** 原因很直接：大多数业务场景下数据库的可用性远好于系统时钟的稳定性。时钟回拨是硬件/OS 层面的问题，无法在应用层完全解决；而数据库 99.99% 可用可以通过主从 + 异地多活轻易达成。雪花算法适用于需要完全无状态、跨机房部署的极致场景（如接入层的 requestId）。

**加分项：** 提到百度的 UidGenerator——基于号段模式的工业级实现，使用 ring buffer 平滑 ID 分配、提前异步加载下一段、通过 CachedUidGenerator 适配高并发场景。提到美团的 Leaf——同时支持 Segment 模式（号段）和 Snowflake 模式（雪花），并通过 ZooKeeper 来替代雪花算法中的机器 ID 手动分配，实现了自动注册和回收。提到 Twitter Snowflake 原始实现中机器 ID 是 hardcode 在配置文件中的，这就是为什么后来美团的 Leaf 改用 ZooKeeper 顺序节点来自动分配——推广到 100 台机器后手动配置是不可维护的。

## Q6：如何解决时钟回拨问题？

### 考察点
对分布式系统中"信任边界"的理解——能不能认识到时钟不可信，以及在不同严重程度下采取的分层防御策略。

### 解答思路
1. 先定义时钟回拨的场景分类（短时微调 vs 长时间跳变 vs 重启重置）。
2. 从轻到重给出三层防御策略——内核级、运行时级、外部依赖级。
3. 强调终极方案是"不信任时钟"，而非试图修复时钟。

### 参考答案

**时钟回拨的三种典型场景：**

1. **NTP 微调（最常见）：** NTP 客户端发现本地时钟与 NTP 服务器偏差几毫秒，逐步校准（slew mode），每次回拨不超过几毫秒。这是正常行为，但雪花算法的序列号是基于毫秒为单位判断的，即使是 1ms 的回退也可能导致重复 ID。
2. **长时间跳变：** 虚拟机休眠后唤醒、物理机 BIOS 电池没电、手动执行 `date -s`。时钟可能回退数小时，所有依赖时间戳的系统全部出问题。
3. **冷启动时间重置：** 机器重启时 BIOS 时间未同步，系统启动时钟被初始化为 1970 年，直到 NTP 同步完成。这期间所有基于时间戳的逻辑全部异常。

**分层防御策略：**

**第一层——内核级（内核参数防御，最可靠且无业务侵入）：**
```bash
# /etc/ntp.conf 中限制时间跳变幅度
tinker panic 0  # 禁止 NTP 在偏差过大时退出

# 使用 chronyd 替代 ntpd
# chronyd 的默认行为更保守：大偏差时先 step 再逐步 slew
# 配合 -x 参数：chronyd -x（禁止 step，永远只 slew）
```

**关键配置建议：**
- 生产环境用 `chronyd` 替代 `ntpd`，它更擅长处理间歇性网络和时钟跳变
- 配合 `-x` 参数禁止 step，始终用 slew 模式避免突然跳变
- 设置 `maxslewrate` 限制每秒最大调整速率（如 83333 ppm，即每秒最多调整 83ms）

**第二层——运行时级（应用层容忍短回拨，最常见方案）：**

```java
// 方案一：回拨等待法（容忍几毫秒的回拨）
long lastTimestamp = getLastTimestamp();
long currentTimestamp = System.currentTimeMillis();
if (currentTimestamp < lastTimestamp) {
    long offset = lastTimestamp - currentTimestamp;
    if (offset <= 5) {  // 5ms 以内等待即可
        Thread.sleep(offset + 1);  // sleep 到超过上次时间戳
        currentTimestamp = System.currentTimeMillis();
    } else {
        throw new ClockBackwardsException("回拨超过 5ms, 拒绝服务");
    }
}

// 方案二：扩展位法（美团的 Leaf 方案）
// 在原来的 Snowflake 结构上增加"时钟回拨计数位"
// 发生回拨时，回拨计数位 + 1，有效延长序列号的取值范围
// 本质上是用额外的 bit 为时钟回拨留了缓冲

// 方案三：借用未来时间法
// 发生时钟回拨时，不抛异常，将 lastTimestamp 保持不变
// 序列号继续递增，直到用完该毫秒的所有序列号
// 缺点：短期内容忍，但序列号耗尽后仍需处理
```

**第三层——外部依赖级（基于 ZK 的 Lease 机制，彻底去除对本地时钟的依赖）：**

美团的 Leaf Snowflake 实现：用 ZooKeeper 的持久顺序节点替代"时间戳 + 机器 ID"中的机器注册部分。关键在于每个 Worker 在 ZooKeeper 上注册一个临时顺序节点，定期上报时间戳。ZK 集群来判断"是否发生了回拨"——如果 Worker 上报的时间戳小于它上次上报的值，ZK 认为发生了回拨，拒绝为此 Worker 分配新的 sequence。

**终极方案——不信任时钟：**
如果系统重要性足够高（如资金流水号），**直接不使用雪花算法**，改用号段模式（Segment Mode）。号段模式完全基于数据库号段分配，与时钟无关——这是最简单的解决方案，也是大多数业务场景的最优解。

**防御层级总结：**

```
轻度回拨 (< 5ms) → 运行时等待（几乎无成本）
中度回拨 (< 1s)  → 扩展位/未来时间（增加 bit 开销）
重度回拨 (> 1s)  → ZK Lease 检测 + 报警 + 人工介入
终极方案         → 不用雪花算法，改用号段模式
```

**加分项：** 提到 Google 的 TrueTime（Spanner 论文 2012）——通过原子钟 + GPS 在数据中心内建立了 7ms 以内的时钟误差范围，对外提供单时间戳的确定性信任。虽然硬件成本极高，但证明了"本地时钟不可信，可信时钟需要外部设备辅助"这一工程原则。提到 AWS 的 Time Sync Service（2017）——通过在每个 EC2 实例本地运行 chrony + 本地 GPS 支撑的参考时钟，将误差控制在 1ms 以内，让云上用户也能享受到近似 TrueTime 的时间质量。提到数据库方案 Phoenix（HBase 生态）通过单调递增的 sequence number 代替 timestamp 作为 MVCC 版本号，彻底避免了所有时钟依赖问题——这是一个工程设计中的经典思路：当你无法解决一个问题时，考虑从设计上去掉引发这个问题的依赖。

## Q7：分布式幂等性如何设计？

### 考察点
能否区分不同层次的幂等性需求（数据库/接口/消息），并针对每一层给出最简实现，而非一套方案打天下。

### 解答思路
1. 先明确幂等性要解决的核心问题——"操作重复执行得到相同结果"。
2. 分层讲解：数据库层（唯一键 + 乐观锁）、接口层（Token 机制 + 状态机）、消息层（消费者去重）。
3. 强调生产级实现的关键细节：幂等键的设计、过期清理、并发竞态。

### 参考答案

**幂等性的本质理解：**

幂等 ≠ 不重复执行。幂等是"重复执行的结果和执行一次相同"。扣款 100 元不是幂等的（重复扣就扣 200 了），但"设置余额为 100 元"是幂等的。所以幂等设计的核心是将"增量操作"转化为"绝对赋值"或"带条件的增量操作"。

**第一层：数据库级幂等**

**(A) 唯一索引约束——最可靠的方式：**
```sql
-- 使用业务幂等键作为唯一索引
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    request_id VARCHAR(64) NOT NULL,
    -- ...
    UNIQUE KEY uk_request_id (request_id)
);
```
原理：`INSERT ... ON DUPLICATE KEY UPDATE`（MySQL）/ `INSERT ... ON CONFLICT DO NOTHING`（PostgreSQL）。利用数据库的 ACID 特性，从根本上杜绝重复写入。
- **关键选择：幂等键字段。** 幂等键通常是业务单据号或客户端生成的 requestId（UUID），不是自增 ID。
- **并发处理：** 同时插入相同幂等键的请求，一个成功一个失败（DuplicateKeyException），失败方查询已有数据后返回。

**(B) 乐观锁——幂等更新：**
```sql
UPDATE account
SET balance = balance - 100, version = version + 1
WHERE user_id = 123 AND version = 5;  -- version 5 是上次读到的版本
```
如果受影响行数为 0，说明发生了并发修改，回退业务逻辑或重试。

**(C) 状态机——串行化操作：**
```java
// 订单状态：PENDING -> PAID -> DELIVERED -> COMPLETED
// 状态机保证一个操作只能从特定状态转移到下一个状态
public void paySuccess(String orderId) {
    int affected = update(
        "UPDATE orders SET status = 'PAID' WHERE order_id = ? AND status = 'PENDING'",
        orderId
    );
    if (affected == 0) {
        // 要么已经支付过了（幂等），要么状态异常
        log.warn("重复支付回调或状态异常, orderId={}", orderId);
    }
}
```

**第二层：接口级幂等（Token 机制）**

流程：
1. 客户端先调用 `/api/getToken` 获取一个全局唯一 Token
2. 服务端将 Token 存入 Redis：`SET token:xxx 1 EX 300`（5 分钟过期）
3. 客户端请求业务接口时参数中带上 Token
4. 服务端用 `DEL token:xxx` 的返回值判断——返回 1 表示首次使用，返回 0 表示重复请求

```java
// Redis Lua 脚本保证原子性
String lua = """
    if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('DEL', KEYS[1])
    else
        return 0
    end
""";
// 返回 1 表示合法请求，返回 0 表示非法或重复请求
```

**Token 机制的关键细节：**
- Token 必须有过期时间，否则 Redis 内存泄漏
- `获取 Token` 和 `提交业务` 之间可能因客户端异常中断产生"空悬 Token"，过期机制可自动清理
- 高并发下 Token 判断必须原子操作（Lua 脚本）

**第三层：消息级幂等（消费者去重）**

消息重复消费的来源：生产者重试 + 消费者处理成功但 Ack 超时 + MQ 的 at-least-once 投递语义。

去重方案：
```
消费消息 -> 尝试 Redis SETNX msg_id (EX 业务处理超时时间的 2 倍)
  ├── 成功 -> 处理业务 -> 提交 offset
  └── 失败 -> msg_id 已存在 -> 直接 Ack（丢弃重复消息）
```

**幂等键设计原则：**
- **粒度匹配：** 幂等键的粒度必须与操作的业务含义一致。扣库存的幂等键不能和创建订单共用，否则一个幂等键只能处理一个操作。
- **生命周期管理：** 幂等键记录不能无限保留。定时清理 N 天前的数据，保留周期 > 业务重试窗口的最大时长。
- **可追溯性：** 幂等键记录中保留原始请求的参数 snapshot，方便问题排查（"这个幂等返回是怎么回事？"）。

**加分项：** 提到 Stripe 的幂等设计——所有 POST 请求通过 `Idempotency-Key` header 传递幂等键，服务端将首次请求的完整响应缓存 24 小时，重复请求直接返回原始响应（而不仅是去重）。这种设计让客户端可以安全地重试任何写操作，不必担心网络超时后的重试产生副作用。提到微信支付的"支付通知回调重试机制"——微信支付在收到支付通知的成功响应前会持续重试（15s/15s/30s/180s/1800s/1800s/3600s），所以商户系统必须保证回调处理的幂等性，通常以微信订单号（transaction_id）作为幂等键。

## Q8：接口幂等性如何保证？CQRS命令查询职责分离的适用场景？

### 考察点
能否将接口幂等性从单机层面提升到分布式层面的完整方案设计，以及从业务语义出发判断 CQRS 的适用边界。

### 解答思路
1. 接口幂等性从客户端到服务端全链路分析（生成幂等键 → 传输 → 校验 → 兜底返回）。
2. CQRS 从"什么是"到"为什么用"到"什么时候不该用"逐步分析。
3. 强调两者的内在联系——CQRS 中的 Command 天然需要幂等。

### 参考答案

**接口幂等性——全链路保障方案：**

**(1) 幂等键生成策略：**

| 策略 | 示例 | 适用场景 | 风险 |
|------|------|----------|------|
| 业务自然键 | `orderNo + operationType` | 有确定业务单据号的操作 | 需确认唯一性 |
| 客户端 UUID | `UUID.randomUUID()` | 前后端分离架构 | UUID 可能被客户端丢失重试 |
| 业务字段哈希 | `MD5(userId + amount + timestamp)` | 批量接口 | 同一业务请求参数完全相同便是重复，无法区分"想要再操作一次" |

**生产推荐：客户端生成 UUID 作为幂等键，通过 HTTP Header `X-Idempotency-Key` 传递。** 这是 Stripe、PayPal 等支付系统的标准实践。

**(2) 服务端校验流程：**

```
请求到达 -> 解析 X-Idempotency-Key
  -> Redis SETNX (key, processing) EX 30s  // 锁定幂等键
    ├── 成功（首次请求）-> 执行业务逻辑 -> 存储结果 -> 更新 Redis 状态
    │                                              └── SET (key, result) EX 86400
    └── 失败 -> GET key 判断状态
          ├── 值为 "processing" -> 返回 409 Conflict（还在处理中）
          └── 值为 结果数据 -> 直接返回缓存的结果（幂等返回）
```

**关键细节：**
- **锁的超时时间：** 略大于业务处理的 P99 延迟。太短容易并发冲突（锁提前释放），太长导致客户端等待过久。
- **结果缓存时间：** 24 小时通常足够。Stripe 的默认值是 24 小时。
- **并发请求处理：** 对于几乎同时到达的重复请求，第一个拿到锁，第二个 409，并非两个都通过。

**(3) 数据库兜底：**
接口层幂等是防御性编程，最终保障仍然是数据库层的唯一键。Redis 可能挂掉、锁可能过期，但数据库的唯一约束是永不失效的最后一道防线。

```sql
CREATE TABLE payment_orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    idempotency_key VARCHAR(64) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    -- ...
    UNIQUE KEY uk_idempotency_key (idempotency_key)
);
```

代码中 catch `DuplicateKeyException`，从数据库中查询已存在的记录，按幂等语义返回。

**CQRS（Command Query Responsibility Segregation）——命令查询职责分离：**

**核心思想：** 将"写操作（Command）"和"读操作（Query）"使用不同的模型、不同的数据库、甚至不同的服务来实现。Command 修改数据但不返回数据（或只返回操作结果），Query 只读取数据不修改数据。

```java
// CQRS 风格接口设计
// Command：修改状态
POST /api/orders          // 创建订单
PUT  /api/orders/{id}/pay // 支付订单

// Query：查询状态
GET  /api/orders/{id}           // 查询单个订单
GET  /api/orders?userId=123     // 查询用户订单列表
```

**CQRS 的优势：**

1. **读写分离，独立优化：** 读模型可以针对查询场景做反范式设计（宽表、预聚合），写模型可以保证事务一致性（标准范式表）。MySQL 负责写，Elasticsearch 负责搜索读——就是典型的 CQRS。
2. **独立扩容：** 读请求通常是写请求的 10-100 倍，可以单独给读服务加机器，不干扰写服务。
3. **简化复杂领域：** 在 DDD 中，CQRS 使 Command 模型聚焦于业务规则和聚合的一致性，Query 模型只关注如何高效地从多个聚合中拼装数据返回。

**CQRS 的适用场景（满足以下至少 2 条才应考虑）：**

| 信号 | 说明 |
|------|------|
| 读写比 > 10:1 | 读远大于写，独立优化读路径有显著收益 |
| 查询需要多表 Join 或跨聚合 | 单个查询需要关联 5+ 张表，反范式化能极大降低延迟 |
| 读写模型差异大 | 写模型需要严格范式保证一致性，读模型需要宽表保证查询性能 |
| 有独立搜索需求 | 全文搜索、复杂过滤等，需要 ES 等搜索引擎 |
| 事件溯源架构 | 配套使用 Event Sourcing，CQRS 几乎是最佳拍档 |

**CQRS 的不适用场景：**

| 信号 | 风险 |
|------|------|
| 业务逻辑简单 | 过度设计，CRUD 足以应付，CQRS 增加维护成本 |
| 对一致性要求高 | 读写分离后存在同步延迟，需要额外的最终一致性保障 |
| 团队经验不足 | CQRS 增加了系统复杂性，维护成本高 |
| 没有独立扩容需求 | 单体应用 + 数据库读写分离已经足够 |

**CQRS 和接口幂等性的关系：**

CQRS 中的 Command 天然需要幂等性。原因很直接——Command 通常由消息驱动（Command Bus / Message Queue），而消息传递是 at-least-once 的。如果 Command 不幂等，消息重试就会导致业务错误（重复扣款、重复发货）。

**生产实践经验：**
- 先做"数据库读写分离 + 缓存"，这是 CQRS 的最小可行版，80% 的场景够用了
- 只有读到"查了 5 张表拼装数据还特别慢"时，才考虑独立读模型
- CQRS + Event Sourcing 是组合技，但不是套餐——不用 Event Sourcing 的 CQRS 完全可行

**加分项：** 提到 Axon 框架——Java 生态中 CQRS + Event Sourcing 的标杆实现，将 Command + Event + Aggregate 的生命周期管理完全规范化。提到 Kafka 作为 CQRS 的 Event Store（日志不可变 + 可重放）在 Netflix、Uber 的应用——DDD 聚合的状态变化以事件流的形式写入 Kafka，Query 端从 Kafka 消费事件构建自己的查询视图（Kafka Streams 做流式聚合）。这是 CQRS 在大数据量场景下的工业级实践范式。提到 Greg Young（CQRS 术语的创造者）的一句话："CQRS is not a top-level architecture. It's a pattern that you apply when you need it."——强调 CQRS 不该是默认选择，而是解决特定问题的工具。

## Q9：常见的负载均衡算法有哪些？如何进行服务划分？

### 考察点
候选人是否理解不同负载均衡算法的适用场景和 trade-off，以及服务划分的工程方法论——是背算法名字还是真正做过生产级服务治理。

### 解答思路
1. 先枚举常见算法，按"无状态均衡"和"有状态均衡"两大类分别讲解原理和适用场景。
2. 重点讲解一致性哈希——它是理解分布式缓存、分片数据库、RPC 路由的基础，候选人必须能讲清楚哈希环和虚拟节点的设计。
3. 服务划分部分从"垂直拆分（业务域）"到"水平拆分（读写分离、分库分表）"两个维度讲方法，结合实际项目经验。

### 参考答案

**一、负载均衡算法分类**

**1. 无状态均衡算法（不关心请求归属）：**

| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| 轮询（Round Robin） | 依次分配，循环往复 | 实现简单，绝对公平 | 无视节点负载差异 | 节点同配置、短连接场景 |
| 加权轮询 | 按权重比例分配，Nginx 默认使用平滑加权轮询 | 适配异构集群 | 权重需人工维护 | 服务实例配置不同的 K8s 集群 |
| 随机 | 随机选取节点 | 简单，比轮询更"无状态" | 分配不均（小流量明显） | Dubbo 默认策略 |
| 最小连接数 | 选择当前活跃连接最少的节点 | 真实反映负载 | 需维护连接计数 | 长连接场景（WebSocket、RPC） |
| 最短响应时间 | 选择历史响应时间最小的节点 | 自适应性最强 | 需持续采集延迟数据 | Envoy/Linkerd 这类 Service Mesh 代理 |

**2. 有状态均衡（一致性哈希）：**

一致性哈希的核心场景是**节点变化时，尽可能少的请求被重新分配**。映射过程：
1. 构造一个 0 ~ 2^32-1 的哈希环
2. 将每个节点的 IP 算哈希值，映射到环上
3. 请求的 key（如用户 ID）算哈希值，顺时针找到第一个节点
4. 节点增减时，只影响相邻节点的数据，不触发全量路由变更

**虚拟节点**是生产中的关键优化——为每个物理节点生成 150-200 个虚拟节点散列在环上，解决两个问题：
- **数据倾斜：** 物理节点只映射到环上少数位置，放大实际负载差异
- **增减节点时的雪崩：** 物理节点少时，去掉一个节点导致大片请求重新分配

生产配置经验：虚拟节点数 = max(150, 实际节点数 * 5)。

**二、服务划分方法论**

**垂直拆分（按业务域）：**
- 用户服务、订单服务、支付服务——按 DDD 的限界上下文划分
- 判断标准：服务间数据耦合度低、团队组织匹配（康威定律）、独立部署频率不同
- **生产铁律：** 不要按技术层划分（DAO 层一个服务、Service 层一个服务），这是分布式单体，跨层调用把网络延迟放大成性能灾难

**水平拆分（按数据量/流量）：**
- 读写分离：CQRS 模式，写走主库、读走从库，读服务独立扩容
- 分库分表：按租户 ID（SaaS 多租户）、按用户 ID（社交/电商）、按时间（日志/监控数据）
- 冷热分离：热数据 Redis/TiKV，冷数据对象存储归档

**服务划分的决策优先级：**
1. 你能独立部署吗？（无状态优先 → 有状态后拆）
2. 出问题影响哪些功能？（按故障爆炸半径反向设计）
3. 数据是否天然分开？（有明确分片键的先拆）

**加分项：** 提到 Nginx 的平滑加权轮询算法（SWRR）的退化问题——某权重节点失效时，算法会在 n 次请求内收敛到新的权重分布，收敛速度比传统加权轮询快。提到 Envoy 的 Maglev 一致性哈希——Google 开源的哈希算法，查找时间复杂度 O(1)（经典一致性哈希是 O(log n)），通过查找表预先计算提升转发面性能，适合高吞吐网关场景。提到 Dubbo 3.x 的自适应负载均衡——基于 P2C（Power of Two Choices）结合 EWMA（指数加权移动平均）计算节点评分，比最小连接数更能反映真实负载（避免了瞬时波动导致的错误判断）。

## Q10：常用的限流算法有哪些？滑动窗口、令牌桶、漏桶的区别和原理？

### 考察点
候选人是否能从"算法原理 -> 编码实现 -> 分布式扩展 -> 生产踩坑"的完整链路讲清楚限流，而不是停留在"令牌桶一秒放 N 个令牌"的层面。

### 解答思路
1. 从"为什么需要限流"切入——流量突发、资源保护、公平性三个动机。
2. 分别讲解四种算法的原理、伪代码、优缺点，突出"代码怎么写"而不是"理论怎么说"。
3. 重点给出四种算法的差异对比表，让候选人能根据场景做选择。

### 参考答案

**一、固定窗口计数器**

算法逻辑：将时间轴切成固定窗口（如 1s），每个窗口内维护一个计数器，超过阈值就拒绝。下一个窗口计数器归零。

```
窗口：[0, 1s] → 计数器 cnt，请求超过 limit 拒绝
窗口：[1s, 2s] → 计数器归零，重新计数
```

**致命缺陷——"双倍流量"问题：** 假设 1s 窗口限制 100 个请求，在 0.9s-1.0s 涌入 100 个请求（合法），在 1.0s-1.1s 涌入 100 个请求（合法但两个窗口相邻），实际 0.9s-1.1s 这 200ms 内通过了 200 个请求，相当于两倍流量。根本原因是窗口边界是固定死的，无法感知跨边界的流量突增。

**二、滑动窗口**

算法逻辑：将每个大窗口（如 1s）拆成多个小格子（如 10 个格子，每个 100ms），记录每个小格子的请求数。判断时统计过去 N 个小格子的请求总和，超过阈值拒绝。

```
Redis 实现（ZSET）:
- key: rate_limit:{api_name}:{user_id}
- member: 请求时间戳（微秒）
- score: 请求时间戳（微秒）
- 每次请求：ZREMRANGEBYSCORE 删除窗口外的记录，ZCARD 统计当前窗口内记录数
- ZCARD > limit → 拒绝；否则 ZADD 并放行
```

**三、令牌桶（Token Bucket）**

算法逻辑：以固定速率往桶里放入令牌（r 个/秒），桶容量为 B。请求来时取令牌，取到就放行，取不到就拒绝/排队。

```
伪代码：
lastRefillTime = now()
tokens = B  // 初始满令牌

func allow():
    now = now()
    elapsed = now - lastRefillTime
    tokens = min(B, tokens + elapsed * r)  // 补充令牌
    lastRefillTime = now
    if tokens >= 1:
        tokens -= 1
        return true
    return false
```

**关键参数：** r（速率）控制长期平均吞吐量，B（桶容量）控制允许的突发流量大小。假设 r=100/s，B=200：如果一段时间没有流量，桶里攒了 200 个令牌，突发流量可以一波消耗完——这就是令牌桶允许一定突发的能力来源。

**生产级注意：** 上述算法有一个隐患——如果长时间无流量，`elapsed` 会非常大，`tokens` 会涨到 B。但当经过一个超大 `elapsed` 后，只计算到了 `min(B, ...)` 这个上限，实际损失的令牌就是你"过期"的突发额度。这个行为是正确的（桶容量限制了最大突发），但要理解它的含义。

**四、漏桶（Leaky Bucket）**

算法逻辑：请求先进队列，以固定的速率从队列中取出请求处理。队列满则拒绝/丢弃。

```
伪代码：
queue = []
lastDrainTime = now()

func allow(req):
    // 先排水
    now = now()
    drainCount = (now - lastDrainTime) * rate
    for i in range(drainCount):
        if queue not empty: queue.poll()
    lastDrainTime = now
    // 再入队
    if queue.size() >= capacity:
        return reject
    queue.add(req)
    return accept
```

**核心特征：** 漏桶强制平滑——不管上游流量怎么突发，下游看到的处理速率始终是恒定的。它不关心"你是什么时候来的"，只关心"我什么时候能处理你"。

**差异总结表：**

| 维度 | 固定窗口 | 滑动窗口 | 令牌桶 | 漏桶 |
|------|----------|----------|--------|------|
| 核心思路 | 窗口内计数 | 滚动时间窗口计数 | 按速率补充令牌，请求消耗令牌 | 请求排队，恒速处理 |
| 突发处理 | 不支持（双倍流量问题） | 不支持（流量超阈值即拒绝） | **支持**（桶容量即允许的突发量） | **不支持**（强制平滑） |
| 实现复杂度 | 极简单 | 中（Redis ZSET 实现） | 中（Guava RateLimiter 20 行） | 中（需维护队列） |
| 适用场景 | 低流量 API（快速上线） | 需要精确控制窗口内总请求数 | **网关/API 限流首选** | 消息队列消费端保护数据库 |
| 流量整形能力 | 无 | 弱 | 强（Burst 模式） | 最强（恒定速率） |
| Redis 分布式 | 简单（INCR + EXPIRE） | 可行（ZSET + ZREMRANGEBYSCORE） | 需要 Lua 脚本保证原子性 | 需要分布式队列，复杂 |

**加分项：** 提到 Guava RateLimiter 的 SmoothBursty 和 SmoothWarmingUp 两种实现——SmoothBursty 允许秒级突发（冷系统没有预热），SmoothWarmingUp 有预热期（冷启动时逐步提升速率到目标值，适合刚重启的数据库保护场景）。提到 Sentinel 的滑动窗口实现——使用 LeapArray（环形数组 + 时间窗口滑动），每个格子用 LongAdder 统计（无锁 + 高并发），比 Redis ZSET 方案性能高一个数量级但只支持单机。提到 Redis + Lua 实现分布式令牌桶的关键——Lua 脚本保证"补充令牌 → 判断 → 扣减"三步原子性，避免并发竞态；Cluster 模式下注意 Lua 脚本必须保证所有 key 在同一个 slot（用 hash tag）。

## Q11：自研限流器：令牌桶参数有没有考虑预热？限流和熔断的区别？

### 考察点
候选人是否真正落过地——是否理解冷启动预热的重要性，以及能否区分"流控"和"断路"两个不同维度的保护机制。

### 解答思路
1. 先解释令牌桶预热的概念和为什么需要——刚重启的系统需要逐步放量，避免瞬时打垮。
2. 给出预热令牌桶的实现思路（从 Guava SmoothWarmingUp 的原理出发），讲清楚"预热期"和"稳定期"的令牌生成速率曲线。
3. 对比限流和熔断的本质区别，从触发条件、保护对象、恢复机制三个维度讲清楚。

### 参考答案

**一、令牌桶的预热（Warm Up）问题**

标准令牌桶在系统冷启动时可能造成"保护失效"：

**场景：** Redis 刚重启，缓存全空，此时大量请求穿透到数据库。标准令牌桶从初始时刻就开始全速发放令牌（如 1000 QPS），数据库瞬间承受全量流量——限流器"放过去了 1000 QPS"，但数据库刚启动时连 100 QPS 都扛不住。

**预热令牌桶的核心思想：** 冷启动时速率从低到高逐步爬升，经过预热期后达到稳态速率。生成速率的曲线不是平的，而是一个从 1/3 * stableRate 逐渐爬到 stableRate 的过程。

```
key = rate_limiter:预热:{resource}
初始令牌数 = 0（冷启动）
预热因子 coldFactor = 3（默认值）
预热周期 warmupPeriod = 10s（从 1/3 速率爬升到全速率的时间）

速率公式（简化）：
stableInterval = 1 / stableRate（稳定态每发一个令牌间隔）
斜率 = (coldFactor - 1) * stableInterval / warmupPeriod
当前速率 = stableInterval + 斜率 * (maxPermits - storedPermits)

// 当 storedPermits 少（系统繁忙）：间隔小（速率快）
// 当 storedPermits 多（系统空闲，即冷启动）：间隔大（速率慢，需要预热）
```

Guava 的 `RateLimiter.create(permitsPerSecond, warmupPeriod, TimeUnit)` 就是这个实现。Sentinel 的 `WarmUpRule` 也提供了相同能力。

**生产配置经验：**
- `warmupPeriod` 通常设为 2-3 倍的数据库连接池预热时间（连接池预热约 3-5s → warmupPeriod 设 10s）
- `coldFactor` 默认 3 是合理的，极端场景可调大到 5-10
- **不是所有接口都需要预热**——只对依赖了"有冷启动代价"的后端（数据库、缓存、消息队列）的接口加预热
- 预热和 Hystrix 的信号量/线程池隔离配合使用——预热阶段 + 快速熔断，双重保护冷启动

**二、限流 vs 熔断的本质区别**

| 维度 | 限流（Rate Limiting） | 熔断（Circuit Breaking） |
|------|----------------------|--------------------------|
| **触发条件** | 流量超过阈值（QPS / 并发数） | 失败率/慢调用率超过阈值 |
| **保护对象** | 保护服务自身（防止被打垮） | 保护下游依赖（防止被拖死） |
| **决策依据** | 流量指标（QPS、令牌数） | 健康指标（错误率、RT） |
| **核心动作** | 拒绝超出阈值的请求 | 快速失败，不调用下游 |
| **恢复机制** | 下一个时间窗口自动恢复 | 熔断打开后进入半开探测，探测成功才恢复 |
| **状态模型** | 无状态（或弱状态：令牌数） | **有明确状态机**（关闭 → 打开 → 半开 → 关闭） |
| **典型框架** | Guava RateLimiter, Sentinel | Hystrix, Resilience4j, Sentinel |
| **一句话总结** | "你来太多了，我接不住" | "你不对劲，我先不调你了" |

**二者的互补关系：**
- 限流是**第一道防线**——入口处通过 QPS 控制保证系统不超负荷
- 熔断是**第二道防线**——已经放进去的请求，如果下游开始大量失败，熔断器快速切断，防止线程资源耗尽
- 生产标配：**网关层限流（Nginx/Sentinel Gateway）+ 服务调用层熔断（Resilience4j/Sentinel）**，形成纵深防御

**加分项：** 提到 Sentinel 的"流量整形"三种模式——直接拒绝（Default）、Warm Up（预热）、匀速排队（RateLimiter 的漏桶模式，让请求以固定间隔通过，适合处理突发流量如秒杀）。提到 TCP BBR 拥塞控制与预热令牌桶的相似性——都是通过探测可用带宽来动态调整发送速率，而非简单粗暴的丢包/AIMD。提到生产中的一个经典错误——限流和熔断都用"直接抛异常"的方式拒绝请求，导致上游无差别对待两种异常（应该用不同的异常类型或错误码区分，让上游决定是重试还是降级）。

## Q12：熔断和降级的区别是什么？

### 考察点
候选人是否理解熔断和降级是不同层次、不同触发时机、不同执行主体的保护机制——90% 的候选人会混为一谈，能清晰区分的通常是真正在生产环境排过障的。

### 解答思路
1. 从"谁触发的、触发时机、保护谁、怎么恢复"四个维度讲清熔断和降级的本质区别。
2. 用具体场景串联两个机制的执行顺序，让候选人理解它们如何协同工作。
3. 给出差异总结表。

### 参考答案

**熔断（Circuit Breaking）和降级（Fallback / Degradation）是两种不同的保护手段，但经常被混用。先厘清定义：**

**熔断：** 当调用下游服务连续失败达到阈值时，熔断器自动打开（Open），后续请求不再调用下游，直接快速失败。熔断是**被动的、自动的、基于失败率统计的**。

**降级：** 当系统压力过大或依赖不可用时，主动关闭非核心功能或返回兜底数据，保证核心链路可用。降级可以是**主动的（人工开关触发）也可以是被动的（熔断触发降级逻辑）**。

**关键区别在于：降级是"我决定不做什么"，熔断是"我检测到你不正常所以不调你了"。**

**四维对比表：**

| 维度 | 熔断（Circuit Breaking） | 降级（Fallback / Degradation） |
|------|--------------------------|-------------------------------|
| **触发者** | 框架自动检测（失败率/慢调用率） | 人工配置（开关）或熔断自动触发 |
| **触发时机** | 运行时：下游异常累计到阈值 | 事前：预估流量高峰（大促）；事中：熔断打开后触发 |
| **保护对象** | 保护自身线程资源不被下游拖垮 | 保护核心链路、核心资源不被非核心功能占用 |
| **核心动作** | 短路调用（不调用下游） | 返回兜底结果（默认值/缓存/静态页） |
| **是否调用下游** | 熔断打开时不调用 | 降级可能调用下游（返回兜底），也可能不调用 |
| **恢复条件** | 半开探测成功 → 关闭熔断 | 人工恢复开关 / 依赖恢复 |
| **典型框架/工具** | Hystrix, Resilience4j CircuitBreaker, Sentinel | Sentinel 降级规则, Apollo 开关 + 自定义降级逻辑 |

**场景串联——一个请求的完整保护链路：**

```
                    ┌─────────────────────────────────┐
                    │     智能网关                      │
                    │   1. 限流（QPS > 阈值？→ 拒绝）     │
                    └──────────┬──────────────────────┘
                               │ 放行
                    ┌──────────▼──────────────────────┐
                    │     订单服务                      │
                    │   2. 调用支付服务 → 熔断器状态？    │
                    │      ├─ 关闭 → 正常调用            │
                    │      ├─ 打开 → 不调支付，走降级逻辑  │
                    │      └─ 半开 → 探测性调用           │
                    └──────────┬──────────────────────┘
                               │
                    ┌──────────▼──────────────────────┐
                    │     降级策略（Fallback）            │
                    │   3. 返回兜底数据：                  │
                    │      - 支付状态查询 → 缓存中的状态    │
                    │      - 推荐列表 → 静态热门推荐       │
                    │      - 用户头像 → 默认头像           │
                    └─────────────────────────────────┘
```

**生产中的降级分类：**

| 降级类型 | 触发方式 | 示例 |
|----------|----------|------|
| **人工降级** | 运维通过配置中心关闭 | 大促前关闭"猜你喜欢"，CPU 留给下单链路 |
| **自动降级** | 熔断打开后的 fallback | 支付服务熔断后返回"支付处理中"提示 |
| **开关降级** | 代码中 if-else + Apollo 开关 | `if (degradeSwitch) return cachedData;` |
| **限流降级** | 被限流后走降级逻辑 | 超过 QPS 不直接抛错，返回静态降级数据 |

**加分项：** 提到 Netflix Hystrix 的设计哲学——每个 HystrixCommand 都必须有 `getFallback()`，这本质上是"熔断和降级强制绑定"。但 Sentinel 选择了更灵活的设计——熔断规则和降级规则分离配置，允许熔断触发时做不同的事（抛异常 / Fallback 函数 / 什么都不做只记日志）。提到降级的"有损服务"理念——降级不是不做，是用更少的资源做更少的事。比如热门商品详情页在 Redis miss 时不查数据库（降级），直接返回缓存在 CDN 的静态 HTML，用户看到的是一个"稍微不新鲜"的页面，而不是一个 500 错误。提到 SRE 中的错误预算（Error Budget）与降级的关联——当错误预算耗尽时，系统应自动进入全局降级模式，优先保障核心功能，这是 Google 的实践范式。

## Q13：什么是分布式服务雪崩？熔断降级核心解决什么问题？

### 考察点
候选人是否理解雪崩的形成机制（级联失败 + 资源耗尽的正反馈循环），以及熔断降级如何从"阻断传播链"和"保障核心链路"两个维度来解决雪崩——要求能画链路图讲清楚级联过程。

### 解答思路
1. 先用具体链路讲解雪崩的形成过程，用"线程池耗尽"串联 3 层服务的级联失败。
2. 分析雪崩的两个关键因素——"级联失败"和"资源耗尽的正反馈循环"。
3. 对应给出熔断和降级分别如何打断这个循环。

### 参考答案

**一、雪崩是如何形成的（三层级联失败）**

假设一个典型的微服务调用链路：`Gateway → 订单服务 → 支付服务 → 账户服务`。

```
第 1 步（故障点）：账户服务因为数据库慢查询开始响应变慢，RT 从 50ms 涨到 5s。

第 2 步（资源耗尽）：支付服务调用账户服务的线程池（假设 200 个线程）在 5s 内被全部占满，
新来的请求进不了线程池，开始排队或直接拒绝。

第 3 步（级联传播）：订单服务调用支付服务也开始超时（因为支付服务的线程都在等账户服务返回），
订单服务的线程池也开始耗尽。

第 4 步（雪崩）：Gateway 调用订单服务也开始超时，用户的请求从最上游就开始失败。
整个链路的所有服务（即使没有任何问题的服务）都被拖垮。
```

**雪崩的两个关键因素：**

1. **级联失败（Cascading Failure）：** 下游故障 → 上游调用超时 → 上游资源被堵住 → 上游也开始故障 → 更上游也故障。就像多米诺骨牌。

2. **资源耗尽的正反馈循环：** 线程池满了 → 请求排队 → RT 更长 → 线程占用的时间更长 → 线程池更满。这是一个自我加强的恶性循环。HTTP 连接池、数据库连接池都一样——资源耗尽后系统进入"假死"状态，看起来活着但完全不响应。

**二、熔断如何阻断雪崩**

熔断的核心是**在失败的传播链上插一个"断路器"**。回到上面的场景：

```
支付服务 → 账户服务：账户服务变慢，但支付服务的熔断器检测到
"5s 内错误率 80%"，熔断器打开 → 后续对账户服务的调用直接返回失败，
线程立刻释放 → 支付服务的线程池没有被耗尽 → 雪崩链在支付服务这里被切断了。
```

**熔断解决的核心问题：快速失败，保护线程资源。** N 个线程等待下游超时所浪费的时间，足够处理 N * (timeout / normalRT) 个正常请求。熔断就是把这 N 个线程的等待时间节省下来，让上游还能正常处理其他请求。

**三、降级如何保障核心链路**

降级解决的是"当部分依赖不可用时，如何保证核心功能还能跑"。继续上面的场景：

```
订单服务调用支付服务被熔断 → 订单服务执行降级逻辑：
- 不创建新支付，改为"支付处理中"状态
- 返回给用户："您的订单已生成，支付结果请稍后查看"
- 关键点：下单成功了（核心链路保住），只是支付确认有延迟（非核心体验降级）
```

**二者在各层分工清晰：**

| 位置 | 策略 | 解决的问题 |
|------|------|-----------|
| 服务调用方 | 熔断 | 防止自己线程被下游拖垮 |
| 服务调用方 | 降级（Fallback） | 下游不可用时通过兜底逻辑保证自身可用 |
| 服务提供方 | 限流 | 防止自己被打垮 |
| 全局 | 降级（Degradation） | 关非核心功能保核心链路 |

**加分项：** 提到雪崩的三种典型触发场景——（1）慢 SQL 导致数据库连接池耗尽；（2）热点 Key 导致缓存击穿，瞬间流量全部打到数据库；（3）消息队列消费慢导致积压，上游 RPC 超时。提到"雪崩演练"的生产实践——Netflix 的 Chaos Monkey 和阿里的大促压测，本质上就是在演练"如果某个依赖炸了，你的保护机制能不能在 3 秒内响应"。提到 Sentinel 的"自适应系统保护"——不设固定阈值，根据系统 Load、CPU 使用率、RT、并发线程数自适应调整入口流量，这是一种"反雪崩"的全局视角（入口流量和系统负载形成负反馈而非正反馈）。

## Q14：请详细讲解熔断器的核心状态机，包括完整的状态流转规则。半开状态的核心作用是什么？

### 考察点
候选人是否理解熔断器三种状态的完整流转逻辑，以及半开状态为什么是熔断器设计的"精髓"——它解决了"如何安全地尝试恢复"这个最棘手的问题。

### 解答思路
1. 画出完整的三态状态机，讲清每个状态的进入条件和退出条件。
2. 重点剖析"半开状态"的设计智慧——为什么不是 Open 直接切到 Close。
3. 给出 Resilience4j 的生产级配置示例，把状态机参数化。

### 参考答案

**一、熔断器三态状态机**

```
                    ┌─────────────────────────────────────┐
                    │           熔断器状态机                │
                    │                                      │
                    │    ┌──────────────────────────┐      │
                    │    │        CLOSED（关闭）      │      │
                    │    │  正常调用下游，统计指标    │      │
                    │    └──────┬───────────┬───────┘      │
                    │           │           │              │
                    │    失败率达到阈值    │              │
                    │    或慢调用率达到阈值  │              │
                    │           │           │              │
                    │           ▼           │              │
                    │    ┌──────────────────┴───┐          │
                    │    │    OPEN（打开）       │          │
                    │    │  直接拒绝，不调下游   │          │
                    │    │  启动一个计时器       │          │
                    │    └──────────┬──────────┘          │
                    │           │                          │
                    │    等待时间到（sleepWindow）           │
                    │           │                          │
                    │           ▼                          │
                    │    ┌──────────────────────────┐      │
                    │    │  HALF_OPEN（半开）         │      │
                    │    │  放行少量探测请求           │      │
                    │    └──────┬───────────┬───────┘      │
                    │           │           │              │
                    │    探测成功（失败率 < 阈值）  │         │
                    │           │    探测失败（失败率 >= 阈值）│
                    │           ▼           ▼              │
                    │    ┌──────────┐ ┌──────────┐        │
                    │    │  CLOSED  │ │   OPEN   │        │
                    │    │ 恢复正常 │ │ 继续熔断 │        │
                    │    └──────────┘ └──────────┘        │
                    └─────────────────────────────────────┘
```

**状态流转规则详解：**

**CLOSED → OPEN：**
- **条件：** 在统计窗口（slidingWindowSize）内，失败率（failureRateThreshold）达到阈值，或慢调用率（slowCallRateThreshold）达到阈值，且经过最小调用次数（minimumNumberOfCalls）的统计。minimumNumberOfCalls 的意义：刚启动时前面几个请求都失败，失败率 100%，如果此时就打开熔断器等于"一枪就崩"，这个参数防止误熔断。
- **动作：** 熔断器记录当前时间 `openTime = now()`，进入 OPEN 状态。

**OPEN → HALF_OPEN：**
- **条件：** 从 OPEN 开始经过 `waitDurationInOpenState`（通常叫 sleepWindow）时间。设计意图是给下游一个"冷静期"，让它有时间自我修复（如数据库连接池恢复、慢 SQL 被 kill 掉）。
- **动作：** 自动转换，不需要外部触发。

**HALF_OPEN → CLOSED：**
- **条件：** 在 HALF_OPEN 状态下，放行的探测请求失败率低于阈值（通过 `permittedNumberOfCallsInHalfOpenState` 控制探测请求数量，默认 10 个）。
- **动作：** 熔断器重置所有统计计数器，回到 CLOSED。

**HALF_OPEN → OPEN：**
- **条件：** 探测请求的失败率仍然高于等于阈值。
- **动作：** 重新记录 openTime，回到 OPEN 状态，再等一个 sleepWindow 后重试。

**二、半开状态（HALF_OPEN）的核心作用**

半开是熔断器设计的精髓，它解决了三个问题：

**1. 避免"立即重试"造成二次雪崩。** 如果 OPEN 直接切到 CLOSED，等于对下游说"时间到了，我信任你了"，但下游可能根本没恢复。半开状态相当于"我先派个侦察兵过去看看"。

**2. 控制探测流量的爆炸半径。** 不是全量放开，而是只放行 `permittedNumberOfCallsInHalfOpenState` 个请求（Resilience4j 默认 10 个）。这 10 个请求即使全部超时，占用的线程数也是可控的（不会超过 10 个），不会引发二次雪崩。

**3. 提供渐进式恢复。** 探测流量成功后不是立即全量放开，而是逐步不限制（Resilience4j 在半开状态下，如果探测请求全部成功，会立即转为 CLOSED 并全量放开）。这种设计保证了恢复过程是"验证 → 信任 → 全量"的渐进式，而不是赌博式的。

**Resilience4j 配置示例：**

```yaml
resilience4j.circuitbreaker:
  instances:
    paymentService:
      slidingWindowType: COUNT_BASED        # 基于请求数统计
      slidingWindowSize: 100                # 统计最近 100 次请求
      minimumNumberOfCalls: 20              # 至少 20 次调用后才判断
      failureRateThreshold: 50              # 失败率 50% 触发熔断
      slowCallRateThreshold: 100            # 慢调用率 100% 触发熔断
      slowCallDurationThreshold: 3000ms     # RT > 3s 算慢调用
      waitDurationInOpenState: 10000ms      # OPEN 10s 后进入半开
      permittedNumberOfCallsInHalfOpenState: 10  # 半开允许 10 个探测
      automaticTransitionFromOpenToHalfOpen: true # 自动从 OPEN→HALF_OPEN
```

**加分项：** 提到 Hystrix 的熔断器设计差异——Hystrix 只有一个 `sleepWindow`（默认 5s），半开后只放 1 个请求判断是否恢复，过于保守（一个请求的成功/失败随机性太大）。Resilience4j 允许配置多个探测请求（默认 10 个），用概率降低误判。提到 Netflix 的"自适应熔断"实践——不是固定阈值，而是动态计算下游的"健康分数"（基于成功率和延迟的 P99 值），健康分数连续低于阈值才触发熔断（连续 N 个采样窗口都低分），防止瞬时波动导致误熔断。提到半开状态下并发探测请求的处理——Resilience4j 用 `AtomicInteger` + CAS 控制并发探测数，超过 `permittedNumberOfCallsInHalfOpenState` 的请求直接拒绝，这保证了半开状态的资源占用是有上界的。

## Q15：主流的熔断策略有哪些？各自的核心逻辑和适用场景？

### 考察点
候选人是否能区分"慢调用比例熔断"和"异常比例熔断"这两种主流策略，以及是否会基于不同下游的特点选择不同的熔断策略——不是在背配置项，而是在做架构决策。

### 解答思路
1. 按 Sentinel/Resilience4j 的分类，逐一讲清三种熔断策略的核心逻辑。
2. 每种策略给出适用场景和配置建议，体现"不同服务不同策略"的实践经验。
3. 用对比表总结"什么时候用什么策略"。

### 参考答案

**主流熔断策略分为三类（以 Sentinel 的定义为准，Resilience4j 语义类似）：**

**一、慢调用比例熔断（Slow Call Ratio）**

**核心逻辑：** 统计窗口内，响应时间超过 `maxAllowedRT`（如 3s）的请求占比达到 `slowRatioThreshold`（如 50%），且总请求数达到 `minRequestAmount`（如 10 个），触发熔断。

**设计意图：** 捕获"下游正在变慢但还没完全故障"的中间态。很多生产故障的早期表现是 RT 缓慢上升（数据库连接池逐渐耗尽、缓存逐出导致更多磁盘 I/O），慢调用比例熔断能在这个阶段介入，比"等下游完全报错"更及时。

**适用场景：**
- 对响应时间敏感的服务（C 端用户实时请求 > B 端后台任务）
- 数据库依赖（数据库慢查询不会直接报错，而是 RT 飙升到 5s-10s）
- 第三方 API 调用（对方不报错，但响应特别慢）

**配置建议：**
```
慢调用 RT 阈值：P99 RT * 2-3 倍（如日常 P99 = 500ms → 阈值设 1500ms）
慢调用比例阈值：50%-80%（不需要 100%，出现一半慢调用就应该警觉）
最小请求数：10-20 个（避免小样本误判）
统计窗口：10-30s（太短容易抖动，太长反应太慢）
```

**二、异常比例熔断（Error Ratio）**

**核心逻辑：** 统计窗口内，异常（Exception / HTTP 5xx）的请求占比达到 `errorRatioThreshold`（如 50%），且总请求数达到 `minRequestAmount`，触发熔断。

**设计意图：** 这是最经典的熔断策略，用明确的错误信号（异常/5xx）作为熔断条件。信号最强、误判率最低。

**适用场景：**
- 下游返回明确错误码（500、连接拒绝、超时 Exception）
- RPC 调用（Dubbo/gRPC 直接抛 RpcException）
- 对一致性要求高的服务（宁愿熔断也不接受静默失败）

**配置建议：**
```
异常比例阈值：50%（过半失败即熔断，阈值太高反应太慢，太低容易误熔断）
最小请求数：20（避免 1-2 个失败就误判）
统计窗口：10-30s
注意：异常的严重程度不一致——Connection Refused 和 Timeout 都是异常，
但 Timeout 更需要快速熔断（因为每个 Timeout 消耗了完整的超时等待时间），
可以用加权异常计数或单独配置 Timeout 的敏感度
```

**三、异常数熔断（Error Count）**

**核心逻辑：** 统计窗口内，异常请求的绝对数量超过 `errorCountThreshold`（如在一分钟内超过 50 个），触发熔断。

**设计意图：** 大流量接口用比例熔断效果好，但对于 QPS 很低的服务（如每分钟几个请求），50% 异常率意味着 2 个失败中 1 个异常就熔断了，很可能误判。异常数熔断给出了一个"绝对门槛"，无论比例如何，异常数没到就不熔断。

**适用场景：**
- 低 QPS 服务（如后台管理系统、定时任务调用的接口）
- 作为异常比例熔断的补充条件（两个策略同时配置，谁先触发谁生效）

**配置建议：**
```
异常数阈值：根据接口的 SLA 来定，如每分钟允许最多 10 个失败
注意：统计窗口内，异常数是累计值，窗口滑动后旧记录过期，计数会下降
```

**四种策略的差异总结：**

| 策略 | 判定依据 | 灵敏度 | 误判风险 | 最适用场景 |
|------|----------|--------|----------|-----------|
| 慢调用比例 | RT 超阈值的比例 | 高（能捕捉故障早期信号） | 中（下游正常变慢可能误判） | 数据库、第三方 API、C 端同步接口 |
| 异常比例 | 异常/5xx 的比例 | 中（信号明确） | 低（基本不会误判） | RPC 调用、HTTP 服务间调用 |
| 异常数 | 异常的绝对数量 | 低（需要累计到阈值） | 低 | 低 QPS 接口、定时任务 |
| 信号量隔离 | 并发线程数达到上限 | 高 | 中 | 不直接报错但要防止线程耗尽 |

**加分项：** 提到 Netflix 的"自适应熔断"——不是固定阈值策略，而是使用岭回归（Ridge Regression）预测下游的失败概率，根据预测值动态调整熔断阈值，比固定阈值响应更快且误判率更低。提到 Sentinel 的"混合策略"——可以同时配置慢调用比例 + 异常比例，满足任一条件就熔断，这是一种"OR"逻辑的多维度保护。生产经验：不要只用一种策略，至少同时配"慢调用比例 + 异常比例"；慢调用保护 RT 飙升，异常比例保护直接报错，两种场景互不覆盖。提到 CPU/LOAD 系统指标触发的熔断——Sentinel 支持基于系统 Load、CPU 使用率的熔断，当系统 Load > 阈值时直接拒绝所有入口请求，这是比服务级熔断更宏观的保护，在"全站压力大"时比逐个服务熔断更有效。

## Q16：生产环境中熔断阈值的核心配置最佳实践是什么？如何设计一套微服务全链路的熔断降级体系？

### 考察点
候选人是否具备生产级熔断配置的经验——不是会写配置，而是知道"这个参数设多少、为什么、出问题怎么调"。全链路熔断降级体系的能力，是高级工程师和架构师的分水岭。

### 解答思路
1. 逐一给出每个熔断参数的配置原则和调优经验，附带生产级配置示例。
2. 从"入口 → 中间 → 底层"三个层面设计全链路保护体系，讲清每层用什么工具、保护什么。
3. 给出配置管理、灰度放量、演练验证等生产实践。

### 参考答案

**一、熔断阈值的核心配置最佳实践**

**1. 滑动窗口大小（slidingWindowSize）：10-30 秒**

- 太短（< 5s）：瞬时的网络抖动可能触发熔断，导致不必要的服务中断（"假阳性"）
- 太长（> 60s）：下游已经故障了 30s 才开始熔断，30s 内已经把上游线程资源耗尽了
- **经验值：10-30s，优先选 30s。** 30s 是平衡"防抖动"和"快速响应"的最佳点
- 为什么是 30s？因为 Kubernetes Pod 健康检查默认是 30s，运维能理解的故障检测周期也在这个量级

**2. 失败率阈值（failureRateThreshold）：50%**

- 太低（< 30%）：轻微的业务异常就会触发全量熔断，业务可用性下降（出现大量人工告警）
- 太高（> 80%）：大部分请求都失败了才熔断，保护效果大打折扣
- **经验值：50%。** "过半失败"是明确的信号——这不是偶发故障，是系统性故障
- 对于支付/交易链路可以降到 30%（更敏感），对于搜索推荐可以升到 70%（容忍度高）

**3. 最小调用次数（minimumNumberOfCalls）：20-50**

- 过小：刚启动时 3 个请求都失败，33% 失败率触发熔断（冷启动误判）
- 过大：真正故障时等 100 个请求都失败才熔断（响应太慢）
- **经验值：20-50。** 这是一个"统计显著性"的门槛——少于 20 个样本，失败率没有统计意义

**4. 熔断休眠时间（waitDurationInOpenState）：10-60 秒**

- 太短（< 5s）：下游故障还没恢复就开始探测，延长故障时间
- 太长（> 120s）：下游早就恢复了（如数据库主从切换 10s 完成），你在那干等 2 分钟
- **经验值：30-60s。** 配合监控告警，运维收到告警 → 定位问题 → 修复，这个过程通常 1-5 分钟。sleepWindow 设 30s 意味着"2 次探测内如果有修复，自动恢复"
- **高级用法：指数退避——** 第 1 次熔断等 30s，第 2 次等 60s，第 3 次等 120s...最大 300s。这样对于短暂故障快速恢复，对于长故障减少无效探测

**5. 半开探测请求数（permittedNumberOfCallsInHalfOpenState）：10-20**

- **经验值：10。** 10 个请求的样本量能给出 90% 置信度的故障判断（如果 10 个里有 5 个失败，失败率大概率 > 50%）
- 低 QPS 接口可以设为 3-5（探测本身就占用了很多配额）

**6. 慢调用 RT 阈值（slowCallDurationThreshold）：P99 * 2-3 倍**

- 不要拍脑袋设 1s 或 3s，要根据真实监控数据
- **经验方法：** 取过去 7 天的 P99 RT，乘以 2-3 倍。日活 P99 = 200ms → 设 500ms；数据库查询 P99 = 50ms → 设 150ms
- 定期 review：每季度根据最新的 P99 数据调整阈值

**二、全链路熔断降级体系设计**

一个完整的微服务全链路保护体系，从外到内分 4 层：

```
                    ┌─────────────────────────────────────────────┐
                    │ 第 1 层：网关层（全域保护）                      │
                    │ Nginx/Kong/APISIX                            │
                    │ - IP 级别限流（防止单 IP 刷接口）                 │
                    │ - 接口级别限流（/api/order QPS 上限）             │
                    │ - 网关级熔断（后端 5xx 比例 > 50% → 熔断该路由）    │
                    │ - 全局降级开关（大促时一次性关非核心接口）           │
                    └────────────────────┬────────────────────────┘
                                         │
                    ┌────────────────────▼────────────────────────┐
                    │ 第 2 层：服务治理层（RPC/SDK 保护）              │
                    │ Sentinel / Resilience4j                      │
                    │ - 每个 Feign/Dubbo 调用→独立的熔断器             │
                    │ - 热点参数限流（秒杀商品 ID 单独限制）              │
                    │ - 系统自适应保护（CPU > 80% → 全局限流）          │
                    │ - 线程池隔离（核心链路独立线程池，不被非核心拖垮）     │
                    └────────────────────┬────────────────────────┘
                                         │
                    ┌────────────────────▼────────────────────────┐
                    │ 第 3 层：中间件保护层                           │
                    │ 数据库连接池（HikariCP）                       │
                    │ - connectionTimeout: 30s → 降到 5s（快失败）    │
                    │ - maximumPoolSize: 按"核心业务 20/非核心 10"    │
                    │ 缓存（Redis）                                 │
                    │ - 热点 Key 自动发现 + 本地缓存（如 Caffeine）     │
                    │ - 缓存穿透：布隆过滤器 + 空值缓存                 │
                    │ 消息队列（RocketMQ/Kafka）                     │
                    │ - 消费端限流（listener concurrency 控制并发度）   │
                    │ - 死信队列 + 人工介入（避免无限重试）              │
                    └────────────────────┬────────────────────────┘
                                         │
                    ┌────────────────────▼────────────────────────┐
                    │ 第 4 层：基础设施层                             │
                    │ 容器/K8s                                     │
                    │ - Pod HPA 自动扩容（CPU > 60% 扩容）            │
                    │ - Readiness Probe 失败自动摘除流量              │
                    │ - PDB（PodDisruptionBudget）保证最小可用数       │
                    │ 存储                                         │
                    │ - 数据库只读副本自动切换（ProxySQL/RDS 自动故障转移）│
                    └─────────────────────────────────────────────┘
```

**配置管理最佳实践：**

1. **熔断参数统一管理：** 所有微服务的熔断配置集中在配置中心（Apollo/Nacos），不要散落在各服务的 yaml 文件里。好处是出问题可以热更新，不需要重启服务。

2. **按环境差异化：** 
   - 开发环境：熔断阈值宽松（避免频繁熔断影响开发效率）
   - 预发环境：完全同步生产配置（压测时可以验证熔断策略）
   - 生产环境：精细配置 + 监控告警

3. **灰度放量：** 新熔断策略先在 10% 流量验证 24 小时，观察无异常误熔断后全量放开。

4. **熔断事件的可观测性：**
   - 每次状态变更（OPEN / HALF_OPEN / CLOSED）记录 INFO 日志 + 上报 metrics
   - 熔断打开时发送告警（企业微信/飞书/PagerDuty）
   - Prometheus + Grafana 面板展示每个服务的熔断状态、失败率、慢调用率

5. **定期混沌工程演练：** 每季度至少做一次"断网演练"——随机注入一个下游不可用，验证：
   - 熔断器是否在预期时间内打开？
   - 降级逻辑是否正确执行？
   - 监控告警是否及时触发？

**加分项：** 提到"熔断保护的反模式"——（1）把 Hystrix/Sentinel 的 fallback 写成"return null"，导致 NPE 在更上游爆发；（2）所有服务用同一套熔断配置（一条慢 SQL 拖垮全站）；（3）未配置线程池隔离，1 个慢服务的线程耗尽影响了同进程的其他服务调用。提到 Service Mesh（Istio/Envoy）做全链路熔断的优势——不需要在业务代码中嵌入 Sentinel 依赖，Envoy 通过 Outlier Detection（异常检测）在 Sidecar 层面自动熔断不健康的上游实例，业务代码零侵入。但 Sidecar 熔断只能基于连接级别的指标（连接失败、TCP 超时），无法感知业务级别的异常（订单状态返回错误码），所以 Service Mesh 熔断通常作为基础层的保护，业务语义级别的熔断仍然需要 SDK 层实现。提到阿里双十一的"全链路压测 + 限流降级"战术——大促前对全链路进行"摸高"压测，通过压测结果反向优化各层的限流和熔断阈值，做到"不靠运气、靠数据"的策略制定。

## Q17：Resilience4j和Sentinel的核心定位与区别是什么？

### 考察点
考察候选人对微服务容错框架的选型判断力，能否根据团队技术栈和公司基础设施做出合理决策。

### 解答思路
1. 先明确两者的出身背景和技术生态，这是理解差异的基石
2. 从架构模型、规则管理、监控体系等维度做结构化对比
3. 给出实际的选型决策树，避免"看心情选"

### 参考答案

这个问题本身就是一个很好的面人题——面试官往往不是想听你背两者的功能列表，而是看你有没有真正在项目中做过技术选型。两者的差异本质上是设计哲学的分野：**Resilience4j 是"库"，Sentinel 是"平台"。**

| 维度 | Resilience4j | Sentinel |
|------|-------------|----------|
| 出身 | Java 函数式编程社区，灵感来自 Hystrix 但重写 | Alibaba 中间件团队，生产验证于双十一 |
| 设计哲学 | 轻量库（Library），按需组合，无外部依赖 | 管控平台（Dashboard + SDK），开箱即用 |
| Netty 依赖 | 无 | 有（Sentinel Dashboard 基于 Netty） |
| 规则管理 | 代码内硬编码或自定义配置源 | 控制台实时推送 + 本地文件降级 + 动态数据源 |
| 流量整形 | 基础限流（令牌桶/信号量） | 更丰富：基于调用关系的限流、热点参数限流、集群限流、自适应限流 |
| 熔断策略 | 按失败率/慢调用率/失败数熔断 | 同上，额外支持按异常比例/异常数熔断 |
| 系统自适应保护 | 无内置 | 内置（根据 CPU Load、RT、入口 QPS 自动限流） |
| 监控 | 通过 Micrometer 对接 Prometheus/Datadog 等 | Sentinel Dashboard 自带监控，也支持 Prometheus |
| Spring Boot 集成 | spring-cloud-starter-circuitbreaker-resilience4j | spring-cloud-starter-alibaba-sentinel |
| 国际化 | 英文社区活跃，Netflix 替代方案首选 | 中文文档最佳，国内大厂首选 |

**关键差异深挖：**

**1. 规则管理的本质不同**

Resilience4j 的规则配置在你的 `application.yml` 里，改一次熔断阈值需要重新部署。这对做海外业务、团队有完善的 CI/CD pipeline + GitOps 流程的团队来说不是问题——配置即代码本身就是最佳实践。但对国内电商场景，大促时需要临时调整限流阈值、随时切换降级开关，Sentinel Dashboard 的可视化操作 + 实时推送就是刚需。

如果你用 Resilience4j 但又需要动态规则，也有方案——自己写一个 ConfigurationProperties 监听器对接 Apollo/Nacos，但不等于 Sentinel 直接内置了这个能力。

**2. 生态绑定问题**

用 Sentinel 意味着你在 Spring Cloud Alibaba 生态里。如果你整个微服务体系已经是 Spring Cloud Netflix 或 Spring Cloud Kubernetes，引入 Sentinel 的 Dashboard 等于多了一套运维组件。而 Resilience4j 作为纯 Library，可以无缝对接到你已有的 Micrometer -> Prometheus -> Grafana 可观测体系。

**3. 生产选型决策树**

```
你的公司是否已有 Sentinel/Spring Cloud Alibaba 基础设施？
├── 是 → 用 Sentinel（不要重复造轮子，成本最低）
└── 否 → 继续问
        是否已经在用 Spring Cloud 标准体系（Gateway/Config/Micrometer）？
        ├── 是 → 用 Resilience4j（零额外运维组件）
        └── 否 → 继续问
                是否需要大促级别的实时流量管控能力？
                ├── 是 → Sentinel（Dashboard 是刚需）
                └── 否 → Resilience4j（简单够用）
```

**加分项：** 提到 Sentinel 的"集群限流"实现——多个 Sentinel Client 通过 Token Server 共享一个全局 QPS 配额，解决单机限流不精确的问题（如限流 100 QPS，100 台机器每台限 1 还是总共 100？）。提到 Resilience4j 的 `Bulkhead`（舱壁隔离）是 Hystrix 线程池隔离的升级版——用 SemaphoreBulkhead 替代线程池，零上下文切换开销，但要注意信号量隔离无法阻断被调用方的超时（线程池隔离可以 `future.cancel`），所以需要配合 `@TimeLimiter` 使用。

## Q18：Sentinel实现熔断、限流的底层原理？Seata是怎么进行分布式事务控制的？

### 考察点
考察对中间件底层实现的理解深度，能否脱离 Spring Boot 启动器层面的认知，解释真实的工作原理。

### 解答思路
1. Sentinel 部分分两部分讲：限流的滑动窗口算法和熔断的状态机
2. Seata 部分从 AT 模式切入讲 undo_log 机制，再提 TCC 和 Saga
3. 给出两者在生产环境的高可用部署方案

### 参考答案

**一、Sentinel 底层原理**

Sentinel 的内核只有两个核心概念：**Resource（资源）** 和 **Rule（规则）**。所有的工作都由一串 **Slot Chain（责任链）** 完成。

```
请求进入 → NodeSelectorSlot(构建调用树) → ClusterBuilderSlot(统计簇点)
 → StatisticSlot(核心：做统计) → FlowSlot(限流检查) → DegradeSlot(熔断检查)
 → AuthoritySlot(黑白名单) → SystemSlot(系统自适应保护) → 业务逻辑
```

**限流的底层：LeapArray 滑动窗口**

Sentinel 没有用常见的令牌桶或漏桶，而是实现了一个叫 `LeapArray` 的滑动窗口数据结构：

```
环形数组，固定 N 个窗口（默认 2 个，每个窗口 500ms）
当前时间 currentTimeMillis / 500ms → 定位到某个窗口格
如果当前格的时间已过期 → 重置该格的计数 → 返回当前格 → 自增计数
通过"当前窗口计数 + 所属窗口计数"判断是否超过阈值
```

这个设计的精妙之处在于：**O(1) 的时间复杂度，几乎无锁（只对单个窗口格做 CAS），极低的内存占用。** 和普通的滑动窗口（维护一个有序队列，每次请求都要扫一遍窗口）相比，LeapArray 性能高出 1-2 个数量级。

**Sentinel 的 QPS 限流默认是"饥饿模式"**——它不等一个完整的 1 秒窗口过去再判断，而是用的 `warm up` 或 `default` 两种控制器。默认控制器每秒发放一次"通行证"，当剩余令牌不够时直接拒绝，没有积压排队（排队模式需要单独开启 `RateLimiterController`）。

**熔断的底层：状态机 + 断路器**

Sentinel 的熔断是基于"熔断器状态机"：

```
CLOSED（正常）→ 探测周期内慢调用比例或异常比例超过阈值 → OPEN
OPEN（熔断中）→ 经过指定"熔断时长"后 → HALF_OPEN
HALF_OPEN（探测中）→ 放行一个请求 → 成功 → CLOSED；失败 → OPEN
```

这里的关键实现细节：
- 慢调用的 RT 上限是 `StatisticConfig.maxRt`（默认 4900ms，可以改），超过这个值被截断为 maxRt，避免偶发的极端值干扰整体统计
- 异常比例统计会区分"业务异常"和"熔断本身的降级异常"，降级异常不算入异常比例（避免熔断打开后再统计到降级异常导致无法恢复）
- HALF_OPEN 阶段放行几个请求是可配置的（`maxHalfOpenProbeCount`），放太多了可能直接被流量打死，放太少了探测不准确

**二、Seata 分布式事务原理**

Seata 的 AT 模式是目前使用最广的模式，底层原理一句话：**自动生成反向 SQL（undo_log），在事务回滚时执行反操作。**

```
全局事务流程（两阶段，但非 XA 标准的 2PC）：

阶段一（执行 + 注册）：
  1. 解析业务 SQL，生成前镜像（BEFORE_IMAGE）和后镜像（AFTER_IMAGE）
  2. 执行业务 SQL
  3. 将 undo_log（包含前后镜像 + 反向 SQL）插入到同一个本地事务中
  4. 提交本地事务 + 向 TC（Transaction Coordinator）注册分支事务

阶段二（提交或回滚）：
  - 全局提交：TC 异步通知各 RM 删除对应的 undo_log（异步、快速）
  - 全局回滚：TC 通知各 RM 执行 undo_log 中的反向 SQL 回滚数据
```

**Seata AT 模式的三个角色：**
- **TC（Transaction Coordinator）：** 独立部署的服务端，维护全局事务状态
- **TM（Transaction Manager）：** 在业务发起方（标注 @GlobalTransactional 的方法），负责开启/提交/回滚全局事务
- **RM（Resource Manager）：** 每个参与事务的微服务，管理自己的 undo_log 和本地事务

**Seata 的三种模式对比：**

| 模式 | 原理 | 适用场景 | 优缺点 |
|------|------|---------|--------|
| AT | 自动生成 undo_log，反向补偿 | 基于关系数据库的微服务 | 零侵入，但对 SQL 有要求（必须 WHERE 带主键） |
| TCC | 手动实现 Try/Confirm/Cancel 三阶段 | 对一致性要求极高的金融场景 | 侵入性大，但不会有脏读 |
| Saga | 正向服务 + 正向补偿服务 | 长事务、老系统无 TCC 接口 | 一阶段就提交，可能出现脏读，需幂等 |

**生产环境 Seata 高可用部署：**

TC（Seata-Server）必须集群部署，否则单点故障。存储模式建议用 DB 模式（undo_log 持久化到 MySQL），配置多个 TC Server 连接同一个数据库。客户端通过注册中心（Nacos/Eureka）发现 TC Server 集群，实现故障转移。

**加分项：** 提到 Seata AT 模式的"脏读问题"——因为 AT 模式一阶段就已经提交了本地事务，在全局事务还没提交前，其他事务可以读到这个未提交的数据（虽然二阶段可能回滚）。解决方案是 Seata 的 `@GlobalLock` 注解 + SELECT FOR UPDATE，或利用 Seata 的全局锁机制。提到 Sentinel 在 Seata 场景下的应用——TC Server 的 RPC 调用需要熔断保护（如果 TC 不可用，业务不能无限重试导致雪崩），建议单独给 TC 调用配置一个限流 + 熔断规则。

## Q19：高并发秒杀系统如何设计？如何解决超卖？库存扣减是先减Redis再同步数据库吗？

### 考察点
考察高并发写场景的架构设计能力，特别是缓存和数据库的一致性、扣减顺序的选择。

### 解答思路
1. 从流量漏斗角度逐层削峰：CDN → 网关限流 → 业务校验 → 队列异步
2. 库存扣减方案对比：Redis 递减 vs 数据库乐观锁，给出混合方案
3. 回答核心问题：扣减顺序的选择依据

### 参考答案

**秒杀系统的核心矛盾：** 瞬时极高并发（百万 QPS 级别）vs 数据库的有限写入能力（MySQL 单库几千 TPS）。所以设计思路从来不是"让数据库扛住"，而是"让数据库尽量少干活"。

**全链路架构（从用户点击到库存扣减完成）：**

```
第 1 层：CDN + 前端
- 秒杀页面静态化（HTML/CSS/JS 全部 CDN，含缓存策略为 max-age=0 或 must-revalidate）
- 按钮状态由异步接口获取（避免 CDN 缓存了按钮状态）
- 点击瞬间按钮置灰 + 防重（前端兜底，但不能依赖）

第 2 层：网关（Nginx/Kong）
- IP 级别限流：单 IP 每秒 10 次请求
- 接口级别限流：/seckill/submit 每秒 10 万 QPS（防止流量透传到后端）
- 对于超限请求直接返回"活动太火爆"（Nginx 层面返回，不进入 JVM）

第 3 层：商品详情/库存状态缓存（Redis）
- 秒杀开始前将库存预热到 Redis：SET seckill:stock:{skuId} 1000
- 用户点击后，后端先读 Redis 判断库存是否 > 0
- 库存为 0 直接返回"已售罄"（这层拦截 99% 的无效请求）

第 4 层：库存预减 + MQ 异步下单
- Redis Lua 脚本原子操作：DECR seckill:stock:{skuId}，判断返回值 >= 0
- 返回值 >= 0 → 发 MQ 消息到下单队列 → 返回"排队中"
- 返回值 < 0 → INCR 回滚 → 返回"已售罄"

第 5 层：MQ 消费者（削峰填谷）
- 消费下单消息，校验资格（是否已买过、是否在黑名单）
- 数据库执行最终扣减 + 创建订单
```

**回答核心问题：是先减 Redis 再同步数据库吗？**

**是的，核心方案就是"Redis 前置扣减 + 数据库异步最终扣减"。** 选择 Redis 前置扣减的原因：
1. **Redis 单线程处理 Lua 脚本，天然原子性**，不会有并发超卖
2. **Redis QPS 是数据库的 100 倍以上**（单机 10 万+ vs 单库几千）
3. **数据库只用在最终落库时扣减**，这时候请求已经被 MQ 削峰了，数据库完全没有压力

**但是"Redis 先扣"有个问题**：如果 Redis 扣了，数据库还没扣，Redis 就挂了怎么办？答案是：
- **Redis 持久化（RDB + AOF）** 保证 Redis 重启后库存可恢复
- **Redis 主从 + Sentinel** 做高可用
- **最坏情况**：Redis 数据丢了，就要依赖数据库的实际库存来对账修正（对账任务每小时跑一次）

**超卖解决方案总结：**

| 方案 | 原理 | QPS 上限 | 超卖风险 | 适用场景 |
|------|------|----------|---------|---------|
| 数据库悲观锁 (SELECT FOR UPDATE) | 锁住库存行 | ~1000 | 无 | 低并发，强一致性 |
| 数据库乐观锁 (version CAS) | UPDATE stock=stock-1 WHERE stock>=1 AND version=? | ~2000 | 极小 | 一般并发 |
| Redis DECR + Lua 原子化 | Lua 脚本内判断+扣减 | ~10 万 | 无（Redis 单线程） | 秒杀（推荐） |
| Redis 预减 + MQ 异步落库 | 混合方案 | ~10 万+ | 需对账兜底 | 高并发秒杀（最佳实践） |

**加分项：** 提到"库存一致性对账"机制——定时任务每 5 分钟对比 Redis 库存和数据库库存，差异超过阈值（如 5 个）立即告警 + 自动修正。提到"数据库层面也要加乐观锁"——即使 Redis 已经扣减了，MQ 消费者在数据库 UPDATE 时也要加 `WHERE stock >= quantity`，双重保险防超卖。提到"Redis 扣减的溢出处理"——Lua 脚本里库存减到负数后要立即 INCR 回滚，避免 Redis 里的库存变成负数导致后续所有请求都被误判为售罄。提到"秒杀商品预热策略"——秒杀开始前 1 分钟把商品库存从数据库加载到 Redis，开始前 10 秒把商品详情也预热到本地缓存（Caffeine），双重预热避免缓存击穿。

## Q20：秒杀设计考虑的最主要几个问题是什么？怎么保证库存不出错？

### 考察点
考察能否抓住秒杀系统的核心矛盾，而不是陷入技术细节的罗列。

### 解答思路
1. 归纳秒杀系统需要解决的 5 个核心问题
2. 库存正确性从三个维度保证：并发安全、一致性、容灾兜底
3. 给出库存正确性的完整验证链路

### 参考答案

**秒杀的 5 个核心问题（按优先级排序）：**

```
优先级 1：保证库存不出错（超卖 = 资损，少卖 = 流量浪费）
优先级 2：系统不崩溃（再好的设计扛不住流量也没用）
优先级 3：用户体验可接受（排队可以，但不能白屏或一直报错）
优先级 4：公平性（防黄牛、防脚本、防同一个用户买多件）
优先级 5：可回滚、可对账（出问题能追回来）
```

**库存不出错的三个保证维度：**

**维度一：并发安全——扣减操作的原子性**

这是最基础也是最重要的。所有并发方案本质上是"用性能换正确性"的博弈：

- **方案 A（淘汰）：** Java `synchronized` / `ReentrantLock` —— 单机锁，分布式环境下完全无效
- **方案 B（淘汰）：** Redis `SETNX` 分布式锁 —— 性能太差，秒杀场景会成为瓶颈
- **方案 C（推荐）：** Redis Lua 脚本原子执行 —— Redis 单线程执行 Lua，天然串行化

```lua
-- 库存扣减 Lua 脚本（关键代码）
local stock = redis.call('GET', KEYS[1])
if not stock then
    return -1  -- 库存 key 不存在
end
if tonumber(stock) <= 0 then
    return 0   -- 售罄
end
local afterStock = redis.call('DECR', KEYS[1])
if afterStock < 0 then
    redis.call('INCR', KEYS[1])  -- 回滚
    return 0
end
return afterStock  -- 返回剩余库存
```

**维度二：多层防御——不依赖单点保护**

库存不出错不能只靠 Redis Lua 脚本一层保护，万一有 Bug 怎么办？需要多层防御：

```
第 1 层：Lua 脚本的原子扣减（主防线）
第 2 层：数据库乐观锁 UPDATE stock = stock - quantity WHERE stock >= quantity（兜底）
第 3 层：数据库唯一约束 UNIQUE(user_id, sku_id)（防同一用户重复购买）
第 4 层：对账任务每 5 分钟对比 Redis 和 MySQL 的库存数据
```

**维度三：最终一致性——异步扣减的对账和补偿**

Redis 扣减成功 + MQ 消息发送成功 ≠ 数据库最终扣减成功。消息可能丢失，消费者可能宕机。需要：

1. **MQ 消息持久化 + 消费者手动 ACK：** 只有数据库扣减成功后才 ACK，失败则重试
2. **定时对账任务：** 每小时跑一次，对比"Redis 已扣总数"和"数据库已创建订单数"
3. **库存校准机制：** 公式 = 总库存 - 数据库订单数 = 实际剩余库存，用这个值修正 Redis
4. **告警阈值：** Redis 库存 vs 数据库库存偏差超过 5 个就触发 P0 告警

**实践中的一个常见踩坑：**

很多人认为 Redis DECR 后小于 0 就代表超卖了，然后用 INCR 回滚。但如果这个过程不是 Lua 原子脚本，在 GET 和 DECR 之间可能已经被其他请求插入，导致判断不准确。所以**整个"判断 + 扣减 + 回滚"必须在同一个 Lua 脚本中完成**，不能拆成多个 Redis 命令。

**加分项：** 提到"预热造数验证"——上线前在预发环境构造多种异常场景：Redis 突然宕机、MQ 积压 100 万消息、数据库主库切换。通过混沌工程验证库存对账机制在这些极端情况下是否仍能保证最终一致性。提到"库存补偿的反向操作"——不是只有"多扣了库存要加回来"（退款场景），还有"少扣了库存要补扣"——比如用户取消订单后库存要回补，但此时 Redis 里可能已经没有了（因为 Redis 过期），这时只依赖数据库精确库存 + 对账任务恢复到 Redis。提到"秒杀活动结束后的库存回收"——活动结束后 Redis 里的库存 key 要清理掉，但在此之前必须确认所有 MQ 消息都已被消费（通过检查 MQ 的消费位点 lag 是否为 0）。

## Q21：如何避免用户重复下单？

### 考察点
考察幂等性设计的实际落地能力，能否在分布式环境下做到端到端的防重。

### 解答思路
1. 按防重发生的层级分别设计：前端、网关、业务
2. 重点讲分布式环境下的幂等键设计
3. 给出数据库 + Redis 双重保障方案

### 参考答案

**先说结论：防重没有银弹，必须多层防御，每层解决不同粒度的问题。**

**第 1 层：前端防重（用户体验层，不可信赖）**

```
- 点击"提交订单"后按钮立即置灰 + 显示 loading
- 使用 CSS pointer-events: none 禁用点击
- 30 秒内不允许重复点击
```

这一层只能防普通用户的误操作，防不了脚本攻击和网络重试。**很多面试者只回答这一层，直接被淘汰。**

**第 2 层：接口幂等（业务逻辑层，核心防线）**

通过"幂等键"来实现一次业务操作和多次请求的结果一致。核心流程：

```
1. 前端进入下单页面时，后端生成一个全局唯一的 token（幂等键）
   token = 时间戳 + 用户ID + 随机数 的 MD5 或直接用雪花算法生成的 ID

2. 前端提交订单时携带这个 token

3. 后端处理逻辑：
   -- Lua 脚本：先判断 token 是否已处理过
   local exists = redis.call('EXISTS', KEYS[1])
   if exists == 1 then
       return redis.call('GET', KEYS[1])  -- 返回上次处理结果
   end
   -- 设置 token，初始状态为"处理中"
   redis.call('SET', KEYS[1], 'PROCESSING', 'EX', 3600)
   return 'NEW'

4. 如果返回 'NEW'，执行业务逻辑（下单），完成后更新 token 状态为 'SUCCESS'
5. 如果返回上次结果（SUCCESS/FAIL），直接返回，不再执行业务
```

**幂等键的生成策略和存储：**

- **谁生成：** 后端在下单页面初始化时生成（不要用前端生成的，不可信）
- **存储在哪：** Redis（高并发场景，设置过期时间），数据库（持久化，用于对账）
- **过期时间：** 设置为业务超时时间的 2 倍（如 30 分钟未支付取消，token 保留 60 分钟）
- **撞库风险：** 如果用 UUID 或雪花算法，碰撞概率极低（2^-128），生产环境足够

**第 3 层：数据库唯一约束（最后防线）**

```sql
-- 核心防重索引
ALTER TABLE t_order ADD UNIQUE INDEX uk_user_sku_token (user_id, sku_id, idempotent_token);

-- 插入订单时依赖唯一索引保证不重复
INSERT INTO t_order (...) VALUES (...);
-- 如果捕获到 DuplicateKeyException，返回"订单已存在"或上次结果
```

**三层防重的总结：**

```
层次          核心手段                  防护对象
前端层        按钮置灰                  普通用户误操作
接口层        Redis SETNX + token      网络重试、中间人重放、脚本攻击
数据库层      UNIQUE 约束              一切漏网之鱼（终极兜底）
```

**注意：** 数据库层不能作为唯一保护——如果你只依赖数据库唯一索引，每个重复请求都会穿透 Redis 打到数据库，数据库报 DuplicateKeyException，虽然数据不会重复，但数据库的 QPS 会被无效请求占满。

**加分项：** 提到"重复请求返回上一次结果"而不是返回"请勿重复下单"——前者对用户透明更友好（网络抖动导致的重复提交，用户无感知），后者用户可能会困惑。提到"token 的主动失效机制"——如果用户离开下单页面（beforeunload 事件）或页面 5 分钟无操作，主动调用接口将 token 标记为失效，释放资源。提到"幂等键在微服务链路中的传递"——如果下单链路涉及多个微服务（订单服务 → 库存服务 → 支付服务），每个服务都要用同一个幂等键，通过 HTTP Header 或 RPC Context 透明传递。

## Q22：30分钟未支付自动取消，用户在29分59秒付钱，30分钟超时自动取消也触发——代码怎么写？百万级订单超时自动取消系统如何设计？

### 考察点
考察分布式延迟任务的设计能力，特别是并发竞争条件（Race Condition）的处理方案。

### 解答思路
1. 先解决"29分59秒"的并发竞争问题
2. 再展开百万级订单的延迟任务系统架构
3. 对比 RocketMQ 延迟消息和 Redis ZSet 两种方案

### 参考答案

**一、29分59秒的并发竞争问题**

这是个经典的"取消和支付的竞态条件"。核心思路：**无论取消还是支付，都要检查订单的最新状态，两者只允许一个成功。**

```java
// 取消订单的代码（定时任务触发）
@Transactional
public void cancelOrder(Long orderId) {
    // 关键：用 SELECT FOR UPDATE 加行锁，保证和支付操作互斥
    Order order = orderMapper.selectForUpdate(orderId);
    if (order == null) {
        return;
    }
    // 状态判断：只有待支付状态才能取消
    if (order.getStatus() != OrderStatus.PENDING_PAYMENT) {
        return; // 已经支付或已取消，直接返回
    }
    // 二次确认：再查一次支付中心，防止有支付回调还没同步过来
    PaymentStatus payStatus = paymentService.queryPaymentStatus(order.getOrderNo());
    if (payStatus == PaymentStatus.SUCCESS) {
        // 支付已成功，把订单状态修正为已支付（补偿）
        order.setStatus(OrderStatus.PAID);
        orderMapper.updateById(order);
        return;
    }
    // 执行取消：改状态 + 释放库存
    order.setStatus(OrderStatus.CANCELLED);
    order.setCancelTime(new Date());
    orderMapper.updateById(order);
    // 异步释放库存
    mqProducer.send(new ReleaseStockMsg(order.getSkuId(), order.getQuantity()));
}

// 支付回调的代码（支付中心异步通知）
@Transactional
public void handlePaymentCallback(String orderNo, String transactionId) {
    Order order = orderMapper.selectForUpdateByOrderNo(orderNo); // 同样加行锁
    if (order == null) {
        return;
    }
    // 如果订单已经被取消，执行退款而不是更新状态
    if (order.getStatus() == OrderStatus.CANCELLED) {
        // 钱已经扣了但订单已取消 → 自动发起退款
        refundService.refund(transactionId, order.getPayAmount(), "订单已超时取消");
        return;
    }
    if (order.getStatus() != OrderStatus.PENDING_PAYMENT) {
        return; // 重复回调，幂等处理
    }
    // 正常更新为已支付
    order.setStatus(OrderStatus.PAID);
    order.setPayTime(new Date());
    order.setTransactionId(transactionId);
    orderMapper.updateById(order);
}
```

**关键点：**

1. **SELECT FOR UPDATE 行锁是核心保障**——取消和支付回调同时到达时，数据库行锁保证只有一个操作能拿到数据并修改，另一个被阻塞等待。
2. **取消操作中要二次确认支付状态**——因为有可能支付中心的回调先到达（订单已变 PAID），取消逻辑需要先查支付中心，确认没支付再取消。
3. **支付回调中要处理"已取消"的情况**——用户确实在最后一秒付了钱，订单被另一个线程取消了（因为钱到账有延迟），此时必须自动退款。
4. **退款不能同步做，要发 MQ 异步处理**——防止退款接口超时导致整个事务回滚，影响订单状态更新。

**二、百万级订单超时取消系统设计**

百万级订单的取消不是"每分钟扫一次数据库"能解决的。核心方案有三种：

**方案对比：**

| 方案 | 原理 | 延迟精度 | 百万级可行性 | 复杂度 |
|------|------|---------|------------|--------|
| 数据库定时扫表 | SELECT WHERE status=PENDING AND create_time < now()-30min | 分钟级 | 不可行（慢 SQL） | 低 |
| Redis ZSet | ZADD order:timeout score=取消时间戳 value=订单号 | 秒级 | 可行 | 中 |
| RocketMQ 延迟消息 | 下单后发 18 级延迟消息（1s~2h） | 秒级 | 可行但有限制 | 低 |
| 时间轮（Netty HashedWheelTimer） | 内存中维护时间轮的槽位 | 毫秒级 | 单机可行，分布式需改造 | 高 |

**生产级方案：RocketMQ 延迟消息 + Redis ZSet 兜底**

```
下单成功后：
Step 1: 发送 RocketMQ 延迟消息（delayLevel = 30 分钟级别）
       消息体：{orderId, orderNo, expireTime}

Step 2: 同时写入 Redis ZSet 作为兜底
       ZADD order:cancel:zset {expireTimestamp} {orderNo}

正常路径（MQ 延迟消息触发）：
- 延迟消息在 30 分钟后被消费
- 消费者执行 cancelOrder(orderId)
- 取消成功后，ZREM order:cancel:zset {orderNo} 清理 Redis

兜底路径（定时任务扫描 Redis ZSet）：
- 每分钟执行一次定时任务
- ZRANGEBYSCORE order:cancel:zset 0 {nowTimestamp} 获取所有到期的订单
- 批量执行取消操作（线程池并发，控制并发度）
- 取消成功后 ZREM 清理
```

**为什么需要 Redis ZSet 兜底？**

RocketMQ 延迟消息有限制：开源版只支持 18 个延迟级别，商业版支持任意时间。如果你的"30 分钟"精确匹配了某一个 delayLevel，那没问题。但如果产品要求改成"45 分钟未支付取消"而开源 RocketMQ 的 delayLevel 不支持 45 分钟，就不能只依赖 RocketMQ。Redis ZSet 的 score 可以精确到毫秒级别的时间戳，灵活性远高于 RocketMQ。

**定时任务扫描 Redis ZSet 的生产优化：**

```java
// 每分钟执行一次
@Scheduled(cron = "0 * * * * ?")
public void scanExpiredOrders() {
    long now = System.currentTimeMillis();
    // 每次扫描最多取 1000 个，分页处理避免 OOM
    Set<String> expiredOrderNos = redisTemplate.opsForZSet()
        .rangeByScore("order:cancel:zset", 0, now, 0, 1000);
    
    if (CollectionUtils.isEmpty(expiredOrderNos)) {
        return;
    }
    
    // 并发处理，控制并发度（避免打爆数据库）
    ExecutorService executor = new ThreadPoolExecutor(
        10, 10, 60, TimeUnit.SECONDS, new LinkedBlockingQueue<>(1000)
    );
    
    for (String orderNo : expiredOrderNos) {
        executor.submit(() -> {
            try {
                cancelOrderByOrderNo(orderNo);
                // 取消成功后删除 ZSet 中的记录
                redisTemplate.opsForZSet().remove("order:cancel:zset", orderNo);
            } catch (Exception e) {
                log.error("取消订单失败: {}", orderNo, e);
                // 失败不删除，下次继续尝试（需要设置重试上限）
            }
        });
    }
}
```

**加分项：** 提到"延迟消息的幂等性"——RocketMQ 的延迟消息被消费后最终会提交 offset，但如果消费者在处理中宕机，消息会重新投递。所以取消操作的 `cancelOrder` 方法必须是幂等的（通过订单状态判断，已取消的直接返回成功）。提到"时间轮的分布式方案"——如果要做到秒级到毫秒级的延迟，可以基于 Redis ZSet + 时间轮做两层：Redis ZSet 做持久化存储和故障恢复，内存时间轮做实时触发。服务重启时从 Redis ZSet 重新加载最近 1 小时的待取消订单到时间轮。提到"取消操作的可观测性"——关键指标：每分钟取消订单数、取消成功率、平均取消延迟（预约取消时间 vs 实际取消时间的差值）。这些指标要接入 Prometheus + Grafana 监控面板。

## Q23：请设计一个SSO系统，支持10个微服务，日活100万

### 考察点

### 参考答案

**SSO 系统的三个核心问题：**

1. **一处登录，处处可信：** 用户在 A 系统登录后，访问 B 系统不需要重新登录
2. **一处登出，处处失效：** 用户在 A 系统登出后，所有系统的登录态全部失效
3. **统一鉴权：** 所有微服务的权限校验走同一套认证中心，不各自维护一套

**架构设计总览：**

```
                        └───────────┘         └───────────┘
```

**登录流程（JWT + Redis 双写方案）：**

```
1. 用户访问微服务 A（未登录）
2. 网关拦截请求 → 302 重定向到 SSO 登录页 → URL 带上回调地址
   redirect_uri = https://sso.example.com/login?redirect_uri=https://order.example.com

3. 用户输入账号密码 → SSO 认证中心校验
   - 密码校验通过
   - 生成双 Token：
     Access Token（JWT，有效期 30 分钟，存前端内存/Cookie）
     Refresh Token（随机字符串，有效期 7 天，httpOnly Secure Cookie）

4. SSO 认证中心生成 Session：
   - Redis 记录：SESSION:{sessionId} → {userId, loginTime, refreshToken, ...}
   - 设置过期时间 = Refresh Token 有效期（7 天）

5. 302 重定向回微服务 A，URL 带 Authorization Code

6. 微服务 A 后端拿 Authorization Code 去 SSO 换取 Access Token + Refresh Token

7. 微服务 A 把 Access Token 返回给前端，前端后续请求带在 Header 里
```

**Token 的设计决策：**

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 纯 JWT（无状态） | 认证中心零压力 | 无法主动失效，JWT 泄漏后只能等过期 | 内部微服务间调用 |
| 纯 Session（Redis） | 可控性强，随时失效 | 认证中心有状态，每次鉴权要查 Redis | 传统 Web 应用 |
| JWT + Redis 双写（推荐） | 高性能 + 可控 | 实现稍复杂 | SSO 认证系统 |

**为什么用 JWT + Redis 双写？**

- Access Token 用 JWT，网关验签即可，不需要每次请求都调 SSO，性能高
- Redis 存储 Session 和 Refresh Token，需要踢人下线时直接删除 Redis 记录，Access Token 虽然还有效但无法刷新，30 分钟内自然过期
- 两者配合实现了"高性能鉴权 + 主动失效"的最佳平衡

**网关层的统一鉴权逻辑（关键代码思路）：**

```java
// API 网关的全局过滤器
public class AuthFilter implements GlobalFilter {
    
    // 需要放行的路径（登录、注册、健康检查）
    private static final List<String> WHITE_LIST = List.of(
        "/sso/login", "/sso/register", "/actuator/health"
    );
    
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();
        
        // 白名单放行
        if (WHITE_LIST.stream().anyMatch(path::startsWith)) {
            return chain.filter(exchange);
        }
        
        // 从 Header 获取 Access Token
        String token = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (token == null || !token.startsWith("Bearer ")) {
            return unauthorized(exchange, "未登录");
        }
        token = token.substring(7);
        
        // JWT 验签（不调 SSO，网关本地验签）
        try {
            Claims claims = JwtUtil.parseToken(token);
            // 将用户信息写入请求头，透传给下游微服务
            exchange.getRequest().mutate()
                .header("X-User-Id", claims.get("userId").toString())
                .header("X-User-Name", claims.get("username").toString())
                .header("X-User-Roles", claims.get("roles").toString());
            return chain.filter(exchange);
        } catch (ExpiredJwtException e) {
            // Access Token 过期 → 引导前端用 Refresh Token 刷新
            return unauthorized(exchange, "Access Token 过期，请刷新");
        } catch (JwtException e) {
            return unauthorized(exchange, "非法 Token");
        }
    }
}
```

**100 万日活的容量规划：**

```
日活 100 万，假设：

- 每人平均访问 20 个页面 → 鉴权 QPS 约 230（峰值 ×3 ≈ 700）

```

**跨子域 Cookie 方案：**

如果微服务在不同子域名（order.company.com, user.company.com），Cookie 的 Domain 要设为 `.company.com`，这样所有子域名共享登录 Cookie。如果是完全不同域名，则需要用 SSO 的统一登录页跳转方案（CAS 模式）。

**加分项：** 提到"OAuth2.0 + OIDC"标准化——自己设计的 SSO 协议很难和第三方系统集成，更好的方案是直接兼容 OAuth2.0 授权码模式 + OIDC（OpenID Connect）身份认证。这样未来接入第三方应用（如企业微信、飞书）时不需要重新对接。提到"安全增强措施"——暴力破解防护（同一 IP 连续 5 次登录失败锁定 30 分钟）、异地登录检测（通过 IP 变化和设备指纹触发二次认证）、JWT 的 jti（JWT ID）防重放机制。提到"服务间鉴权"——微服务之间调用（如订单服务调用户服务）也需要鉴权，方案是用 Service Account + 短期 JWT，网关只拦截外部请求，内部 RPC 调用由服务自身按需校验。

```sql
    UNIQUE KEY uk_role_perm (role_id, permission_id),
    INDEX idx_perm_id (permission_id)
) COMMENT '角色-权限关联表';
```

**五张核心表的 ER 关系：**

```
sys_user ──(N:M)── sys_user_role ──(N:M)── sys_role ──(N:M)── sys_role_permission ──(N:M)── sys_permission
```

**权限校验的完整链路（一个请求的鉴权过程）：**

```
1. 网关层：JWT 验签 → 提取 userId + roles → 写入 Header
2. 微服务层：Spring Security Filter 拦截
   - 从 SecurityContextHolder 获取当前用户的角色列表
   - 根据请求的 URL + HTTP Method，匹配 sys_permission 表中的 perm_code
   - 检查用户拥有的 role 是否关联了该 permission
   - @PreAuthorize("hasAuthority('order:create')")
3. 数据权限层（业务鉴权）：
   - 普通用户只能看到自己创建的订单
   - 部门经理看到本部门所有订单
   - 在 SQL 层面通过 MyBatis 拦截器自动拼接 WHERE 条件
```

**数据权限的实现（行级控制）：**

数据权限不属于 RBAC 标准模型的范畴，但实际项目中必须要实现。方案是额外维护一张"数据权限规则"表：

```sql
CREATE TABLE sys_data_permission_rule (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    role_id       BIGINT NOT NULL COMMENT '角色ID',
    table_name    VARCHAR(64) NOT NULL COMMENT '目标表名',
    scope_type    TINYINT NOT NULL COMMENT '1:全部 2:本部门 3:本部门及子部门 4:仅本人',
    scope_column  VARCHAR(64) COMMENT '过滤字段名（如 create_by, dept_id）',
    INDEX idx_role_table (role_id, table_name)
) COMMENT '数据权限规则表';
```

当用户执行 `SELECT * FROM t_order` 时，MyBatis 拦截器根据用户的 role 查询数据权限规则，自动改写 SQL 为：
```sql
-- 仅本人权限
SELECT * FROM t_order WHERE create_by = #{currentUserId}

-- 本部门权限
SELECT * FROM t_order WHERE dept_id = #{currentUserDeptId}
```

**加分项：** 提到"权限缓存设计"——用户的角色和权限列表在登录后缓存到 Redis，每次鉴权从 Redis 读取而非每次查 MySQL（100 万日活下，权限查询要扛住 QPS 700+）。角色变更时主动清除所有在线的该角色用户的权限缓存。提到"超级管理员的特权设计"——不查 RBAC 表，代码里硬编码判断 `if (roles.contains("ROLE_SUPER_ADMIN")) return true;`，避免超级管理员权限被人误删导致无法操作。提到"权限的审计日志"——谁在什么时间改了谁的权限、权限变更前后的值，全部记录到审计日志表，保留 90 天，满足等保和安全审计要求。提到"前端按钮级别的权限控制"——Vue/React 项目中通过自定义指令（`v-permission="'order:delete'"`）或高阶组件按权限渲染按钮，不在前端暴露用户无权操作的功能入口，减少误操作。

## Q25：鉴权如何实现？

### 考察点
候选人能否区分认证（Authentication）和授权（Authorization），并给出从网关到微服务再到数据层的完整鉴权链路设计。

### 解答思路
1. 先明确"鉴权"包含了认证和授权两个独立步骤，很多人面试时混为一谈。
2. 以一次完整请求为主线，拆解网关层 JWT 验签、微服务层 RBAC 权限校验、数据层行级权限的完整链路。
3. 讨论 JWT 无状态方案 vs OAuth2.0 授权码模式 vs Session 有状态方案的选择依据。

### 参考答案

**第一层：认证（Authentication）——"你是谁"**

生产中最主流的方案是 JWT（JSON Web Token）无状态认证，替代传统的 Session 方案。完整流程：

```
用户登录 → 提交用户名+密码 → 后端验证（BCrypt 比对密码哈希）
  → 生成 Access Token（JWT，有效期15分钟）+ Refresh Token（UUID，有效期7天，存 Redis）
  → 前端存储 Access Token 在内存，Refresh Token 在 httpOnly Cookie
```

JWT 的 Payload 中携带 `userId`、`roles`、`permissions` 等基本信息，避免每次鉴权都查数据库。验签用 RSA256 非对称加密——网关持有公钥即可验签，签发服务持有私钥，各微服务无需持有私钥。

**Refresh Token 的双令牌机制是关键设计：**
- Access Token 短有效期（15分钟）：即使泄露，窗口期很短
- Refresh Token 长有效期（7天）+ Redis 存储：可主动撤销（修改密码/封号时直接删 Key）
- 前端拦截器：401 时自动用 Refresh Token 换新 Access Token，用户无感知
- 刷新时做"轮换"（Rotation）：旧 Refresh Token 立即失效，发一个新的 Refresh Token。如果旧 Token 被重复使用就判定为盗用，强制所有设备下线

**第二层：授权（Authorization）——"你能干什么"**

核心模型是 RBAC（Role-Based Access Control），五张表：`sys_user`、`sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission`。

权限校验链路：
1. 网关从 JWT 中提取 userId/roles，写入请求 Header（`X-User-Id`、`X-User-Roles`）
2. Spring Security Filter 拦截请求，从 SecurityContextHolder 获取当前用户信息
3. 根据 URL + HTTP Method 匹配权限表，判断用户拥有的角色是否关联了该权限
4. 通过 `@PreAuthorize("hasAuthority('order:delete')")` 注解声明接口所需权限

**第三层：数据权限（行级控制）**

RBAC 控制的是"能不能访问这个接口"，但控制不了"能看哪些数据"。数据权限通过 MyBatis 拦截器实现——根据用户的角色和部门，自动在 SQL 后拼接 `WHERE create_by = #{userId}` 或 `WHERE dept_id IN (...)`。

**认证方案选型对比：**

| 方案 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| JWT 无状态 | 微服务/分布式系统 | 不依赖中心存储，水平扩展友好 | Token 无法主动失效（需黑名单） |
| Session 有状态 | 单体应用/传统 MVC | 服务端可控，随时踢人 | 分布式需 Session 共享（Redis） |
| OAuth2.0 | 第三方登录/开放平台 | 标准化协议，支持多种授权模式 | 实现复杂，调试成本高 |

**加分项：** 提到"JWT 黑名单机制"——Redis 存储被撤销的 Token ID（jti），Key 为 `jwt:blacklist:{jti}`，TTL 为 Token 剩余有效期。网关验签后先查黑名单，命中则直接 401。这解决了"JWT 无法主动失效"的核心缺陷。提到"网关层统一鉴权"——所有微服务共享的鉴权逻辑（Token 验签、黑名单检查、基础角色校验）应该在 API Gateway（Kong/Spring Cloud Gateway）统一完成，微服务只关注业务相关的细粒度权限。避免每个微服务都写一套 JWT 验签代码。

## Q26：如何设计一个实时、可靠、可扩展的登录拉黑与强制下线系统？

### 考察点
候选人能否从"事件产生 → 事件分发 → 策略执行 → 状态持久化"的完整链路设计一个实时风控系统，重点考察 Redis Pub/Sub、WebSocket、多级缓存的综合运用。

### 解答思路
1. 先从"实时"切入——如何让黑名单在秒级内生效于所有网关实例。
2. 再从"可靠"展开——如何保证黑名单指令不丢失、不遗漏，即使目标用户不在线。
3. 最后从"可扩展"收束——百万级黑名单如何存储和快速匹配。

### 参考答案

**整体架构：**

```
管理员操作 → 风控后台 → 发布黑名单事件（Redis Pub/Sub）
    → 所有网关实例订阅并实时加载到本地缓存
    → 用户下次请求 → 网关检查本地黑名单 → 命中则 403 + 推送强制下线通知
```

**第一环：实时性——如何让黑名单秒级生效**

方案一（推荐）：Redis Pub/Sub + 本地缓存。

风控后台将拉黑指令发布到 Redis Channel `channel:user:blacklist`，所有网关实例作为 Subscriber 收到消息后立即更新本地 Caffeine Cache（Guava Cache 的继任者）。用户下次请求到达网关时，O(1) 时间即可判断是否在黑名单中。从操作到生效的延迟 = Pub/Sub 消息延迟（< 10ms）+ 用户请求间隔（用户不刷新页面就没请求）。

方案二（补充）：WebSocket 主动推送强制下线。如果用户当前在线（持有 WebSocket 连接），服务端收到黑名单事件后，通过 WebSocket 推送 `{"type": "force_logout", "reason": "account_banned"}` 指令，前端收到后立即清除 Token 并跳转到登录页，不需要等用户下次请求。这是从"被动拦截"到"主动踢出"的关键。

**第二环：可靠性——如何保证指令不丢失**

Pub/Sub 是"即发即忘"模式，订阅者不在线时消息直接丢失。需要三层兜底：

1. **数据库持久化**：拉黑操作先写入 MySQL `user_blacklist` 表（`user_id, reason, operator, expire_time, created_at`），保证指令不丢失。
2. **定时全量同步**：每个网关实例每 5 分钟从 MySQL 全量拉取黑名单列表（`WHERE status=1 AND expire_time > NOW()`），覆盖 Pub/Sub 丢失的消息。
3. **Redis Set 兜底**：除了 Pub/Sub，风控后台同时将黑名单 userId 写入 Redis Set（`SADD blacklist:active 12345`）。网关每次鉴权时，如果本地缓存未命中，回源查 Redis Set。

**第三环：可扩展——百万级黑名单的高效匹配**

- **分级存储**：活跃黑名单（近期被封的活跃用户，通常 < 1万）存在 Caffeine Cache + Redis Set 中，O(1) 查找。历史黑名单（已过期/已解封）只存 MySQL，低频查询走数据库。
- **布隆过滤器粗筛**：在 Caffeine Cache 前面加一层布隆过滤器，99% 的正常用户请求一次布隆过滤器判断即可放行，大幅减少缓存穿透。
- **分片网关**：网关水平扩展时，每个网关实例维护自己的本地缓存，Redis Pub/Sub 保证所有实例的缓存最终一致。

**完整流程（一个用户被封禁到被强制下线的全链路）：**

```
1. 管理员在风控后台点击"封禁用户 A"
2. 后端执行：
   a. INSERT INTO user_blacklist (user_id=10001, status=1, expire_time=now()+7d)
   b. SET blacklist:token:10001 "banned:fraud" EX 604800  (Redis，Token黑名单)
   c. PUBLISH channel:user:blacklist {"userId":10001,"action":"ban","reason":"fraud"}
   d. 如果用户在线，通过 WebSocket 推送 {"type":"force_logout"}
3. 所有网关实例收到 Pub/Sub 消息 → 更新本地缓存
4. 用户 A 的下次请求 → 网关拦截 → 403 "您的账号已被封禁，原因：fraud"
5. 用户 A 尝试用 Refresh Token 刷新 → Redis 黑名单命中 → 401
6. 前端 WebSocket 收到 force_logout → 清除 Token → 跳转登录页提示封禁信息
```

**加分项：** 提到"灰度拉黑"——不直接封禁，而是在封禁前先降低用户权限（如禁止发帖、禁止支付），观察用户行为后再决定是否永久封禁。技术上通过 RBAC 动态添加"受限角色"实现。提到"解封的回滚机制"——解封时不仅要删除黑名单记录，还要检查用户是否有其他未过期的封禁记录，避免 A 管理员封了 7 天、B 管理员 3 天后提前解封，结果原来的 7 天变成了 3 天（这需要保留封禁历史明细表）。提到"高并发下的缓存击穿保护"——封禁一个 KOL 可能导致大量用户同时查询该用户状态，Caffeine Cache 的 `refreshAfterWrite` 配合单机锁可避免缓存击穿。

## Q27：黑名单网址过滤系统如何设计？

### 考察点
候选人是否理解大规模 URL 过滤的核心挑战——海量黑名单（千万级甚至亿级）下的快速匹配，以及如何平衡误判率、内存占用、更新延迟。

### 解答思路
1. 先定义核心指标——QPS、黑名单规模、允许误判率、更新延迟，这些决定技术选型。
2. 从粗筛到精筛设计三层漏斗：布隆过滤器 → 哈希表精确匹配 → DFA/AC 自动机模式匹配。
3. 讨论增量更新、灰度发布、监控告警等运营层面的设计。

### 参考答案

**核心设计目标：**
- 黑名单规模：千万级 URL（含域名级和路径级）
- QPS：10 万+（网关层每请求必查）
- 延迟：P99 < 1ms（不能成为瓶颈）
- 更新延迟：分钟级（新增黑名单尽快生效）
- 误判率：零误判（正常网站不能被误封）

**三层漏斗架构：**

```
用户请求 URL → [第一层] 布隆过滤器（域名级粗筛）
    → 命中 → [第二层] 哈希表精确匹配（完整 URL/digest）
        → 命中 → [第三层] DFA/AC 自动机（正则/通配符模式匹配）
            → 命中 → 拦截，否则放行
    → 未命中 → 直接放行（99%+ 的请求在此层结束）
```

**第一层：布隆过滤器（域名级粗筛）**

布隆过滤器是这道题的核心。原理：用 K 个哈希函数将每个域名映射到 M 位的位数组中。查询时，如果 K 个位置全是 1，则"可能存在"；任一位置为 0，则"一定不存在"。

- 千万级黑名单域名，布隆过滤器只需约 120MB 内存（误判率 0.01%）
- 查询复杂度 O(K)，K 通常取 5-10，远小于哈希表查询
- 布隆过滤器的误判（false positive）由第二层哈希表兜底纠正

公式：给定 n 个元素和期望误判率 p，位数组大小 m = -n * ln(p) / (ln2)^2，哈希函数个数 k = (m/n) * ln2。

示例：n = 10,000,000，p = 0.0001 → m ≈ 191MB，k ≈ 13。生产环境可通过 Redis Bloom Filter 模块或 Guava BloomFilter 实现。

**第二层：哈希表精确匹配**

当布隆过滤器命中时，进入精确匹配。存储结构：`Map<String, BlockRule>`，Key 可以是完整 URL 或 URL 的 MD5/SHA256 摘要。

- 千万级 URL → 约 500MB-1GB 内存（含对象开销），需要分片存储
- 优化：按域名前缀分片（一致性哈希），每个分片独立部署，减少单节点内存压力
- 使用 Caffeine Cache + Redis 二级缓存：热点 URL 规则缓存在本地（Caffeine），冷数据在 Redis

**第三层：DFA/AC 自动机（模式匹配）**

不是所有黑名单都是精确 URL——很多规则是通配符或正则，如 `*://*.example.com/path/*`。这时用 AC 自动机（Aho-Corasick）做多模式串匹配。

- 将通配符规则编译为 AC 自动机的状态转移图
- 查询时，输入域名/URL 在状态机上跑一遍，O(n) 时间内检查是否命中任意模式
- AC 自动机天然支持增量添加规则（动态构建失效链接）

**增量更新机制：**

- 运营人员提交黑名单 → 审核 → 写入 MySQL → Canal 监听 binlog → 推送增量变更
- 每个过滤节点订阅 Canal 消息 → 更新本地布隆过滤器 + 哈希表 + AC 自动机
- 每 10 分钟做一次全量对账（从 MySQL 重新构建布隆过滤器），覆盖增量丢失的情况

**加分项：** 提到"灰度放量"——新的黑名单规则先在小流量（1%）上生效，观察误判率无异常后再全量放开。这要求过滤系统支持按规则级别的灰度开关。提到"白名单优先"——白名单域名（如政府网站、支付平台）在所有黑名单检查之前优先判断，命中白名单直接放行，避免被错误添加的黑名单误伤。提到"布隆过滤器不可删除"的缺陷——标准布隆过滤器不支持删除元素（因为多个元素可能共享同一个比特位），如果黑名单需要频繁增删，改用 Counting Bloom Filter（每个比特位升级为计数器）或 Cuckoo Filter（支持删除且空间效率更高）。提到"URL 规范化预处理"——在进入匹配引擎前，URL 需要去参数字、URL Decode、统一小写、路径标准化（`/a/./b/../c` → `/a/c`），否则绕过方式太多。

## Q28：从零设计分布式链路跟踪系统

### 考察点
候选人是否理解链路跟踪的本质——从协议层（Trace/Span 模型）到传输层（采样/上报）再到存储层（索引/检索），考察的是"能否在需要时从零自研"的能力而不仅仅是用 Jaeger。

### 解答思路
1. 先定义核心数据模型——Trace、Span、SpanContext，这是链路跟踪的基石。
2. 设计采样策略——头部采样、尾部采样、自适应采样，这是生产级链路跟踪的核心难点。
3. 设计存储与查询——海量 Span 的写入、存储、检索方案。

### 参考答案

**第一步：核心数据模型——Trace/Span/SpanContext**

一切链路跟踪系统都基于 Google Dapper 论文（2010）的模型：

- **Trace**：一次完整的分布式调用链，由全局唯一的 TraceId 标识
- **Span**：Trace 中的一个基本工作单元（如一次 RPC 调用、一次 DB 查询），由 SpanId 标识
- **SpanContext**：跨进程传递的上下文，包含 TraceId + SpanId + ParentSpanId + Baggage（透传的 KV 数据）

关键设计决策：**SpanId 的生成方式**

不要用数据库自增或 UUID——需要用"全局唯一 + 趋势递增 + 高性能"的 ID 生成算法。推荐方案：
- 雪花算法（Snowflake）：64 位，41 位时间戳 + 10 位机器 ID + 12 位序列号。优点是趋势递增，便于存储引擎（Elasticsearch）按时间范围高效查询。
- 或直接用 `traceId = `${timestamp}-${ip}-${random}` 的简单拼接方案，更容易调试（一眼能看出时间和来源机器）。

**TraceId 在跨服务间的传递：**

```
服务 A → [Header: X-Trace-Id, X-Span-Id, X-Parent-Span-Id] → 服务 B
    → 服务 B 创建新 Span，ParentSpanId = A 的 SpanId
    → 服务 B 调用服务 C，B 的 SpanId 成为 C 的 ParentSpanId
```

在框架层面，通过拦截器/过滤器自动注入和提取（如 Dubbo Filter、Spring Cloud Gateway Filter、gRPC Interceptor），业务代码零侵入。

**第二步：采样策略——链路跟踪最核心的工程难题**

全量采样（100%）在生产上几乎不可能——头部互联网公司每天的 Span 量级在千亿甚至万亿级别，全量存储成本不可接受。所以采样策略决定了"哪些数据被保留"：

| 采样策略 | 描述 | 适用场景 |
|----------|------|----------|
| 恒定采样 | 固定比例（如 1%），随机抽取 | 稳定流量，用户行为均匀分布 |
| 头部采样（Head-based） | 在 Trace 入口处决定是否采样 | 实现简单，但可能漏掉长尾错误 |
| 尾部采样（Tail-based） | 等 Trace 结束后再根据结果决定 | 能保证所有错误/慢请求都被追踪 |
| 自适应采样 | 根据 QPS 动态调整采样率 | 大流量时降低采样率，低流量时提高 |

生产级推荐：**头部采样 + 尾部采样的混合方案。** 头部用 1% 的恒定采样覆盖正常流量，尾部对所有包含 ERROR 标记或耗时 > P99 阈值的 Trace 强制保留。存储侧给异常 Trace 更高优先级，正常 Trace 可配置更短的 TTL。

**第三步：数据上报——尽量降低对业务的影响**

- 本地异步缓冲：每个服务实例维护一个内存队列（如 Disruptor RingBuffer），Span 完成后先入队，异步批量上报。队列满时直接丢弃（不阻塞业务线程）。
- 上报协议：gRPC 流式上报（比 HTTP 批量上报效率高），序列化用 Protobuf（比 JSON 体积小 60-80%）。
- 背压处理：Collector 过载时返回 429，Agent 指数退避重试（最大 5s 间隔）。

**第四步：存储与查询**

- 存储引擎选择：ElasticSearch 是最主流选择（时序数据 + 全文检索），列式存储（ClickHouse）适合聚合分析场景，Cassandra 适合极高写入吞吐。
- 索引设计：按 `traceId` 做哈希分片 + 按 `startTime` 做时间范围分片（ES Rollover Index，按天/小时切分索引）。
- 冷热分离：近 3 天数据存在 SSD 集群（热），3-30 天数据迁移到 HDD 集群（温），30 天后归档到 S3/OSS（冷），大幅降低存储成本。

**第五步：可视化——必须回答的三个问题**

1. 调用链拓扑图：展示一次 Trace 的完整服务调用层级和时间瀑布
2. 服务依赖图：基于 Span 间调用关系自动生成服务拓扑
3. 耗时分析：P50/P90/P99/P999 延迟、各 Span 耗时占比

**加分项：** 提到 OpenTelemetry——CNCF 孵化的可观测性标准，定义了统一的 API/SDK 和数据格式（OTLP 协议），目标是"一次埋点，到处上报"。与其绑定某个厂商（Jaeger/Zipkin/Datadog），不如用 OpenTelemetry 做数据采集层，后端可灵活切换存储。提到"Baggage 的正确使用"——Baggage 是 Trace 级别的透传参数，可以把 `userId`、`orderId`、`tenantId` 放进 Baggage 中，所有 Span 自动携带，这在排查"特定用户为什么慢"时极其有用。但 Baggage 会增大每次 RPC 的 Header 体积，只应放关键维度。提到"日志与 Trace 的关联"——在每个 Span 的日志中自动注入 TraceId/SpanId，这样在日志系统中可以根据 TraceId 搜索到该请求的所有日志。这是"可观测性三支柱"结合的最基础实践。

## Q29：链路追踪你怎么做？Jaeger/Zipkin/Micrometer/Prometheus各干什么？

### 考察点
候选人能否清晰区分 Metrics、Logging、Tracing 三大可观测性工具，理解每个工具在"观测栈"中的定位，而不是把 Jaeger 和 Prometheus 的功能搞混。

### 解答思路
1. 先画"可观测性三支柱"的框架图，把四个工具分别归类。
2. 逐个工具展开——核心理念、数据模型、典型使用场景。
3. 给出实际项目中的组合方案和完整的故障排查流程。

### 参考答案

**先建立宏观框架——可观测性三支柱的工具体系：**

| 支柱 | 核心问题 | 数据模型 | 工具 |
|------|----------|----------|------|
| Metrics（指标） | 系统出了什么问题？ | 时序数值（CPU%、QPS、P99延迟） | Micrometer + Prometheus + Grafana |
| Tracing（链路） | 哪个服务/方法出了问题？ | 带因果关系的 Span 树 | Jaeger / Zipkin |
| Logging（日志） | 问题出在哪一行代码？ | 非结构化/结构化文本 | ELK（Elasticsearch + Logstash + Kibana） |

这四个工具的定位不是"四选一"，而是**各司其职**：

**Micrometer（指标门面）：** Micrometer 不是监控系统，它是 Java 生态的指标采集门面（类比 SLF4J 之于日志）。它提供统一的 API（`meterRegistry.counter("http.requests").increment()`），屏蔽了 Prometheus、Datadog、InfluxDB 等不同后端差异。Spring Boot Actuator 默认集成了 Micrometer，开箱即用地暴露 JVM 指标（内存、GC、线程池）。

**Prometheus（指标存储与查询）：** Prometheus 是时序数据库，负责拉取（Pull 模式）各服务的 `/actuator/prometheus` 端点，存储指标数据，并提供 PromQL 查询语言。核心数据模型是"指标名 + 标签集 + 时间戳 + 值"，如 `http_server_requests_seconds_count{method="GET",status="200",uri="/api/order"} 15432 1684234567`。Prometheus 不做展示——展示交给 Grafana。

**Grafana（指标可视化与告警）：** Grafana 从 Prometheus（或其它数据源）读取数据，生成 Dashboard。它还能基于 PromQL 配置告警规则（如"P99 延迟 > 1s 持续 5 分钟"），通过钉钉/飞书/邮件/PagerDuty 发送告警。Grafana 的核心价值是让数据"可被看见"——运维团队不需要敲 PromQL，在 Dashboard 上就能一眼看到系统健康状态。

**Jaeger（链路跟踪——Uber 开源）：**
- 数据模型：基于 OpenTracing 标准（已合并进 OpenTelemetry），以 Trace → Span 树模型记录一次请求的全链路耗时
- 核心组件：Jaeger Agent（本地采集）、Jaeger Collector（汇聚）、Cassandra/ES（存储）、Jaeger UI（可视化）
- 特色：自适应的采样策略、服务依赖图自动生成

**Zipkin（链路跟踪——Twitter 开源）：**
- 比 Jaeger 更早的分布式链路跟踪系统，理念类似
- 核心组件：Reporter（埋点上报）、Collector（HTTP/Kafka 接收）、Storage（MySQL/ES/Cassandra）、UI
- Jaeger vs Zipkin 的核心差异：Jaeger 支持自适应采样和更丰富的数据模型，部署更重但功能更强；Zipkin 更轻量，部署简单但高级功能少

**Jaeger vs Zipkin 详细对比：**

| 对比维度 | Jaeger | Zipkin |
|----------|--------|--------|
| 来源 | Uber 开源 | Twitter 开源 |
| 部署复杂度 | 较重（5+ 组件） | 较轻（Java 单体即可） |
| 存储后端 | Cassandra、ES、Badger | MySQL、ES、Cassandra |
| 采样策略 | 自适应、速率限制、远程控制 | 仅恒定采样 |
| 数据模型 | 丰富（支持 log、tag、baggage） | 基础（annotations + tags） |
| 社区 | CNCF 毕业项目 | CNCF 归档（2023 年停止维护） |
| 推荐 | **新项目首选** | **历史项目存量** |

**完整的故障排查流程（三支柱协同）：**

```
1. Grafana Dashboard → 发现错误率飙升（Metrics）
2. Grafana → 点击错误率曲线 → 按 endpoint 下钻 → 定位到 /api/order/create 接口 P99 延迟 5s
3. Jaeger UI → search traces by endpoint="/api/order/create" AND duration>5s → 找到慢 Trace
4. Jaeger UI → 展开 Trace 时间瀑布 → 发现 OrderService → InventoryService 的 RPC 耗时 4.8s
5. Kibana → search log by TraceId=xxx AND service=inventory-service → 找到具体日志
6. 日志显示：Redis 连接池耗尽，等待连接超时
```

**加分项：** 提到 OpenTelemetry 的现状——它已合并 OpenTracing 和 OpenCensus，成为 CNCF 的"可观测性统一标准"。用 OpenTelemetry SDK 做埋点，后端可以同时输出到 Jaeger（Tracing）、Prometheus（Metrics）、ELK（Logging），避免为每个后端重复埋点。提到 Jaeger 的"自适应采样"原理——根据每秒 Span 数动态调整采样率，保证上报到 Collector 的 Span 量恒定，避免后端被打爆。做不好采样是生产中最常见的链路跟踪失败原因。

## Q30：如何用Micrometer+Prometheus+Grafana做监控？如何用Jaeger/Zipkin做分布式链路追踪？

### 考察点
候选人是否真正动手搭建过监控与链路追踪体系，而非仅仅了解概念。重点考察集成的具体步骤、PromQL 编写、Grafana Dashboard 配置、Jaeger 采样策略的实际经验。

### 解答思路
1. 前半部分：从 Micrometer 埋点 → Prometheus 采集 → Grafana 展示，讲一个完整的监控体系搭建过程。
2. 后半部分：从 Spring Boot 集成 Jaeger → 采样策略配置 → Dashboard 排查，讲完整的链路追踪落地。
3. 重点讲生产环境的关键配置（JVM 指标、自定义业务指标、告警规则），而不是简单引包。

### 参考答案

**第一部分：Micrometer + Prometheus + Grafana 监控体系**

**Step 1：引入依赖与基础配置**

```xml
<!-- Spring Boot Actuator 自带 Micrometer -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics
  metrics:
    export:
      prometheus:
        enabled: true
    tags:
      application: ${spring.application.name}  # 全局标签，区分服务
```

配置后访问 `/actuator/prometheus` 即可看到所有指标（JVM 内存、GC、线程、HTTP 请求等），Prometheus 定期拉取此端点。

**Step 2：自定义业务指标——这是核心价值**

开箱即用的 JVM 指标只能告诉你"系统没挂"，但"业务是否正常"需要自定义指标：

```java
// 1. 计数器——下单量
Counter orderCounter = Counter.builder("orders.created.total")
    .description("订单创建总数")
    .tag("channel", "app")  // 按渠道区分
    .register(meterRegistry);
orderCounter.increment();

// 2. 计时器——支付接口耗时分布
Timer.Sample sample = Timer.start(meterRegistry);
// ... 业务逻辑 ...
sample.stop(Timer.builder("payment.duration")
    .description("支付接口耗时")
    .publishPercentiles(0.5, 0.95, 0.99)  // P50/P95/P99
    .register(meterRegistry));

// 3. Gauge——线程池活跃线程数（实时快照）
Gauge.builder("threadpool.active.threads", threadPool, pool -> pool.getActiveCount())
    .register(meterRegistry);
```

**生产环境关键自定义指标总结：**

| 指标类型 | 示例 | 告警用途 |
|----------|------|----------|
| Counter | `orders.total`、`payments.failed` | 监控业务量级和失败率 |
| Timer | `api.latency`、`db.query.time` | 监控接口和数据库延迟 |
| Gauge | `connection.pool.size`、`queue.depth` | 监控资源饱和度 |
| DistributionSummary | `request.payload.size` | 监控请求体大小分布 |

**Step 3：Prometheus 配置拉取**

```yaml
# prometheus.yml
scrape_configs:
  - job_name: 'spring-boot'
    metrics_path: '/actuator/prometheus'
    scrape_interval: 15s  # 采集间隔
    static_configs:
      - targets: ['service-a:8080', 'service-b:8081']
        labels:
          env: 'production'
```

**Step 4：Grafana Dashboard 与告警**

- Dashboard：导入 Spring Boot 官方 Dashboard（ID: 12900），或自定义 Panel 展示 QPS、P99 延迟、错误率三大黄金信号
- 告警规则（PromQL）：
  ```

  rate(http_server_requests_seconds_count{status=~"5.."}[5m]) / rate(http_server_requests_seconds_count[5m]) > 0.05
  
  # P99 接口延迟 > 2s
  histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[5m])) > 2
  ```

**第二部分：Jaeger/Zipkin 分布式链路追踪**

**Jaeger 集成（推荐方案，OpenTelemetry + Jaeger）：**

```xml
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-spring-boot-starter</artifactId>
</dependency>
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-jaeger</artifactId>
</dependency>
```

```yaml
otel:
  traces:
    exporter: jaeger
    sampler:
      probability: 0.1  # 10% 采样率
  exporter:
    jaeger:
      endpoint: http://jaeger-collector:14250  # gRPC
  service:
    name: ${spring.application.name}
```

**生产级采样策略配置（关键！）：**

```yaml
# OpenTelemetry 采样器：父 Span 被采样则子 Span 强制采样 + 恒定 10%
otel:
  traces:
    sampler:
      parent-based: true          # 父子一致性
      probability: 0.1             # 新 Trace 的采样率
      # 进阶：通过 Jaeger Remote Sampler 动态调整
      # type: jaeger-remote
      # endpoint: http://jaeger-collector:5778/sampling
```

**自动埋点 vs 手动埋点：**

Spring Boot Starter 自动为 HTTP 请求、数据库查询、消息队列消费创建 Span（通过 Java Agent 字节码增强），覆盖了 90% 的场景。但关键业务节点需要手动埋点：

```java
@GetMapping("/order/create")
public Order createOrder(@RequestBody OrderReq req) {
    Span span = tracer.spanBuilder("order.create.business-logic").startSpan();
    try (Scope scope = span.makeCurrent()) {
        span.setAttribute("order.amount", req.getAmount());
        span.setAttribute("user.id", req.getUserId());
        // 业务逻辑...
        span.setStatus(StatusCode.OK);
    } catch (Exception e) {
        span.setStatus(StatusCode.ERROR, e.getMessage());
        span.recordException(e);
        throw e;
    } finally {
        span.end();
    }
}
```

**Jaeger 生产部署要点：**

- Jaeger Agent 作为 Sidecar 部署在每台宿主机，本地 UDP 接收 Span（零网络开销）
- Jaeger Collector 汇聚后批量写入 ElasticSearch（生产环境推荐，1 万 QPS 下 ES 比 Cassandra 查询体验更好）
- Jaeger Query 提供 UI 查询，Grafana 也可以接入 Jaeger 作为数据源（统一在 Grafana 看指标 + 链路）

**Zipkin 集成（轻量方案）：**

```yaml
spring:
  zipkin:
    base-url: http://zipkin:9411
    sender:
      type: web  # HTTP 上报，也可以用 Kafka/RabbitMQ
  sleuth:
    sampler:
      probability: 0.1
```

**Zipkin vs Jaeger 实际选型建议：**

| 维度 | Zipkin | Jaeger |
|------|--------|--------|
| 部署方式 | `java -jar zipkin.jar` 单体启动 | 5+ 组件，K8s Operator |
| 存储 | 支持 MySQL（小规模可零配置） | 推荐 ES/Cassandra |
| 生产门槛 | 低，适合团队 < 50 人 | 中高，适合团队 > 200 人 |
| 维护状态 | 2023 年已归档 | CNCF 活跃维护 |
| **2026 年推荐** | **不推荐新项目** | **首选** |

**加分项：** 提到"采样率不是越高越好"——10% 采样率对头部互联网公司意味着每天 100 亿个 Span，存储成本巨大。推荐的策略是"异常全采 + 正常按比例"，利用 Jaeger 的 Tail Sampling Processor 根据 Span 的 status 和耗时动态决定是否保留。提到"SLEUTH 已弃用"——Spring Cloud Sleuth 在 Spring Boot 3.x 中已被移除，官方推荐直接使用 Micrometer Tracing（底层基于 Brave/OpenTelemetry），迁移项目中需要注意。

## Q31：谈谈你对系统"可观测性"的理解。Metrics、Logging、Tracing三者关系是什么？

### 考察点
候选人是否真正理解"可观测性"的哲学含义和工程意义，而不是背诵三支柱定义。核心考察是有没有在生产环境中用三支柱联动排查过问题。

### 解答思路
1. 先谈"监控"和"可观测性"的本质区别——这是面试中最容易加分的地方。
2. 再展开三大支柱各自的数据模型和不可替代的价值。
3. 最后讲三者在实际问题排查中如何联动——用具体案例串联三者的关系。

### 参考答案

**第一部分：监控 vs 可观测性——不只是换了个时髦词汇**

这是我面试中最看重的一个区分：

**监控（Monitoring）** 是"我知道系统可能会出什么问题，所以我提前设好告警"。它基于已知的、预设的故障模式。比如"CPU 超过 80% 发告警"、"QPS 低于 1000 发告警"。监控告诉你系统"有没有问题"。

**可观测性（Observability）** 来自控制论——系统输出能被外部观察者推断内部状态的能力。在软件工程中，它的核心价值是：**当系统出现一个你从未预见过的新问题时，你能不修改代码、不重新部署，就通过已有的数据（Metrics + Logging + Traces）定位到根因。**

可观测性回答的是："我不知道系统会怎么坏，但当它坏的时候，我能在 5 分钟内定位到原因吗？"

**第二部分：Metrics、Logging、Tracing 各自不可替代的价值**

这三者在"维度"上有本质区别：

| 维度 | Metrics | Logging | Tracing |
|------|---------|---------|---------|
| 核心问题 | 系统出了什么问题？ | 问题出在哪一行代码？ | 是哪个服务/方法的问题？ |
| 数据模型 | 时序数值（点） | 离散事件（行） | 因果关系（树） |
| 聚合能力 | 极强（PromQL） | 弱（需结构化和索引） | 中（按 Trace/Span 聚合） |
| 存储成本 | 低（数值压缩率高） | 中-高（文本体积大） | 高（调用链结构 + 属性） |
| 典型工具 | Prometheus + Grafana | ELK / Loki | Jaeger / Zipkin |
| 基数 | 低（标签组合有限） | 中-高 | 极高（每个 TraceId 唯一） |
| 使用场景 | 趋势分析、告警、容量规划 | 排查具体问题、审计 | 排查分布式调用延迟 |

**Metrics 的不可替代性：**
- 聚合查询能力是 Tracing 和 Logging 完全无法比拟的。你能用一行 PromQL 算出"过去 5 分钟内，每个接口的 P99 延迟在所有 Pod 上的分布"——用日志或链路追踪做同样的事需要扫描海量原始数据
- 适合长期趋势分析、容量规划、SLO 监控

**Logging 的不可替代性：**
- 唯一能告诉你"某一行代码做了什么"的手段。Trace 可以告诉你"调用 InventoryService 花了 5s"，但无法告诉你"为什么花了 5s"——你得看那台服务器上的日志，可能是 Redis 连接池耗尽了
- 日志也是审计的基础，能记录"谁在什么时间做了什么操作"

**Tracing 的不可替代性：**
- 唯一能告诉你"请求 A 经过服务 X → 服务 Y → 服务 Z，在 Y 上花了 80% 时间"的手段。Metrics 只能告诉你每个服务独立的延迟，无法串联因果
- Tracing 是"导航"——它告诉你去哪里查日志

**第三部分：三支柱联动——生产故障排查的真实案例**

场景：用户反馈"下单按钮点击后要等 10 秒才弹出成功提示"。

```
1. 【Metrics 入口 — 发现问题层面】
   Grafana 打开订单服务的 Dashboard
   → QPS 正常，P50 延迟 200ms 也正常
   → 但 P99 延迟飙到 12s（这说明只有少数请求慢）
   → 符合长尾延迟的特征，需要看 Tracing

2. 【Tracing 导航 — 定位故障服务】
   打开 Jaeger，按 endpoint="/api/order/create" 过滤
   → 按 duration > 5s 排序
   → 选取一个耗时 11s 的 Trace 展开时间瀑布图
   → 发现：OrderService → InventoryService 的 RPC 耗时 10.6s（正常 < 50ms）
   → 再展开 InventoryService 的 Span：
        Span: inventory.checkStock      耗时 10ms（正常）
        Span: inventory.reserveStock    耗时 10.5s（异常！）
        Span: redis.execute             耗时 10.5s
   → 锁定：InventoryService 的 reserveStock 方法中 Redis 操作极慢

3. 【Logging 定因 — 定位具体代码和根因】  
   打开 Kibana，搜索条件：
     service=inventory-service AND traceId={刚才的TraceId}
   → 找到日志：
     2026-05-16 14:23:45.123 [http-nio-8081] WARN  c.e.i.s.InventoryService -
     Redis command [EVAL] timed out after 10000ms, 
     pool active=50, idle=0, max=50
   → 根因：Redis 连接池已耗尽（50 个连接全被占用），新请求排队等连接

4. 【Metrics 验证 — 看是不是持续性问题】
   回到 Grafana，查看 InventoryService 的 Redis 连接池指标：
   → redis.pool.active 曲线确实长时间维持在 50（上限）
   → 结合发布记录：一小时前上线了批量库存预热，每次预热一次性获取 50 个连接
   → 根因彻底确认：批量预热任务打满了连接池，导致正常下单请求被阻塞
```

这个完整的三步排查流程，体现了可观测性的核心价值：**不需要重新部署加日志，仅通过已有的三支柱数据就能定位到根因。**

**加分项：** 提到"可观测性不等于收集大量数据"——很多团队的方向错了，把精力花在"把更细粒度的数据存下来"，结果存储成本爆炸但依然无法快速排查问题。可观测性的关键是"数据的关联性"而非"数据的量"。如果 Metrics 里没有 TraceId、日志里没有 TraceId、Trace 里没有日志关键字段，就算存了 PB 级数据也没用。提到"高基数（High Cardinality）的陷阱"——不要把 userId、orderId、requestId 作为 Metrics 的标签，因为这会导致时序数据库的索引爆炸（每个唯一值生成一个时间序列）。Metrics 的标签只放低基数维度（status、method、service）。高基数数据天然属于 Tracing 和 Logging。提到 RED 和 USE 方法——RED（Rate/Errors/Duration）用于评估服务的外部表现（客户端视角），USE（Utilization/Saturation/Errors）用于评估资源的内部状态（系统内部视角），这是设计可观测性指标时的两个核心框架。

## Q32：支付流程的架构设计是怎样的？唯一ID用什么方法生成？

### 考察点
候选人是否理解支付系统的核心难题——不是"怎么调微信支付 API"，而是幂等性、一致性、对账、分布式 ID 生成这四大工程挑战。考察"钱的安全"高于"系统可用性"的支付领域特有设计思想。

### 解答思路
1. 先画出支付全链路：用户下单 → 业务层生成支付单 → 调用支付渠道 → 异步回调 → 对账。
2. 重点剖析每个环节的幂等性保证——这是支付系统区别于一般业务系统的核心。
3. 单独展开分布式唯一 ID 的生成方案（雪花算法 vs 号段模式），结合支付单号的业务要求。

### 参考答案

**第一部分：支付流程的完整架构**

支付系统的设计原则和一般业务系统完全不同：**钱的安全 > 数据一致性 > 系统可用性 > 用户体验。** 宁可让用户等 5 秒也不要重复扣款。

```
┌─────────────────────────────────────────────────────────────┐
│  1. 用户点击"支付"                                            │
│     → 订单服务生成支付单（状态=待支付）                          │
│     → 调用支付网关，传入：订单号、金额、幂等Key（outTradeNo）     │
│     → 支付网关调用微信/支付宝 API                               │
│     → 返回支付链接/支付参数，前端拉起支付                        │
├─────────────────────────────────────────────────────────────┤
│  2. 用户完成支付（在微信/支付宝 App 内）                        │
├─────────────────────────────────────────────────────────────┤
│  3. 支付渠道异步通知（回调）                                    │
│     → 微信/支付宝 POST 通知到我们的回调接口                      │
│     → 验签（RSA 公钥）→ 验证金额、商户号、订单号                │
│     → 更新支付单状态（待支付 → 已支付）                          │
│     → 更新订单状态（待支付 → 已支付）                            │
│     → 返回 success（7 个字符，一个字都不能少）                   │
├─────────────────────────────────────────────────────────────┤
│  4. 主动查询（兜底）                                           │
│     → 定时任务每 5 分钟扫描"待支付"超过 30 分钟的支付单          │
│     → 主动调用支付渠道查询接口                                  │
│     → 如已支付但回调丢失 → 补单（走和回调相同的处理逻辑）         │
├─────────────────────────────────────────────────────────────┤
│  5. 对账（T+1 / 小时级）                                       │
│     → 下载支付渠道的对账单                                      │
│     → 逐条比对：我方支付单 vs 渠道账单                          │
│     → 发现差账 → 人工处理 / 自动补差                            │
└─────────────────────────────────────────────────────────────┘
```

**第二部分：支付系统最关键的设计——幂等性保证**

支付系统的幂等性贯穿了"扣款"、"回调"、"退款"三个核心环节，每个环节都要独立做幂等：

**1. 支付请求的幂等（防重复扣款）：**

支付单号（outTradeNo）就是幂等 Key。同一个支付单号对微信/支付宝发起两次支付请求，渠道会返回"订单已存在"而不是再扣一次款。所以关键在于支付单号的唯一性——不能因为重试而生成了不同的支付单号。

代码层面的实现：
```java
// 支付单号 = 业务前缀 + 时间戳 + 机器ID + 序列号
String outTradeNo = idGenerator.nextId("PAY"); // 如 PAY202605161423450011234
// 将支付单号和订单号绑定存储
INSERT INTO pay_order (out_trade_no, order_id, amount, status) 
VALUES (#{outTradeNo}, #{orderId}, #{amount}, 'PENDING');
// out_trade_no 上有唯一索引，重复插入直接报 DuplicateKeyException
```

```java
// 重试时的幂等处理
public PayResult pay(PayRequest req) {
    // 1. 查询是否已有支付单
    PayOrder existing = payOrderMapper.selectByOrderId(req.getOrderId());
    if (existing != null) {
        if ("SUCCESS".equals(existing.getStatus())) return existing.getResult();
        // 已存在但未成功，使用已有支付单号重试（而非新建）
        return channelGateway.pay(existing.getOutTradeNo(), existing.getAmount());
    }
    // 2. 新建支付单（唯一索引防并发插入）
    String outTradeNo = idGenerator.nextId("PAY");
    try {
        payOrderMapper.insert(outTradeNo, req);
    } catch (DuplicateKeyException e) {
        // 并发冲突，重新查询已有支付单并重试
        return pay(req);
    }
    return channelGateway.pay(outTradeNo, req.getAmount());
}
```

**2. 支付回调的幂等（防重复通知）：**

微信/支付宝的回调通知可能重复发送（最多 8 次），必须做幂等：

```java
public String handleCallback(CallbackDto dto) {
    // 验签...
    // 幂等：基于状态机判断
    PayOrder order = payOrderMapper.selectByOutTradeNo(dto.getOutTradeNo());
    if (!"PENDING".equals(order.getStatus())) {
        return "success"; // 已处理过，直接返回成功
    }
    // 乐观锁更新（防止并发回调）
    int rows = payOrderMapper.updateStatus(
        dto.getOutTradeNo(), "PENDING", "SUCCESS", dto.getTransactionId()
    );
    if (rows == 0) return "success"; // 被其他线程抢了先
    // 后续业务处理：更新订单状态、发积分...
    return "success"; // 注意：必须返回这 7 个字符
}
```

**3. 退款的幂等：**

退款也有自己的退款单号体系（refundNo），同理用唯一索引 + 状态机保证幂等。

**第三部分：分布式唯一 ID 生成方案**

支付系统对 ID 的要求比一般业务系统更苛刻：全局唯一、单调递增（满足 MySQL 聚簇索引）、高性能（高并发下不成为瓶颈）、带有业务语义（从 ID 上能看出时间和业务类型）。

**方案一：雪花算法（Snowflake）——推荐方案**

64 位长整型：`[1 位未用] [41 位时间戳] [10 位机器 ID] [12 位序列号]`

- 时间戳毫秒级，可用 69 年（从自定义起始时间算起）
- 机器 ID 需要手动分配（K8s 环境下 Pod 重启后 IP 变化，不能用 IP，需要通过 ZK/Redis 自动注册获取 WorkerId）
- 序列号 4096/ms，单机 TPS 约 400 万
- **时钟回拨问题**：这是雪花算法最经典的坑。NTP 校时可能导致系统时间倒退。解决方案：
  - 方案 A（美团 Leaf）：记录上次生成 ID 的时间戳，发现回拨时短暂等待（< 5ms）或抛异常拒绝服务
  - 方案 B（百度 UidGenerator）：使用 RingBuffer 预生成，弱依赖时间
  - 方案 C（生产推荐）：部署 Chrony 替代 NTP，逐步校时而非跳变

**方案二：号段模式（美团 Leaf）——极高并发首选**

不依赖时间戳，每次从数据库批量获取一个号段（如 1000 个 ID），用完再取。数据库只需一条记录：

```sql
CREATE TABLE id_alloc (
    biz_tag    VARCHAR(64) PRIMARY KEY,
    max_id     BIGINT NOT NULL,
    step       INT NOT NULL DEFAULT 1000
);

-- 获取号段（事务保证原子性）
UPDATE id_alloc SET max_id = max_id + step WHERE biz_tag = 'pay_order';
SELECT max_id, step FROM id_alloc WHERE biz_tag = 'pay_order';
```

每个服务实例拿到号段后本地自增分配，T趋近无限。极端情况下服务崩溃，损失一个号段（1000 个 ID），但对支付场景完全可接受。

**方案对比：**

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| UUID | 零依赖，简单 | 无序，索引性能差 | 非核心场景 |
| 雪花算法 | 高性能，趋势递增 | 强依赖时钟，WorkerId 管理复杂 | 绝大多数业务场景 |
| 号段模式（Leaf） | 极高并发，无时钟依赖 | 依赖数据库，号段浪费 | 支付、订单等核心链路 |
| Redis 自增 | 简单 | 依赖 Redis，持久化不友好 | 小规模项目 |

**第四部分：支付单号的业务设计**

系统内部的 ID 生成方案解决的是"无业务语义的唯一性"，但支付单号通常需要带有业务信息，便于人工排查和对账。推荐格式：

```
{业务前缀}{日期}{时间戳}{序列号}{校验位}
PAY 20260516 142345 001234 8

示例：PAY202605161423450012348
```

- 业务前缀（3 位）：PAY（支付）、REF（退款）、TRN（转账）
- 日期（8 位）：YYYYMMDD，一眼看出是哪天的支付单
- 时间戳（6 位）：HHmmss
- 序列号（6 位）：秒内递增
- 校验位（1 位）：Luhn 算法，防止输入错误

注意：支付单号不能直接用雪花算法的长整型——支付单号需要暴露给用户（客服查询、对账单），长整型太长（最长达 19 位），且没有业务可读性。

**加分项：** 提到"支付系统要有自己的对账体系，不能完全相信回调"——微信/支付宝的回调通知虽然号称"可靠性 99.99%"，但在双十一、春晚红包等极端场景下回调丢失和延迟非常常见。必须要有一套主动查询 + T+1 对账的兜底机制。提到"退款的双重保险"——退款不仅需要系统内幂等，还需要每日核对：我方记录的已退款总额 与 支付渠道账单中的退款总额是否一致。差一分钱都要查清楚。提到"长事务的拆分"——支付成功后需要执行一系列后续操作（更新订单、发积分、发券、发消息），但绝不能同步在回调接口中串行执行（微信要求回调 5 秒内返回，超时会重发）。最佳实践是"先落库、再返回 success、再异步处理"——回调接口只做验签 + 更新支付单状态 + 返回 success，后续业务逻辑通过 MQ 异步触发。提到"支付链路的灰度"——支付链路是线上最敏感的链路，任何变更（无论大小）都不能一次全量。必须接入配置中心（Apollo/Nacos），通过配置开关控制新老逻辑。新功能上线时 1% → 10% → 50% → 100%，每一步观察 30 分钟以上，错误率和延迟无异常才放量。

## Q33：支付成功消息如何保证可靠送达？支付业务一致性怎么实现？支付安全接口怎么做鉴权认证？

### 考察点
考察候选人对支付系统核心链路（消息可靠性、数据一致性、接口安全）的生产级理解和实战设计能力。

### 解答思路
1. 先分层拆解：消息可靠送达解决的是"通知不丢"问题，业务一致性解决的是"数据不错"问题，鉴权认证解决的是"请求不伪造"问题——三者分别对应消息层、数据层、接入层。
2. 消息送达从"同步回调 + 异步补偿 + 定时对账"三层兜底来答；业务一致性从"本地事务 + 异步补偿 + 幂等消费"来答；鉴权认证从"证书双向认证 + 签名验证 + 时间窗口防重放"来答。
3. 用真实踩坑经验串联三部分，例如：回调丢失导致用户付款了但订单还是待支付 → 用户投诉 → 发现需要主动查询和对账兜底。

### 参考答案

**第一层：支付成功消息的可靠送达**

支付回调不可靠是常态，不是异常。微信/支付宝的回调通知有 5 秒超时要求，超过 5 秒未返回 success 就会重发，重发间隔呈指数退避（15s → 30s → 1min → 2min → 6min → 15min → 30min → 1h → 2h → 6h，最多 24 小时）。生产环境的可靠送达需要三层兜底：

1. **同步回调（第一道防线）**：接收渠道通知后，先验签、再落库、再返回 success。强调"先落库"——即使后续逻辑挂了，支付单状态已被标记为"已支付"，资金安全已兜底。回调接口必须幂等，用 payment_no 做分布式锁或乐观锁（version 字段），防止重复通知导致重复处理。

2. **异步补偿（第二道防线）**：对于"用户付了钱，但超过合理时间（如 30 秒）还没收到回调"的订单，启动主动查询。用定时任务（每 30 秒扫描一次）或延迟消息（RocketMQ 延迟等级 18 = 30s），调用支付渠道的订单查询接口，同步支付状态。注意要做流量控制——查询接口有 QPS 限制（微信支付查询接口默认 600 次/秒），主动查询必须做限流和熔断。

3. **T+1 对账（第三道防线）**：每天凌晨拉取渠道的对账单，和内部支付流水做全量核对。对账差异分为"长款"（渠道有、我方无）和"短款"（我方有、渠道无），分别触发补单和退款流程。支付宝对账单是 CSV 格式，微信是 TXT，需要各自解析适配。

**第二层：支付业务一致性**

支付业务一致性用"最终一致性 + 幂等性 + 补偿"来保证，不强依赖分布式事务（Seata/XA 在支付场景太重，对性能影响大）：

- 支付成功后，回调接口只做"验签 + 更新支付单 + 发送 MQ 消息"，这是一个本地事务。如果 MQ 发送失败（如 broker 宕机），用"事务消息"（RocketMQ transaction message）或本地消息表（写支付单时同时写入一条 outbox 记录，定时任务扫描未发送的记录补发）。
- 下游消费 MQ 消息时（扣库存、发积分、发券），每个消费者必须支持幂等——用 order_id 或 payment_no 做唯一键，插入前检查是否已处理。消息消费失败后，RocketMQ 会自动重试 16 次（每次间隔递增），16 次后进入死信队列，由人工介入处理。
- 如果库存扣减成功但积分发放失败，不要回滚库存（回滚在分布式环境不可靠），而是通过补偿任务重试积分发放，同时记录异常日志供人工核验。

**第三层：支付安全接口鉴权认证**

支付接口的安全认证分两个方向：对内（前端 → 后端）和对外（后端 → 渠道）。

| 方向 | 方案 | 关键点 |
|------|------|--------|
| 前端 → 后端 | HTTPS + JWT/Token + 签名 | Token 设置短过期（15min），敏感操作加二次验证 |
| 后端 → 微信/支付宝 | HTTPS + 证书双向认证 + 签名验签 | 商户私钥签名，渠道公钥验签；渠道回调时我方同样验签 |

对外接口的关键安全措施：
1. **证书双向认证**：后端请求微信/支付宝时，需要加载商户证书（apiclient_cert.pem 和 apiclient_key.pem）。微信 v3 接口使用 SHA256-RSA2048 签名算法，签名串格式为 `签名串 = HTTP方法\nURL\n时间戳\n随机数\n请求体\n`。
2. **回调验签**：收到渠道回调时，必须用渠道的公钥验证签名，防止伪造通知。这是防止资金损失的底线——如果省掉验签步骤，攻击者伪造回调就能把订单设置为"已支付"而不实际付钱。
3. **时间窗口防重放**：验签时要检查回调中的 timestamp 是否在允许范围内（±5 分钟），防止攻击者抓包后重放旧的回调请求。
4. **敏感信息加密**：微信 v3 接口中，用户的银行卡号、身份证号等敏感字段使用 RSA-OAEP 加密传输，商户需要用自己的私钥解密后才能使用。私钥绝对不能打印进日志，生产环境日志必须对敏感字段做脱敏处理。

### 加分项
提到"支付链路要用独立的数据库账号，只给 select/update 权限，不给 delete/drop 权限"——即使代码有 SQL 注入漏洞，也能限制破坏范围。提到"支付回调接口的服务要独立部署，和其他业务服务物理隔离"——避免大促期间其他服务吃光 CPU/内存导致回调接口不可用。提到"每笔支付单的金额用分（cent）为单位存储，跨服务传递时用字符串而非浮点数"——避免 JSON 反序列化时 0.01 变成 0.00999999。提到"每年至少做一次支付链路的全链路压测 + 演练"——模拟渠道回调丢失、数据库主从切换、MQ 积压等异常场景，确保团队在实际故障时知道怎么处理。

## Q34：公司员工刷卡坐电梯，如何调度电梯集群？需要设计数据库和调度算法

### 考察点
考察候选人从现实场景中抽象系统模型、设计实体关系、选型调度算法的综合工程能力，以及对 IoT/嵌入式场景的性能约束理解。

### 解答思路
1. 先建模：电梯和请求是什么实体，核心状态有哪些，数据库不是重点（电梯控制是实时系统，核心数据在内存）。
2. 再讲算法：从最简单的 SCAN → LOOK → 分组分区调度，逐层优化，结合真实场景（早晚高峰、跨楼层限制）。
3. 最后讲工程落地：TCPServer 收集刷卡事件、内存状态机驱动调度、数据库只做离线分析和审计。

### 参考答案

**第一步：领域建模**

电梯集群模型抽象为三类核心实体：

```
Elevator（电梯）：
  - elevator_id, current_floor, direction(UP/DOWN/IDLE), 
  - status(NORMAL/MAINTENANCE/FULL), capacity(当前人数/最大人数),
  - high_floor, low_floor  (该电梯的服务楼层范围——有的电梯只停 20-35 层)

ElevatorRequest（乘梯请求）：
  - request_id, card_floor, target_floor, request_time, 
  - assigned_elevator_id, status(WAITING/ASSIGNED/BOARDED/COMPLETED)
```

核心数据全部在内存中，数据库只做异步落地（每秒批量写入一次）。原因：电梯调度是毫秒级实时系统，MySQL 一次写入 5-10ms 的延迟不可接受。数据库表结构简化为三张表：`elevator_event`（电梯状态变更日志）、`ride_record`（刷卡乘梯记录）、`elevator_daily_stats`（每日统计）。实际部署时，用 Redis 做实时状态的缓存，MySQL 只做离线分析和审计溯源。

**第二步：调度算法演进**

**初级方案——FCFS（先到先服务）**：不做调度，每部电梯独立响应，谁先抢到谁处理。问题：可能出现 5 部电梯同时响应一个请求然后全部空跑，浪费严重。

**中级方案——LOOK 算法（电梯扫描算法的改进版）**：

LOOK 是经典的电梯调度算法，基本逻辑：电梯沿一个方向持续运行，处理途中所有同向请求，到达该方向最远端后掉头。伪代码：

```
if direction == UP:
    找出所有 current_floor 以上的同向请求和反向请求中最远的楼层 max_floor
    移动到 max_floor，途中停靠所有同向请求楼层
    掉头，direction = DOWN
else:
    找出所有 current_floor 以下的同向请求 max_floor
    移动到 min_floor，途中停靠所有同向请求楼层
    掉头，direction = UP
```

LOOK 比 SCAN 的优化：SCAN 固定跑到两端（1 层和顶楼），LOOK 只跑到有请求的最远端就掉头，减少了无效空跑。

**高级方案——分组分区 + 提前派梯（生产级）**：

真实场景下 LOOK 还不够，需要结合业务特点做多维度优化：

1. **高低区分区**：将建筑物的楼层分为低区（1-15 层）和高区（15-35 层），2 部电梯服务低区、2 部服务高区，减少每部电梯的停靠范围。跨区请求（如从 5 层到 25 层）交由高区电梯处理。

2. **动态调峰（早晚高峰策略）**：
   - 早高峰（8:00-9:30）：大部分请求从 1 楼（大堂）出发，将一半电梯强制调度到 1 楼待命，direction 固定为 UP。
   - 晚高峰（17:30-19:00）：大部分请求从各楼层下到 1 楼，direction 优先设为 DOWN，减少空跑。
   - 平峰期恢复标准的 LOOK 调度。

3. **派梯策略（哪个请求分给哪部电梯）**：这是核心决策。当用户在 8 楼刷卡要去 20 楼，系统计算每部电梯的响应成本 = `abs(elevator.current_floor - card_floor) + 该电梯已有的停靠次数 * 单次停靠耗时`。选择成本最低的电梯分配。同时考虑方向兼容性——如果用户要上行，优先分配当前 direction 为 UP 或 IDLE 的电梯。

4. **防恶意占用**：正常用户刷卡后，系统 3 秒内返回分配的电梯编号。如果用户连续刷卡（如刷 5 次），系统识别为恶意请求，限制其 10 秒内只分配一部电梯。这是从生产环境的真实投诉（有人刷了十几层电梯导致整栋楼等电梯）中总结的。

**第三步：系统架构**

```
刷卡终端 → TCP Server（Netty，长连接，二进制协议） → 调度引擎（内存状态机）
                                                         ↓
                                                    Redis（实时状态）
                                                         ↓
                                                    MySQL（异步批量落地 + T+1 ETL 到数据仓库）
```

- 刷卡终端和服务器之间用 TCP 长连接，协议是紧凑二进制（一个包 20-30 字节），不用 HTTP（HTTP 开销太大，刷卡终端是嵌入式设备）。
- 调度引擎用单机部署（电梯数量通常不超过 20 部，单机完全够用），通过主备 + Keepalived 做高可用。
- 每周通过离线数据分析：哪部电梯的停靠次数最多、哪层楼的等待时间最长、不同时间段的人流曲线，反向优化分区策略和时间段配置。

### 加分项
提到"电梯内人数感知"——通过电梯内的称重传感器或摄像头计算当前载客数量，超过阈值（如额定载重 80%）自动跳过中途请求直达目标楼层，并在调度时标记为 FULL 状态不再接收新分配。提到"电梯的维修模式和消防模式"——维修模式下该电梯从调度池中移除，已分配但未乘坐的请求自动重新调度到其他电梯；消防模式下所有电梯自动降到 1 楼并开门。提到"双轿厢电梯（双层电梯）的调度"——双轿厢电梯的 1 层和 2 层各有一个轿厢，需要额外考虑"同层对齐"问题：当 1 层轿厢停在 5 层时 2 层轿厢在 6 层，两个轿厢的逻辑位置和物理位置存在固定偏移。提到"用强化学习做长线优化"——Google DeepMind 曾用强化学习优化数据中心电梯调度，相比传统算法节省了 30% 以上的等待时间，但落地成本高，适合头部科技公司的大楼。

## Q35：如何解决微服务调用中的服务雪崩问题？

### 考察点
考察候选人对微服务架构中故障传播机制的理解深度，以及对熔断、限流、降级、隔离等稳定性手段的实战组合能力。

### 解答思路
1. 先解释雪崩的成因（级联失败的正反馈循环），用一个具体例子串联。
2. 再分层讲解法：入口层限流 → 依赖层熔断 → 资源层线程隔离 → 业务层降级，每一层都有具体的工具和参数。
3. 最后用一个参数配置表做总结，强调"没有万能参数，每个服务的阈值都要根据压测结果来定"。

### 参考答案

**雪崩的本质**

服务雪崩不是"有一个服务挂了"，而是"一个服务慢了 → 调用方线程池被拖住 → 调用方也慢了 → 上游也被拖住 → 全链路崩溃"的正反馈循环。举个例子：订单服务调用库存服务的 RT 从 50ms 涨到 5s，订单服务的 Tomcat 线程池（默认 200 个线程）在 1 秒内被耗尽，订单服务对所有上游（网关、前端）都不可用——库存服务只慢了 100 倍，但干掉了整个订单服务。

**解法：四层防御体系**

**第一层：入口限流（API Gateway / Sentinel）**

在网关层或服务框架层设置限流规则，超过阈值的请求直接拒绝（返回 429 Too Many Requests 或排队等待），而不是放进后端让它慢处理。常用策略：

| 限流算法 | 原理 | 适用场景 |
|----------|------|----------|
| 令牌桶 | 固定速率放入 token，请求需消耗 token | 允许一定突发，适合网关 |
| 漏桶 | 固定速率处理请求，多余排队 | 平滑输出，适合保护下游 |
| 滑动窗口 | 统计最近 N 秒内的请求数 | 精确控制 QPS，适合业务限流 |

生产级限流的三要素：阈值 = 根据压测结果的 80% 设置（留 20% 安全余量）；失败处理 = 返回明确错误码 + 重试建议（Retry-After 头）；监控 = 限流触发次数、被拒绝的请求占比必须接入告警。

**第二层：依赖熔断（Resilience4j / Hystrix / Sentinel）**

熔断器是防止故障扩散的核心武器。状态机三态：

```
CLOSED（正常）→ 失败次数/慢调用比例超过阈值 → OPEN（熔断）
OPEN（熔断）→ 等待一段时​​间（Sleep Window）→ HALF_OPEN（半开）
HALF_OPEN → 放少量请求试探测 → 成功则 CLOSED，失败则继续 OPEN
```

关键参数调优（以 Resilience4j 为例）：

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| failure-rate-threshold | 50% | 失败率阈值，不宜过低（误熔断） |
| slow-call-rate-threshold | 100% | 慢调用阈值，100% 意味着所有慢调用都计入 |
| slow-call-duration-threshold | 3s | 超过 3 秒算慢调用 |
| wait-duration-in-open-state | 30s | 熔断后 30 秒进入半开状态 |
| permitted-number-of-calls-in-half-open-state | 3 | 半开时放 3 个请求试探 |
| sliding-window-size | 10 | 统计 10 次调用的结果 |

一个常见的踩坑：不要把熔断时间设太短（如 3 秒），否则会形成"开关振荡"——刚熔断马上就半开探测，探测失败又熔断，反复循环，反而加重系统负担。

**第三层：线程隔离（Bulkhead / 线程池隔离）**

给每个下游依赖分配独立的线程池，一个依赖的故障不会耗尽整个服务的线程资源。两种隔离方式：

| 方式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 线程池隔离 | 隔离彻底，可设独立超时 | 线程切换开销，内存占用大 | 核心非关键依赖（短信、邮件） |
| 信号量隔离 | 开销小，无线程切换 | 不能设超时，阻塞式 | 低频调用、性能敏感依赖 |

生产上的折中：核心依赖不隔离（信任链路），非核心依赖线程池隔离。例如订单服务调库存服务（核心）不隔离，调短信通知服务（非核心）用独立线程池（核心线程 5、最大线程 10、队列 100）。

**第四层：业务降级（Fallback）**

熔断或限流后不能直接抛异常给用户，需要有兜底逻辑：
- **静态降级**：返回缓存数据（如商品详情页在库存服务不可用时展示最近一次缓存的库存状态，标注"库存信息可能延迟"）
- **默认降级**：返回默认值（如推荐服务挂了，返回全站热榜而不是空白页）
- **静默降级**：非关键功能直接跳过（如积分服务挂了，不影响下单主流程，事后批量补发积分）

**参数怎么定？**

没有教科书答案，所有参数都要从压测中来。一个标准的压测 → 参数确定流程：

1. 对单个服务做压力测试，找到极限 QPS 和 RT 拐点。
2. 限流阈值 = 极限 QPS 的 80%。
3. 熔断阈值 = 从第一次 RT 恶化到线程池满的时间窗口 / 2（保守估算）。
4. 线上灰度验证一周，观察误熔断率和漏熔断率，微调参数。
5. 每次大促前重新压测重新定参——业务逻辑和依赖关系会变，参数也有保质期。

### 加分项
提到"写一个 SDK 封装稳定性治理能力，业务方只需引入依赖 + 配置项即可接入"——避免每个服务都要重复配置熔断/限流/降级逻辑，降低接入成本。提到"在不同层级做限流的策略区分"——网关层做的是"QPS 总量控制"，服务层做的是"针对每个下游的并发控制"，两者不冲突，需要配合使用。提到"混沌工程"——定期注入故障（如用 ChaosBlade 随机 kill 一个下游服务），验证熔断降级逻辑是否按预期生效。很多团队的熔断规则只在配置文件里写了，但从没真的触发过，真正故障来的时候配置是错的。提到"从超时时间倒推设计"——一个请求的总超时时间（如 3 秒）要合理分配给链路上的每个服务：网关 100ms → 订单服务 1s → 库存服务 500ms → 支付服务 1s，每层的超时要逐级递减，如果内层超时比外层还长等于没设。提到"重试的放大效应"——如果你在每个服务层都重试 3 次，5 层链路在最坏情况下会产生 3^5 = 243 倍流量放大，必须区分"重试"和"兜底"两个概念：只在失败概率最高的那层重试，其他层做降级兜底。
