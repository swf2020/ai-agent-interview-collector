## Q1：什么是 RAG（检索增强生成）？一个完整的 RAG 流程包含哪些关键步骤？请从数据准备到最终生成详细描述整个过程。

### 考察点
考察候选人对 RAG 基本原理的理解深度，以及是否具备从零搭建 RAG 系统的全局视野，而非仅停留在"查文档喂给 LLM"的层面。

### 解答思路
1. 先定义 RAG 的核心概念和它解决的核心问题（幻觉、知识截断、可解释性）。
2. 将 RAG 流程拆分为离线阶段（数据准备）和在线阶段（查询检索与生成）。
3. 针对每个子步骤展开说明关键技术选择与常见工程挑战。

### 参考答案
RAG（Retrieval-Augmented Generation，检索增强生成）是一种将信息检索与语言模型生成相结合的技术范式。其核心思想是：在 LLM 生成回答之前，先从一个外部知识库中检索与用户问题最相关的文档片段，然后将这些片段作为上下文注入到 prompt 中，引导模型基于检索到的"证据"来生成答案，从而有效缓解大模型的幻觉问题和知识截止限制。

一个完整的 RAG 流程包含以下关键步骤：

**一、数据准备阶段（离线）**
1. **文档解析与切分（Chunking）**：将原始文档（PDF、网页、数据库记录等）解析为纯文本，然后按照语义边界（段落、章节）或固定长度（如 512 token）切分为 chunk。切分策略直接影响后续检索的粒度与召回质量，通常需要配合重叠窗口（overlap）来避免关键信息被切断。
2. **向量化（Embedding）**：调用 embedding 模型（如 text-embedding-3-large、BGE、GTE 等）将每个 chunk 转换为高维向量，向量捕捉了文本的语义信息。
3. **向量索引构建**：将生成的向量存入向量数据库（如 Milvus、Pinecone、Qdrant、Weaviate），并建立 ANN（近似最近邻）索引以支持高效检索。

**二、查询检索阶段（在线）**
4. **Query 改写与多路召回**：对用户原始问题进行意图分析、指代消解和改写（可利用 LLM 做 Query Rewriting），再结合向量检索（语义匹配）、关键词检索（BM25，精确匹配）甚至知识图谱检索进行多路召回。
5. **重排序（Reranking）**：使用 Cross-Encoder 模型（如 Cohere Rerank、BGE-Reranker）对多路召回的候选文档进行精细化排序，筛选出最相关的 Top-K 片段，这是提升最终答案质量的关键一环。

**三、生成阶段（在线）**
6. **上下文组装与 Prompt 构建**：将检索到的片段与用户问题、系统指令一起组装为最终 prompt，控制好上下文窗口和 token 分配。
7. **答案生成与引用溯源**：LLM 基于组装好的 prompt 生成答案，通常要求模型逐条引用来源（citation），从而提高答案的可信度与可追溯性。
8. **后处理与效果评估**：对生成结果进行格式校验、敏感词过滤，并通过 RAGAS 等框架评估答案的忠实度（Faithfulness）和相关性（Answer Relevance）。

**加分项：** 高级 RAG 模式如 Self-RAG（让 LLM 自主判断是否需要检索及检索结果是否相关）、CRAG（Corrective RAG，对检索结果做自我修正）、Graph RAG（结合知识图谱处理多跳推理问题）等，代表了该领域的演进方向。此外，Agentic RAG 将检索交给 Agent 自动编排决策，是当前落地热点。

## Q2：RAG 和长上下文模型（如 1M token 窗口）的关系是什么？超长上下文模型出现后 RAG 架构的必要性是否会下降？

### 考察点
考察候选人对技术演进趋势的判断力，能否跳出"选边站队"的二元思维，从成本、延迟、精准度等多维度理性分析两种技术路线的定位。

### 解答思路
1. 首先明确两者不是替代关系，而是互补关系——各自解决不同层面的问题。
2. 从延迟、成本（注意力计算 O(n²)）、准确率（"大海捞针"实验中长上下文的中间信息容易被忽略）、可解释性四个维度对比。
3. 给出两者融合的最佳实践方向。

### 参考答案
长上下文模型并未削弱 RAG 的必要性，反而催生了更高级的 RAG 模式。

RAG 的核心价值不在于"弥补上下文的不足"，而在于**精准的信息筛选与组织**，为模型提供最相关的上下文而非全量背景，从而提升生成质量并降低成本。具体来看，长上下文有以下局限：

1. **成本与延迟问题**：Attention 计算复杂度为 O(n²)，即使 1M token 窗口可用，每次推理的算力消耗和响应延迟仍然是工程上不可接受的。RAG 将相关片段精简到数百至数千 token，大幅降低推理成本。

2. **"大海捞针"困境**：研究表明，当上下文极长时，模型对中间位置的信息召回率显著下降（Lost in the Middle 现象）。RAG 通过检索提前定位关键信息，避免了让模型在长文本中自行定位。

3. **可解释性与可控性**：RAG 天然支持来源溯源，检索到的每个 chunk 都可以标注出处，长上下文"全量喂入"反而模糊了信息来源边界。

当前趋势是将两者结合：用 RAG 做精准召回，用长上下文窗口容纳更完整的上下文（如多篇相关文档、历史对话轮次），实现**"大窗口 + 精检索"**的架构。

**加分项：** 介绍"大海捞针"（Needle in a Haystack）评测方法，以及 Anthropic 提出的上下文工程（Context Engineering）概念——用检索决定"放什么进去"，用长窗口容纳"放进去的内容"。Agentic RAG 中的多步检索也依赖长上下文维持推理链。

## Q3：Chunking 策略有哪些？不同场景下怎么选？长文档切片的粒度一般怎么选择？为什么要有重叠区域？

### 考察点
考察候选人对 RAG 数据预处理细节的掌握程度，chunking 是决定召回质量的上游关键环节，几乎所有 RAG 项目中都会遇到的问题。

### 解答思路
1. 枚举主流切分策略及其适用场景。
2. 给出粒度选择的一般性原则和不同场景下的经验值。
3. 解释重叠区域的必要性和设置方法。

### 参考答案
Chunking 是 RAG 系统中直接影响召回质量的核心预处理步骤。常见策略包括：

**1. 固定长度切分（Fixed-size）**：按 token 数（如 512 token）或字符数切分，实现简单，适合同质化文本（如新闻语料），但容易在句中断开，破坏语义完整性。

**2. 基于分隔符切分（Recursive Split）**：按 `\n\n` → `\n` → `。` → `，` 的分隔符优先级递归切分，优先保留段落和句子边界，是目前最通用的方案（LangChain 的 RecursiveCharacterTextSplitter）。

**3. 语义切分（Semantic / Sentence-based）**：使用 spaCy/NLTK 做句法分析，或利用 embedding 计算相邻句子的语义相似度，在语义转折处切分，适合技术文档、论文等逻辑严密的内容。

**4. 文档结构感知切分**：根据 Markdown 标题层级、HTML DOM 结构、PDF 章节来切分，保留元信息（章节标题、层级路径），用于提升 chunk 的上下文完整性，是当前进阶方案。

**5. Agentic Chunking / 小模型切分**：用小模型判断切分边界，最为灵活但成本较高。

**粒度选择**：根据下游任务决定。FAQ 问答用 128-256 token；一般文档问答用 512-1024 token；法律合同/论文需要完整条款时用 1000-2000 token。核心原则是：一个 chunk 应包含一个完整的语义单元，能独立支撑一个答案。

**重叠区域**：引入 overlap（通常为 chunk 大小的 10%-20%）是为了避免关键信息恰好在两个 chunk 的边界处被割裂。比如一个完整的句子或概念可能被切到两个 chunk 的尾部/头部，导致 embedding 后任一 chunk 都无法单独匹配到该信息。

**加分项：** 提及 Small-to-Big（Sentence Window）检索策略：用小粒度 chunk 做检索（提高召回精度），用大粒度 chunk 或合并相邻 chunk 送给 LLM 生成（保证上下文完整）。还有 Multi-representation Indexing（摘要-原文双层索引）。

## Q4：为什么需要 Rerank 模型？向量检索已经计算了相似度，为什么还要引入交叉编码器进行重排？Rerank 后的截断策略是怎么设计的？

### 考察点
考察候选人对检索精排原理的深入理解，能否意识到向量检索的先天局限，以及 Rerank 在 RAG 管线中的关键价值。

### 解答思路
1. 解释双塔（Bi-Encoder）与交叉编码器（Cross-Encoder）在结构上的根本差异以及由此导致的精度差距。
2. 说明 Rerank 在 RAG 管线中的位置和作用。
3. 阐述 Rerank 后的截断策略（Top-K 选择方法）。

### 参考答案
向量检索（Bi-Encoder）和 Rerank（Cross-Encoder）本质上是两种不同的匹配范式：

**Bi-Encoder（向量召回）**：Query 和 Document 分别独立编码为向量，检索时通过余弦相似度等度量计算匹配度。优点是速度极快（可通过向量索引实现 ANN 搜索），代价是 Query 和 Document 在编码时没有交互，失去了细粒度的语义交互信息。

**Cross-Encoder（重排序）**：将 Query 和 Document 拼接后一起送入模型，通过自注意力机制实现深度交互。这样模型能捕捉到 token 级别的精确对应关系（如否定词、修饰关系、关键词覆盖），精度远高于 Bi-Encoder。缺点是计算开销大，无法对百万级文档逐条计算。

因此实际管线是：**用向量检索快速召回 Top-K 候选（如 Top-100），再用 Rerank 对这 100 个候选做精细排序**，兼顾效率与精度。Rerank 对最终答案质量的影响显著——正确的片段排进 Top-3 和排在 Top-20 之外，进入 LLM 上下文后效果天差地别。

**截断策略**：
1. **固定 Top-K**：取 Rerank 后分数最高的 K 个文档，简单直接。
2. **分数阈值截断**：设定最低相关性分数（如 >0.5），过滤低质量召回。防止在无相关文档时强行喂入无关内容。
3. **MMR（最大边际相关性）**：在相关性和多样性之间取折衷，依次选择"与 Query 相关且与已选文档不重复"的文档，避免多个 chunk 包含相同信息时浪费上下文窗口。
4. **Token 预算控制**：根据 LLM 上下文窗口剩余大小，动态决定纳入多少个 reranked chunk，优先级按分数从高到低，总 token 数不超过预算上限。

**加分项：** 提及 LLM-as-a-Reranker（用 GPT-4 等强模型做 pointwise/pairwise/Listwise 排序）、RankGPT、以及 ColBERT（延迟交互，在 Bi-Encoder 和 Cross-Encoder 之间取得折衷）等前沿方案。工程上关注多路召回融合后的 Rerank 排序一致性。

## Q5：怎么评估 RAG 系统的效果？RAG 系统的评测维度有哪些？如何构建评测数据集？

### 考察点
考察候选人对 RAG 质量保障体系的完整认知，评测能力是衡量工程成熟度的重要指标，也是面试中区分初、中、高级候选人的关键题目。

### 解答思路
1. 从检索端和生成端两个维度分别阐述评测指标。
2. 介绍主流的自动化评测框架与工具。
3. 说明评测数据集构建的最佳实践（三层漏斗）。

### 参考答案
RAG 系统的评测是一个多层次工程，通常分为**检索端**和**生成端**两个维度：

**检索端评测指标：**
- **Recall@K**：Top-K 个召回片段中是否包含正确答案，K 一般取 5/10/20。
- **MRR（Mean Reciprocal Rank）**：第一个相关文档的排名倒数均值，关注最佳结果的排名位置。
- **NDCG@K**：考虑排名位置权重的归一化折损累积增益，越靠前的相关文档得分越高。
- **Hit Rate**：Top-K 中至少命中一个相关文档的查询比例。

**生成端评测指标（RAGAS 框架为代表）：**
- **Faithfulness（忠实度）**：生成的答案是否完全基于检索到的上下文，不编造事实。通过将答案拆解为原子陈述，逐一验证是否能从 context 中找到支撑。
- **Answer Relevance（答案相关性）**：答案是否紧扣用户问题，不偏离主题。
- **Context Precision（上下文精确度）**：检索到的文档中真正被用到的比例，衡量有无噪音。
- **Context Recall（上下文召回度）**：标准答案所需的信息，检索到的上下文覆盖了多少。
- **Answer Correctness（答案正确性）**：答案的语义与标准答案是否一致。

**评测数据集构建（三层漏斗法）：**
1. **标准问答对**：从生产日志中取样或人工构建，覆盖高频问题和典型长尾问题。
2. **对抗性样本**：构造边界 case（否定式提问、跨文档推理、时序敏感问题），测试系统鲁棒性。
3. **持续评测机制**：线上收集用户反馈（点赞/踩、人工标注），配合 LLM-as-a-Judge 做自动化离线回归评测，形成评测闭环。

**加分项：** 提及人工评测（Human Evaluation）的设计方法：双盲评测、Kappa 系数衡量标注一致性。以及 Deepeval、LangSmith、Langfuse 等评测与可观测性平台的选型对比。介绍如何利用 LLM 自动生成评测数据集（Synthetic Data Generation）加速评测迭代。

## Q6：稠密向量和稀疏向量的区别是什么？各自适合什么场景？向量检索和关键词检索是怎么组合的（混合检索）？

### 考察点
考察候选人对检索技术栈底层原理的理解，混合检索是工业级 RAG 系统的标配，也是高频面试题。

### 解答思路
1. 从表示方式、计算方式、优劣势三个角度对比稠密向量和稀疏向量。
2. 说明各自适用场景。
3. 详述混合检索的两种主流组合方式：结果融合与总分结合。

### 参考答案
**稠密向量（Dense Vector）** 是通过 embedding 模型（如 BGE、text-embedding-3）将文本映射到一个固定维度的连续向量空间（如 768/1536 维），每个维度都是一个非零浮点数。它捕捉的是**语义相似性**——即使关键词完全不同，只要语义相关（如"车"和"汽车"），向量距离也很近。适合处理同义词、意译、跨语言等场景，但对专有名词、缩写、数字等精确匹配场景容易漏召回。

**稀疏向量（Sparse Vector）** 是传统信息检索的范式，以 BM25 为代表。向量维度等于词表大小，绝大多数维度为零，非零维度对应 TF-IDF 权重。它捕捉的是**词汇匹配度**——精确的关键词命中，对专有名词、代码片段、型号编号等"硬匹配"场景效果极佳，但无法处理语义层面的同义改写。

**混合检索（Hybrid Search）的组合方式：**

1. **结果层融合（Result Fusion）——最常用**：
   - 分别执行向量检索和 BM25 检索，各自取 Top-K 结果。
   - 通过 **RRF（Reciprocal Rank Fusion）** 算法合并排序：`score(doc) = Σ(1/(k + rank_i))`，k 为常数（通常取 60），对两路排名做加权平滑。
   - 也可用加权求和融合，但需要先对分数做归一化（Min-Max 或 Z-score）。

2. **构造层结合（Sparse-Dense Hybrid Vector）**：
   - 使用 SPLADE 或 BGE-M3 等模型直接生成兼具语义和词汇匹配能力的混合向量，一个向量同时表达稀疏和稠密特征，一次检索即可完成。

**混合检索的适用场景**：几乎所有生产系统都推荐开启混合检索，因为真实查询往往是"语义"和"精确"的混合——用户可能用口语化表达问一个包含专业术语的问题（如"上次那个 BG-2345 型号的故障怎么解决？"）。仅靠向量检索会漏掉"BG-2345"这个关键编号。

**加分项：** 提及 RRF 的平滑参数 k 的选取经验，以及分数归一化方法的对比（Min-Max vs Z-score vs Rank-based）。多路召回扩展：除了向量+BM25，还可加入知识图谱路径、结构化字段过滤；多语言检索中 BM25 需要配合分词器（analyzer）做语言适配。了解 ColBERT 等延迟交互式检索模型在稠密和稀疏之间取得的平衡。

## Q7：RAG 中如果没有召回到相关知识，如何约束模型避免胡编？RAG 幻觉检测与控制怎么做？

### 考察点
考察候选人对 RAG 安全边界和幻觉控制的工程实践能力，这是 RAG 系统从"能用"到"可靠"的关键跃迁。

### 解答思路
1. 先区分两种场景：完全无召回 vs 召回但无相关知识，分别给出策略。
2. 从拒绝回答、检索质量门控、幻觉检测三个层面构建防线。
3. 介绍幻觉检测的具体实现方案。

### 参考答案
RAG 系统中避免胡编需要构建多层防线：

**第一层：检索质量门控**
在检索结果进入 LLM 之前设置质量检查点。计算检索结果与 Query 的相似度分数分布，设定阈值：若 Top-1 相似度 < 0.3（或 Rerank 分数 < 0.5），判定为"低质量召回"，触发降级策略。不将无关内容喂给模型，而是走安全回复模板，如"抱歉，我目前的知识库中没有找到相关信息，建议您换个方式提问或联系人工客服。"

**第二层：Prompt 约束与明确指令**
在 System Prompt 中强约束模型行为——"如果提供的上下文不包含回答问题所需的信息，请直接说'根据现有资料无法回答'，不要猜测或编造。"并配合 Few-shot 示例展示"无可回答时拒绝"的行为模式。这种指令遵循（Instruction Following）是当前强模型可以有效执行的基础防线。

**第三层：幻觉检测（Hallucination Detection）**
在生成后对输出做后验检测，主流方案包括：
- **基于 NLI（自然语言推理）的验证**：将答案拆分为原子事实，逐条与检索上下文做蕴含关系判断（entailment/contradiction/neutral），标注矛盾或不支持的部分。工具如 TruLens、SelfCheckGPT。
- **LLM-as-a-Judge 自检**：让另一个 LLM（或同一模型二次调用）审查答案是否完全基于给定的上下文，输出 Factuality Score。
- **Self-Reflective RAG**：让生成模型在输出时同步标记每个陈述的来源 chunk，若无对应来源则标记为"不确定"，再由系统判定是否保留。
- **检索二次验证**：对答案中的关键实体（人名、数字、日期）做反向检索验证，检查这些实体是否确实出现在原始知识库中。

**加分项：** 提及 G-Eval、UniEval 等参考无关的幻觉评估指标；RAGAS Faithfulness 的实现原理（将答案拆为原子陈述后用 NLI 验证）；DeepEval 框架的 hallucination metric 集成。多轮对话中的滚动幻觉检测——每轮都重新验证之前引用的上下文是否依然有效。

## Q8：Query 改写你是怎么做的？解决什么问题？如何实现？

### 考察点
考察候选人对 RAG 检索前置优化的实践经验，Query 改写是决定召回质量的上游瓶颈，直接影响整个系统的可用性。

### 解答思路
1. 明确 Query 改写要解决的几类核心问题。
2. 介绍当前主流的改写技术栈（规则、LLM、混合方案）。
3. 给出工程落地的具体实现流程和注意事项。

### 参考答案
Query 改写是 RAG 系统中连接"用户自然语言输入"与"知识库检索"的关键桥梁。用户原始 Query 往往不适合直接检索，改写的核心目标是**将用户的非结构化、口语化、模糊的提问重写为更适合检索系统理解的结构化查询**。

**解决的核心问题：**
1. **指代消解与上下文补全**：多轮对话中"它怎么样？""那个方案呢？"，需要根据历史对话补全省略的主语和对象。
2. **口语化转正式化**：将"咋回事""这玩意儿咋整"转为"故障原因及解决方法"。
3. **Query 拆分**：对于复合问题（"A 和 B 的区别是什么？各有什么优缺点？"），拆为多个原子查询分别检索再合并。
4. **关键词抽取与权重调整**：对长问题提取核心检索词，降低噪音词。
5. **假设性文档生成（HyDE）**：先用 LLM 生成一个"假设性答案"，用该答案的 embedding 代替原始 query 做检索，缩小 query-document 的语义鸿沟。

**实现方案（三层递进）：**
1. **规则层**：分词 + 词性标注 + 同义词扩展 + 查询模板。适合高频固定模式的 Query，延迟最低。
2. **LLM 驱动改写**：用专门训练的改写模型或 GPT-4 做端到端改写，Prompt 模板如："将以下用户问题改写为更适合知识库检索的查询语句，保留核心语义，补充隐含上下文，消除歧义：[用户问题]"。改写后再调用 embedding 做检索。
3. **混合方案（工程推荐）**：规则做快速预处理（去停用词、同义词扩展），LLM 做语义级改写（指代消解、意图识别、拆分），改写结果拆分为多路查询并发检索，最后 RRF 融合。

**工程落地关键点**：Query 改写引入的延迟（LLM 调用耗时）需要在准确性和响应速度之间权衡——对简单 Query 可跳过改写直接检索，对模糊、多轮、复合 Query 才触发改写链路。同时缓存改写结果，对高频相似 Query 避免重复调用 LLM。

**加分项：** 提及 Multi-Query Retrieval（从一个 Query 生成多个改写版本并发检索合并结果）、Query2Doc（用小模型生成伪文档再抽取关键词做稀疏检索）、Step-Back Prompting（先抽象成"后退问题"再做检索）。LangChain 的 MultiQueryRetriever 和 LlamaIndex 的 Query Transform 模块的对比。

## Q9：HyDE（Hypothetical Document Embeddings）的原理和应用场景？在 query 模糊时是如何提升召回效果的？

### 考察点
考察候选人对前沿 RAG 检索优化技术的理解深度，HyDE 是 2023 年 Gao 等人提出的经典方案，至今仍是解决 query-document 语义鸿沟的重要方法。

### 解答思路
1. 阐述 HyDE 的核心原理和它要解决的根本问题。
2. 描述 HyDE 的执行流程。
3. 分析适用场景和局限性，解释为何在 query 模糊时特别有效。

### 参考答案
HyDE（Hypothetical Document Embeddings）的核心洞察是：**用户 Query 和知识库文档处于不同的语义空间**——Query 通常很短（几个词到一句话），而文档由完整段落组成，直接拿短 Query 的 embedding 去检索长文档向量，本质上存在"语义不对齐"的问题。

**工作原理：**
1. **假设性文档生成**：给定用户查询（如"如何防止猫咪抓沙发？"），先让 LLM 生成一个假设性的完整回答文档。LLM 不需要知道真实答案，只需生成一个"看起来像答案"的段落，如"防止猫咪抓沙发的方法包括：提供猫抓板、使用驱避剂、定期修剪指甲……"
2. **用伪答案做 Embedding**：对生成的假设文档做 embedding，得到的向量位于"答案文档"的语义空间，而非"查询"的语义空间。
3. **用伪答案的向量去检索真实知识库**：embedding 相似度匹配的是"答案-文档"而非"问题-文档"，大大提高了命中率。

**为何对模糊 Query 特别有效**：模糊 Query 信息量稀少（如"那个自动化的事"），本身 embedding 表达能力极弱。HyDE 通过 LLM"脑补"出一个典型答案的样子，将信息量从少数几个词扩展到几百词，embedding 变得稠密且精确。LLM 的脑补能力在这里被用作了"语义扩展器"而非"回答生成器"。

**适用场景：**
- 用户查询极短、口语化、缺乏专业术语（如客服场景）
- 跨语言检索（用目标语言生成假设文档）
- 知识库文档为长文、用户查询为关键词的场景

**局限性：**
- 额外增加一次 LLM 调用，延迟较高（约 1-3 秒），不适合对延迟敏感的场景。
- 当 LLM 脑补方向跑偏时（生成的假设文档与实际知识库内容方向不一致），反而可能误导检索。
- 对事实型精确查询（如"产品 BG-2345 的规格"）不适用，HyDE 的"脑补"可能生成错误的规格数字。

**加分项：** 提及 HyDE 的变体方案——Reverse HyDE（用知识库文档生成假设性 Query 做索引端增强）、HyDE + 对比学习（用正负例训练专门的假设文档生成模型）、以及与 Query2Doc 的对比（Query2Doc 生成的伪文档用于稀疏检索）。结合 Rerank 做二次过滤可缓解 HyDE 脑补跑偏的风险。

## Q10：RAG 与小模型微调的适用场景分别是什么？全参数微调 vs PEFT（LoRA/Adapter 等）如何选择？

### 考察点
考察候选人对 RAG 和微调两条技术路线的取舍判断力，以及微调技术栈的工程选型能力。这是架构决策层面的高频问题。

### 解答思路
1. 从数据特性、任务需求、资源约束三个维度对比 RAG 和微调的适用边界。
2. 说明两者并非对立，可以互补（RAFT 等融合方案）。
3. 对比全参数微调和各种 PEFT 方法的工程选型。

### 参考答案
**RAG vs 微调的适用场景：**

| 维度 | RAG | 小模型微调 |
|------|-----|-----------|
| 知识更新频率 | 高频更新（实时数据、新闻）——知识库实时写入即可生效 | 低频更新——需重新训练或继续预训练 |
| 知识量级 | 海量知识（百万至亿级文档）——向量库水平扩展 | 有限知识——参数容量受模型规模限制 |
| 可解释性要求 | 高——天然支持溯源和引用 | 低——模型"记忆"，难以追溯推理来源 |
| 任务类型 | 知识密集型问答、文档总结、事实查询 | 格式转换、风格迁移、结构化提取、分类 |
| 延迟要求 | 中等（检索 + 生成） | 低（单次推理） |
| 领域术语特殊度 | 通用领域适配 | 高度专业化领域（医疗、法律、金融内部术语） |

**选择原则：** 知识需要经常更新、需要溯源 → RAG；任务模式固定、有标注数据、需低延迟 → 微调。二者可以结合：用微调让模型"学会"如何利用检索结果（如 RAFT——Retrieval Augmented Fine-Tuning，训练时混入干扰文档让模型学会辨别相关/无关上下文），用 RAG 提供实时知识。

**全参数微调 vs PEFT 的选择：**

- **全参数微调（Full Fine-Tuning）**：更新模型所有参数，效果上限最高，但需 GPU 显存为模型大小的 4-5 倍（如 7B 模型需约 56GB 显存），训练成本高，且每个任务需保存一份完整模型副本。
- **LoRA（Low-Rank Adaptation）**：冻结原模型权重，在 Attention 层注入低秩矩阵作为可训练参数。典型配置 rank=8/16/32/64。参数量仅为原模型的 0.1%-1%，单卡可训练 7B 模型，训练速度约为全参数微调的 2-3 倍。多任务时可热切换 LoRA 权重（仅几十 MB），是当前最主流方案。
- **Adapter**：在 Transformer 层间插入小型瓶颈网络，效果略低于 LoRA，且推理时增加额外计算开销。
- **Prefix/Prompt Tuning**：只训练虚拟 Token 的 embedding，参数量极小但效果上限较低，适合极低资源场景。

**工程选型建议**：首选 LoRA（rank=16/32，alpha=2*rank），在验证集上达到满意效果即可；若效果不够且资源充足，再考虑全参数微调。Q-LoRA（量化 + LoRA）可进一步降低门槛，在消费级 GPU 上微调 33B 模型。

**加分项：** 提及 RAFT（检索增强微调）的论文原理和适用场景；LoRA+ 和 DoRA 等 LoRA 改进方案；vLLM 对 LoRA 热切换的推理优化（多租户共用一个基座模型）。Unsloth 等微调加速框架的对比。RAG 和微调的融合架构：微调做意图路由和格式化，RAG 做知识供给。

## Q11：RAG 的常见失败场景有哪些？如何解决？RAG 系统在实际部署中可能面临哪些挑战？

### 考察点
考察候选人的 RAG 系统实战经验和故障排查能力。这是区分"做过 Demo"和"真正上过生产"的分水岭题目。

### 解答思路
1. 从检索、生成、工程三个层面系统枚举失败场景。
2. 给出每个场景的根因分析和针对性解决方案。
3. 补充实际部署中的非技术挑战。

### 参考答案
**RAG 常见失败场景与解决方案：**

**一、检索层面**

1. **召回失败（低 Recall）**：知识库有答案但没召回来。根因：Query 与文档的语义/关键词不匹配。解决：引入 Query 改写（指代消解、HyDE、多查询扩展）+ 混合检索（向量 + BM25）+ 调优 Chunk 大小和 overlap。

2. **低精度噪音（低 Precision）**：召回了大量不相关文档，淹没了真正有用的信息。根因：向量检索对"看起来相关"但实际无关的内容也给了高分。解决：引入 Reranker（Cross-Encoder）+ 设置相似度阈值过滤 + MMR 去重。

3. **Top-1 陷阱**：最相似的 chunk 恰好不是包含答案的那个（如同一个主题的不同方面）。解决：增大 Top-K（不要只取 Top-1/Top-3），配合多样性策略（MMR）确保覆盖不同角度。

4. **跨 Chunk 推理断裂**：答案需要结合两个或多个非相邻 chunk 的信息才能得出。根因：关键信息分散在不同切片中。解决：Sentence Window Retrieval（小粒度检索 + 大窗口扩展上下文）+ Hierarchical Index（父子文档索引）+ Graph RAG（知识图谱辅助多跳推理）。

**二、生成层面**

5. **幻觉与编造**：模型在上下文不足时强行生成，或在有上下文时混入自身的先验知识。解决：强化 System Prompt 的忠实度约束 + 后置幻觉检测 + Self-Reflective RAG。

6. **上下文忽略**：检索到了正确信息，但模型生成了与之矛盾的内容。根因：模型"更相信"自己的参数知识而非上下文。解决：Prompt 中强调"优先使用提供的上下文" + 使用更强的指令遵循模型 + 对比上下文与输出的 NLI 校验。

7. **引用错误**：答案正确但引用了错误的来源段落。解决：逐句校验引用对应关系 + RAGAS Faithfulness 评测闭环。

**三、工程层面**

8. **Chunk 边界切断（Chunk Boundary Cutoff）**：关键语义单元被硬切到两个 Chunk 中。解决：合理 overlap + Semantic Chunking + Small-to-Big 检索策略。

**实际部署挑战：**
- **数据更新与索引一致性**：文档增删改后，向量索引需同步更新。增量更新策略、版本管理、回滚机制都需要设计。
- **多租户与权限隔离**：企业场景中不同部门/角色只能检索各自权限内的文档，需要在检索阶段做 metadata 过滤。
- **延迟与成本控制**：HyDE、Multi-Query、Reranker 的多次 LLM/模型调用叠加，延迟可达数秒。需设计分级检索策略——简单 Query 走快速通道，复杂 Query 走完整管线。
- **评测与持续优化**：缺少 ground truth 标注数据，线上效果难以量化。需建立"用户反馈 → 自动标注 → 离线评测 → 模型/策略迭代"的闭环。
- **冷启动问题**：系统初期知识库空白或质量差，用户信任度难以建立。

**加分项：** 讨论 RAG 的 Fail-Safe 设计：多层降级策略（检索失败 → 提示模板 → 人工兜底）。线上监控体系——召回率/生成质量/延迟的实时监控和告警。以及 Langfuse、Phoenix Arize 等 RAG 可观测性平台的选型。

## Q12：Self-RAG 和 CRAG 等自适应检索机制的区别？什么是迭代检索（Iterative Retrieval）？与普通 RAG 有何区别？

### 考察点
考察候选人对 RAG 前沿演进方向的理解，自适应检索和迭代检索是 Agentic RAG 的基础能力，代表了从"静态管线"到"动态决策"的范式跃迁。

### 解答思路
1. 先对比 Self-RAG 和 CRAG 的设计理念和核心区别。
2. 定义迭代检索并阐述它与普通 RAG 的本质差异。
3. 串联解释这些机制如何通向 Agentic RAG。

### 参考答案
**Self-RAG vs CRAG：**

**Self-RAG（Self-Reflective RAG）** 的核心是让 LLM 在生成过程中**自主地、按需地决定何时检索、检索什么、以及如何评判检索结果**。它通过在模型输出中插入特殊的 reflection token（如 `<Retrieve>`、`<IsRel>`、`<IsSup>`、`<IsUse>`）来实现：
- `<Retrieve>`：判断当前生成的段落是否需要外部检索
- `<IsRel>`：判断检索到的文档是否与 query 相关
- `<IsSup>`：判断生成的陈述是否被检索文档支持
- `<IsUse>`：判断检索文档对生成的整体有用程度

Self-RAG 通过训练（在标注了 reflection token 的数据上微调 LM）让模型内化了"自我反思"的能力，是**模型内生**的检索决策机制。

**CRAG（Corrective RAG）** 的核心是**对检索结果做"纠错"**。它的流程是：
1. 先执行常规检索，获得候选文档
2. 用检索评估器（Retrieval Evaluator）对每个文档打分，分为"正确""错误""模糊"三类
3. 对"正确"的文档直接使用；对"错误"的文档触发 Web Search 补充检索；对"模糊"的文档混合使用（知识库结果 + Web 搜索结果）
4. 最后对组装好的上下文做"知识精炼"（Knowledge Refinement），剔除冗余和矛盾信息后送 LLM 生成

**核心区别**：Self-RAG 是**"自主决策何时检索"**（检索触发由模型内生决定），CRAG 是**"检索后的纠错优化"**（默认总是检索，但引入外部知识源纠正检索结果）。Self-RAG 的重心在前半段（要不要检索、检索是否可信），CRAG 的重心在后半段（检索结果不可信时怎么办）。

**迭代检索（Iterative Retrieval）**：指不是在生成前做一次检索就结束，而是在生成过程中**根据已生成内容的反馈，反复触发新的检索**。典型流程：
1. 初始检索 → 生成部分答案
2. 从生成的答案中识别出信息缺口或新问题 → 发起第二轮检索
3. 用新的检索结果补充/修正之前的上下文 → 继续生成
4. 重复以上步骤直到答案完整或达到最大迭代次数

**与普通 RAG 的本质区别：**
- 普通 RAG：检索 → 生成（单次管线，Pipeline 模式）
- 迭代检索：检索 ⇄ 生成（循环交互，Agent 模式）
- 普通 RAG 中 LLM 是被动的"消费者"，只消费检索结果；迭代检索中 LLM 是主动的"决策者"，通过生成来指导下一轮检索的方向。
- 迭代检索更适合多跳推理（multi-hop reasoning）、需要对答案逐步"拼接"的复杂问题。

**进化路径**：Self-RAG 和 CRAG 提供了检索的"自适应决策"能力，迭代检索提供了"多步探索"能力，二者结合构成了 **Agentic RAG** 的基础——Agent 自主规划检索步骤、执行检索、评判结果、决定是否继续检索或开始生成。

**加分项：** 提及 FLARE（Forward-Looking Active REtrieval）——在生成过程中主动预测下一句是否需要检索；IRCoT（Interleaving Retrieval with Chain-of-Thought）——将检索步骤交替插入思维链中。LangGraph 和 CrewAI 等 Agent 框架中如何编排迭代检索。对比固定步骤的 Adaptive RAG（根据 Query 复杂度路由到不同检索策略）与动态 Agent 驱动的检索决策。

## Q13：什么是 RAG？RAG、微调和长上下文模型三者的区别和适用场景分别是什么？

### 考察点
考察候选人对三种主流"知识注入 LLM"方案的本质理解，能否清晰区分"检索知识""参数知识""上下文知识"三条路径的优劣势和适用边界。

### 解答思路
1. 先简洁定义 RAG，然后定位三个方案的"知识来源"差异——这是根本。
2. 从知识更新频率、推理成本、延迟、可控性等维度做一个结构化的对比。
3. 给出各自的适用场景组合，强调三者不是互斥而是互补。

### 参考答案
RAG（Retrieval-Augmented Generation，检索增强生成）是让 LLM 在回答时先从外部知识库检索相关文档，将文档作为上下文拼入 prompt，再生成答案的技术。它的知识存储在外部向量库中，推理时才按需检索。

**三者的核心差异：知识来源不同**
- **RAG**：知识来自外部检索系统，LLM 推理时才"现查"，知识可秒级更新，外部可控。
- **微调（Fine-tuning）**：知识写进模型参数，通过训练将领域知识内化到权重中，属于"参数知识"。
- **长上下文模型**：知识直接写在 prompt 上下文里，把全部相关资料一次性塞给模型，属于"上下文知识"。

**适用场景对照表**

| 方案 | 更新频率 | 知识量 | 延迟 | 典型场景 |
|------|----------|--------|------|----------|
| RAG | 秒/分钟级 | TB 级 | 检索+推理 | 客服知识库、法律条文、新闻问答 |
| 微调 | 天/周级 | 受训练数据限制 | 仅推理 | 风格定制、特定格式输出、领域术语内化 |
| 长上下文 | 按需 | 1M token | 仅推理(但长) | 单篇论文分析、会议纪要总结、PR 全文审计 |

**最佳实践是组合使用**：用微调让模型学会领域表达习惯和输出格式，用 RAG 提供实时更新的业务知识，用长上下文处理需要全文通读的深度分析任务。

**加分项：** 讲清 RAG 解决的是"检索后的知识注入"，微调解决"模型行为适配"，长上下文解决"一次性的全文理解"。HyDE（假设文档嵌入）等技术模糊了检索与生成的边界。Fine-tuned RAG（如 RAFT）让模型同时在领域数据和检索不完美结果上训练，实现两者的深度融合。

## Q14：了解搜索系统吗？和 RAG 有什么区别？稀疏检索 vs 稠密检索的核心区别是什么？

### 考察点
考察候选人对信息检索基础的理解深度，能否将传统搜索与 RAG 做结构化对比，并对稀疏/稠密两种检索范式的数学原理和工程取舍有清楚认知。

### 解答思路
1. 先定义搜索系统，然后从目标、输入输出、评价指标三个维度与 RAG 对比。
2. 用 TF-IDF/BM25 和 Embedding 分别解释稀疏检索和稠密检索的数学逻辑。
3. 给出混合检索（Hybrid Search）的实践方案。

### 参考答案
**搜索系统 vs RAG 的区别**：传统搜索系统（如 Elasticsearch、Solr）的目标是返回一个排序好的文档列表，用户需要自己阅读文档找到答案。RAG 的目标是直接生成答案，文档列表只是中间产物。搜索系统关注的是索引效率、排序精度（NDCG、MRR），RAG 更关注答案的忠实度（faithfulness）和相关性（answer relevance）。

**稀疏检索（Sparse Retrieval）**：以 BM25 为代表，将 query 和文档都表示为高维稀疏的词袋（Bag-of-Words）向量，维度等于词典大小，绝大多数值为零。匹配依赖精确的词项重合（lexical matching），通过 TF（词频）、IDF（逆文档频率）和文档长度归一化计算相关度。优点是：可解释性强、冷启动好、对专有名词和数字精确匹配效果好。缺点是：无法处理同义词和语义改写，存在"词项失配"问题。

**稠密检索（Dense Retrieval）**：以双塔模型（Bi-encoder）为代表，用预训练语言模型将 query 和文档分别编码到低维稠密向量空间（如 768 维），通过向量距离度量语义相似度。优点是：捕捉语义相似，能召回字面不匹配但含义相关的文档，抗噪声能力强。缺点是：需要大量训练数据、对少见领域泛化差、可解释性弱。

**混合检索**：实践中通常结合两者（Hybrid Search），先用稀疏检索做关键词召回，再用稠密检索做语义召回，通过 RRF（Reciprocal Rank Fusion）融合两路结果后送 re-ranker 精排。Elasticsearch 8.x 原生支持这种架构。

**加分项：** 学习型稀疏检索（Learned Sparse，如 SPLADE）通过学习得到稀疏但带语义的权重表示，是两者的折中。对比 DPR、ANCE、TAS-B 等稠密检索训练策略的区别。混合检索的融合策略除了 RRF，还有线性加权、LambdaMART 等。

## Q15：OCR 结果有噪声或错误时，你是怎么做纠错或提升解析质量的？

### 考察点
考察候选人对文档解析环节的工程实践能力，OCR 噪声是真实 RAG 系统的常见痛点，能否给出分层次、可落地的纠错方案。

### 解答思路
1. 先定位 OCR 错误的典型类型（字符级、结构级、语义级），分类是纠错的前提。
2. 从预处理和后处理两个方向给出具体方案，优先低成本手段。
3. 给出一个多层级流水线的架构和效果取舍。

### 参考答案
OCR 噪声通常分为三类：**字符级错误**（形近字误识别，如"已→己"、"0→O"）、**结构级错误**（段落合并错误、表格行列错乱、页眉页脚混入正文）、**语义级错误**（专业术语、数学公式识别失败）。

**纠错策略分三层**：

**第一层：预处理优化**
- 选择针对语言和文档类型优化的 OCR 引擎（中文用 PaddleOCR，表格用 Table Transformer + OCR 联动）。
- 图像预处理：去噪、倾斜校正、对比度增强，PDF 优先走数字解析（PyMuPDF）而非统一截图 OCR。
- 对扫描件做区域检测后再分类 OCR，避免将图表区域当作文本。

**第二层：后处理纠错**
- **规则 + 统计纠错**：对 OCR 输出做中文拼写检查（如 pycorrector、SymSpell），基于 N-gram 语言模型纠正形近字。
- **LLM 纠错**：将原始 OCR 结果 + 上下文送入 LLM，用 few-shot prompt 让模型根据语义合理性纠正错误。格式化的表格/列表数据，要求 LLM 逐行输出验证。
- **结构化恢复**：用正则或 layout parser 重建段落边界和阅读顺序，特别是多栏排版。

**第三层：RAG 环节兜底**
- 保证 chunk overlap，降低切断处的信息损失。
- 查询端做 Query Expansion，生成同一问题的多个表述变体来提高召回，弥补文档端的 OCR 缺陷。

**加分项：** 提及 Nougat/Donut 等端到端的文档理解模型（跳过 OCR 直接看图生成 markdown）。OCR-free 路径如 ColPali（直接用 ViT 对页面截图做 embedding 检索）。表格 OCR 纠错专用方案（用 LLM 对提取的表格做交叉验证）。

## Q16：多模态检索中，图像和文本向量不在同一空间时，如何实现对齐？

### 考察点
考察候选人对多模态嵌入对齐方法论的掌握程度，这是多模态 RAG 的核心技术点。

### 解答思路
1. 先解释为什么图像和文本向量不在同一空间（编码器独立预训练），以及为什么需要对齐。
2. 介绍三类对齐方法：联合训练（CLIP 类）、映射桥接、共享编码器。
3. 给出实际选型建议和验证方法。

### 参考答案
图像和文本向量不在同一空间是因为它们通常由各自独立的编码器生成：图像用 ViT/ResNet，文本用 BERT/T5。即使都映射到 768 维，由于训练目标和数据分布不同，两套向量在空间中的几何结构差异巨大，直接进行跨模态相似度计算（如余弦相似度）毫无意义。

**实现对齐的三种主流路径**：

**1. 联合训练（Contrastive Learning）**：最经典的是 CLIP（Contrastive Language-Image Pre-training），用 4 亿对图文对做对比训练，让匹配的图文对在向量空间中互相拉近，不匹配的互相推远。训练后 image encoder 和 text encoder 输出天然在统一语义空间。这是最优方案，但需要大规模图文配对数据和训练资源。

**2. 映射桥接（Adapter/Mapping Network）**：当图像 encoder 已固定（如用预训练的 DINOv2 做语义搜索），可以在其上挂一个可训练的 MLP 或线性投影层，将图像向量映射到文本 embedding 空间。这个 adapter 只需少量图文配对数据微调。

**3. 共享编码器（Unified Encoder）**：让同一个模型处理多种模态，如 ImageBind（六模态共享空间）、UniVL、BLIP-2（用 Q-Former 桥接），推理时各模态输出自然可比较。

**选型原则**：如果兼容性不是问题，直接用 CLIP 系（OpenCLIP、SigLIP、EVA-CLIP）是最快路径。如果已有特定领域的图像 encoder 不想换，训练一个简单的线性 adapter + 少量配对数据即可。验证时要看 Image-to-Text 和 Text-to-Image 的 Top-K 召回率。

**加分项：** 提及通过对比学习在特定垂直领域（医学影像、工业质检）构造领域 CLIP 的过程。讨论 BLIP-2 Q-Former 桥接的设计哲学。说清为什么要用 InfoNCE Loss 而非简单的 MSE 做跨模态对齐训练。

## Q17：长文档为什么一定要切 chunk 再做向量化？不切会有什么问题？

### 考察点
考察候选人对 embedding 模型特性和 RAG 检索机制的底层理解，能否从数学和信息工程两个角度解释 chunking 的必要性。

### 解答思路
1. 从 embedding 模型的最大输入 token 限制和"语义稀释"效应切入。
2. 解释长文本 embedding 的检索精度问题和成本问题。
3. 补充 chunking 带来的额外好处（粒度可控、引用精准）。

### 参考答案
长文档必须切 chunk 再做向量化，主要有三个层面的原因：

**1. Embedding 模型的硬限制**：所有 embedding 模型都有最大输入 token 限制（如 text-embedding-3-large 为 8191 token，BGE-M3 为 8192 token）。超过限制的文本无法直接向量化，必须截断或切分。

**2. 语义稀释效应（更核心的问题）**：即使模型支持超长输入，把一整本书嵌入到一个向量里也是不合理的。Embedding 模型本质上是将文本"压缩"到一个固定维度的向量（如 768 维），文本越长，每个维度的信息承载压力就越大，最终产生的向量倾向于捕捉文档的宏观主题而丢失细节信息。这就是"语义稀释"——你问文档中某一段的具体事实，但整篇文档的向量只表达了"这是一篇关于 XX 领域的文章"，粒度太粗。

**3. 检索精度的信息论解释**：RAG 检索的核心目的是从包含特定事实的小片段中找到答案线索。如果把整个文档笼统地向量化，query 即使高度相关，相似度分数也无法告诉你答案具体在文档的哪一页、哪一段，LLM 还是得到了一整本书，长上下文模型能处理，但 token 成本高昂且可能迷失在无关内容中。

**不切的实际后果**：相似度分数区分度大幅下降（长文档向量趋于均值化），检索到的文档包含大量无关信息，LLM 容易被噪声干扰（"Lost in the Middle"效应），token 成本和延迟都线性增长。

**加分项：** 讲清 chunk 大小是检索粒度的核心杠杆——chunk 越小，检索越精准但丢失上下文；chunk 越大，语义完整但定位模糊。实践中结合 Small-to-Big 策略（小 chunk 检索，大窗口返回）和 Multi-Vector 方案（每个 chunk 生成摘要向量 + 原文向量混合检索）。ColBERT 的 Late Interaction 机制做 token 级匹配，替代传统 chunking 思路。

## Q18：余弦相似度和欧氏距离在高维空间中的差异是什么？实际怎么选？

### 考察点
考察候选人对向量检索底层数学原理的理解，这是选 embedding 模型和调检索参数的必备基础。

### 解答思路
1. 先定义两个指标的计算公式和几何含义。
2. 结合"高维空间的维度诅咒"解释它们在实践中的行为差异。
3. 给出选型指南——场景驱动而非理论偏好。

### 参考答案
**定义差异**：
- **余弦相似度**：衡量两个向量方向的一致程度，计算公式为 cos(θ) = (A·B) / (‖A‖ × ‖B‖)，取值范围 [-1, 1]。它只关心"角度"，不关心"长度"。
- **欧氏距离**：衡量两个向量在空间中的直线距离，计算公式为 d = √(Σ(Ai - Bi)²)，取值范围 [0, +∞)。它同时受方向和长度的双重影响。

**高维空间中的关键差异**：

1. **向量长度的干扰**：文本 embedding 的长度（范数）与实际语义信息量有关——高频词的 embedding 通常范数更大。欧氏距离会被向量长度主导，两个语义无关的"长向量"可能比语义相关的"短向量"欧氏距离更近。余弦相似度消除了长度差异，只比较方向。

2. **维度诅咒**：随着维度增加，两个随机向量的欧氏距离趋于均等（集中现象），区分度下降。余弦相似度受此影响较小，因为它在单位超球面上计算，维度增加时对比度保持更好。实践中在 768+ 维空间，余弦相似度通常能给出更有区分度的排序。

3. **归一化后的等价性**：当所有向量都经过 L2 归一化（映射到单位超球面），余弦相似度和欧氏距离存在单调对应关系：d² = 2(1 - cos(θ))，此时两者排序等价。

**选型指南**：
- 用余弦相似度，当你不确定 embedding 模型是否做了归一化输出时（多数主流模型如 OpenAI 的 embedding 已归一化，此时两者等价）。
- 用欧氏距离，当你需要向量长度作为信号（如图像检索中亮度/对比度信息），或你的向量在训练时就使用了欧氏距离作为优化目标。
- 实际工程中，只要 embedding 是归一化的，选哪个没区别；需要确认的是向量数据库的索引类型支持哪种度量（如 Milvus 的 IVF_FLAT 支持 L2 和 IP，HNSW 支持 L2 和余弦）。

**加分项：** 从训练侧解释——如果 embedding 模型训练时使用 cosine loss，推理时必须用 cosine 才能与训练一致。说清内积（IP/点积）与余弦的关系。对比马氏距离在高维的适用场景。量化下不同度量在百万级向量库中的检索效率差异。

## Q19：文档发生局部更新时，如何做增量索引而不是全量重建？

### 考察点
考察候选人对向量数据库索引更新机制的工程理解，增量索引是生产级 RAG 系统的基础运维能力，直接关系系统的实时性和资源效率。

### 解答思路
1. 先分析"局部更新"对向量索引的影响范围，区分新增、修改、删除三种操作类型。
2. 给出增量索引的核心流程设计——包括变更检测、最小更新范围计算、索引原子操作。
3. 补充索引一致性和性能优化方面的工程考量。

### 参考答案
增量索引的核心思路是：**只对发生变化的文档 chunk 重新 embedding 和入库，不动其他数据**，避免全量重建的高昂计算开销。具体实现分为三个环节：

**一、变更检测机制**
在文档管理层记录每个文档的 hash 指纹（如 MD5/SHA256）和最后修改时间戳。当检测到 hash 变化时，标记该文档为"待更新"。常用方案包括：定时轮询扫描 + 哈希比对（适合批处理），或接入上游系统的变更通知（Webhook/消息队列，适合实时场景）。

**二、增量更新操作分类处理**
- **新增**：直接对新增文档做 chunking → embedding → 写入向量库，同时记录 doc_id 与 chunk_id 的映射关系。
- **修改**：先根据 doc_id 查出该文档的所有旧 chunk，批量删除后再写入新 chunk。向量数据库（如 Milvus）支持按 metadata 过滤批量删除：`collection.delete(filter="doc_id == 'xxx'")`。
- **删除**：仅需按 doc_id 删除对应 chunk，无需做新 embedding。

**三、索引一致性保证**
关键是要**原子性地完成"删旧"与"写新"**——如果先删后写中间有请求进来，可能导致"查不到该文档"的短暂降级。推荐方案是先写入新 chunk（带版本号标记），再删除旧 chunk，最后更新版本号，保证对外始终有数据可用。对高并发场景，可配合读写分离或双 Buffer 策略。

**资源考量：** 增量索引的 embedding 调用量和计算资源消耗与变更量成正比，而非文档总量。对于一个 100 万文档的知识库，如果每天仅 0.1% 发生变更，增量方案比全量重建节省 99.9% 的成本。

**加分项：** 讨论 ES 的近实时（NRT）刷新机制在向量索引中的类比；Milvus 的 Data Manipulation Language（DML）支持和 Upsert 语义；如何利用 Kafka/Flink 构建实时增量索引 Pipeline。变更影响面分析：修改一个文档可能导致需要重建与该文档语义关联的 FAQ 索引或知识图谱关系。

## Q20：向量检索中 Top-K 设置过大或过小分别会带来什么问题？

### 考察点
考察候选人对向量检索参数调优的敏感度，Top-K 是 RAG 系统中看似简单但影响面极大的超参数，直接左右召回质量、延迟和成本。

### 解答思路
1. 分别分析 Top-K 过小和过大的问题表现和根因。
2. 给出不同场景下的推荐 K 值范围。
3. 说明 K 值如何与 Rerank 配合，形成"宽召回 + 精排序"的经典架构。

### 参考答案
**Top-K 过小（如 K=1~3）的问题：**

1. **召回不全（低 Recall）**：正确答案可能排在相似度第 4-5 位，如果只取 Top-3 会直接丢失。这在多文档答案分散、Query 表达不够精确时尤其突出。

2. **多角度信息缺失**：很多问题需要综合多个片段的互补信息（如"A 方案的优缺点"分布在两个 chunk 中），Top-K 太小会导致 LLM 只能看到部分信息，生成不完整的答案。

3. **单一来源偏差**：Top-1/2 可能都是同一文档的相邻 chunk，缺乏多样性，LLM 无法做交叉验证。

**Top-K 过大（如 K=50~100）的问题：**

1. **噪声淹没信号（低 Precision）**：大量低相关度内容挤占上下文窗口，LLM 被迫在大量噪音中寻找有用信息，容易出现 Lost in the Middle 现象——关键信息在上下文中段被模型"忽略"。

2. **延迟与成本暴涨**：更多 chunk 意味着更长的 prompt（token 量翻倍）、更慢的推理速度、更高的 API 费用。同时 Reranker 要对更多候选打分，计算量也随之增加。

3. **幻觉诱发**：不可靠的 chunk 越多，模型混入幻觉的概率越大——"检索到的"信息在形式上都是"权威来源"，模型难以分辨其可信度高低。

**推荐实践：**
- **向量召回阶段**：K 取 20-50（宽召回），保证 Recall 充分
- **Rerank 精排后**：截断至 5-10 个片段送入 LLM（窄输入），兼顾覆盖面和上下文精炼度
- 配合 MMR（最大边际相关性）去重，避免 K 个结果中 80% 内容雷同
- 动态 K 值：根据 Query 复杂度（简单问题 K 小、需要多文档推理 K 大）或 Token 预算自适应调整

**加分项：** 讨论 Recall@K 曲线——通常在 K=10-20 后 Recall 增长进入平台期，是选择 K 的经验参考。多路召回（向量 + BM25 + 知识图谱）各自的 K 值如何取、融合后的总 K 如何控制。LangChain/LlamaIndex 中 RetrievalQA 链的 k 参数底层实现。

## Q21：Agent 一般在什么阶段去查询向量知识库？通过什么方式去查询？查询知识库的工具函数其标准输入和输出是什么？

### 考察点
考察候选人对 Agent 与 RAG 结合点的系统理解，能否清晰描述 Agent 如何将知识库检索作为一个可调用的工具（Tool/Function）编排到推理循环中。

### 解答思路
1. 先定位 Agent 调用知识库的时机——在 ReAct/思考-行动-观察循环中的哪个节点。
2. 说明 Agent 调用知识库的工具（Tool）形式及其与普通 RAG 管线的区别。
3. 给出工具函数的标准入参/出参设计。

### 参考答案
**查询时机**：Agent 通常在 **"思考-行动"循环中的行动（Action）阶段** 查询知识库。以 ReAct 模式为例，流程为：LLM 收到用户问题 → 思考（Thought：我需要查询 XX 相关信息）→ 行动（Action：调用 `search_knowledge_base` 工具，传入改写后的查询语句）→ 观察（Observation：收到检索返回的上下文片段）→ 根据结果决定继续检索还是直接生成最终答案。Agent 还可能基于第一次检索结果的信息缺口，发起**第二轮甚至多轮检索**（迭代检索/多跳推理）。

**查询方式**：Agent 不是直接调用 embedding 模型的，而是通过**一个封装好的 Tool Function** 来查询知识库。这个 Tool 内部封装了 Query 改写 → Embedding → 向量检索 → Rerank 的完整管线，对外暴露一个简洁的函数接口。Agent 通过 Function Calling 协议（OpenAI 的 tool_calls / Anthropic 的 tool_use）来调用它。

**工具函数的标准输入和输出设计：**

- **输入（Input）**：
  ```json
  {
    "query": "用户问题或 Agent 改写后的查询语句（必填，string）",
    "top_k": 5,
    "filters": { "category": "技术文档", "date_range": "2024-01-01,2024-12-31" },
    "search_type": "hybrid"
  }
  ```
  核心参数：`query`（检索查询文本）、`top_k`（返回片段数）、`filters`（可选的 metadata 过滤，如部门、文档类型、时间范围）、`search_type`（可选，指定检索模式如纯向量/混合/关键词）。

- **输出（Output）**：
  ```json
  {
    "results": [
      {
        "content": "片段的文本内容",
        "score": 0.92,
        "metadata": {
          "doc_id": "doc_123",
          "title": "故障处理手册 v2.3",
          "section": "3.2 网络故障排查",
          "page": 15,
          "updated_at": "2025-12-01"
        }
      }
    ],
    "total_found": 42,
    "search_type_used": "hybrid"
  }
  ```
  返回结果是一个 dict/list 结构，包含检索到的文档片段列表、每个片段的文本内容、相似度分数、来源元数据、以及检索统计信息。Agent 拿到这个输出后，会将其拼入下一轮 LLM 调用的上下文中做推理。

**加分项：** 设计"检索质量自评"输出字段——Tool 返回时附带一个 `quality_flag`（如召回置信度 high/medium/low），帮助 Agent 决定是信任结果还是触发补充检索。对比 OpenAI Assistants API 的 file_search tool 与自建 Tool 的优劣。Agent 的多工具编排——知识库检索与 Web Search、数据库查询、代码执行等工具的并行/串行调用策略。

## Q22：系统如何实现图像识别等多模态功能？为什么不直接使用多模态大模型？

### 考察点
考察候选人的系统架构设计能力和工程成本意识，能否在"功能完备"和"资源可控"之间做出理性权衡，而非一味追求最前沿方案。

### 解答思路
1. 先描述"非多模态 LLM + 预处理管线"的工程实现路径。
2. 从延迟、成本、可控性、稳定性四个维度解释为什么不直接用多模态大模型。
3. 给出两者结合的渐进式架构演进建议。

### 参考答案
**实现方案：非多模态 LLM + 图像预处理管线**

在没有多模态大模型的情况下，系统通过**管线编排**实现图像理解：

1. **图像解析与信息提取**：使用专门的视觉模型做 OCR 文字识别（PaddleOCR/Tesseract）、物体检测（YOLO/RT-DETR）、场景分类、图表解析（Table Transformer + 结构化提取），将图片中的视觉信息转化为结构化文本描述。

2. **文本化存储与索引**：将提取出的文本（如 OCR 结果、图片描述、检测到的物体标签）写入知识库的对应 chunk 中，与文档正文一起参与 embedding 和检索。例如一张"系统架构图"会被解析为"该图描述了微服务架构，包含 API Gateway、订单服务、库存服务、消息队列四个组件"。

3. **RAG 检索时正常召回**：用户查询时，如果问题涉及图片内容，检索到的 chunk 中已经包含了预处理阶段生成的文本描述，LLM 就能基于文本理解图片信息。

**为什么不直接使用多模态大模型（如 GPT-4V/Gemini Vision）：**

1. **成本过高**：多模态模型的推理成本远高于纯文本模型（通常 5-20 倍），如果对所有图片做实时分析，成本难以控制。

2. **延迟不可控**：多模态模型推理延迟通常在 2-5 秒以上，而预处理方案中信息已在入库时提取完毕，检索仅需毫秒级。

3. **输出可控性差**：预处理管线中每个视觉模型做确定的单一任务（OCR/检测），输出格式固定、可验证。多模态 LLM 的"看图说话"输出不稳定——同一张图每次描述可能有差异，影响下游 RAG 召回的一致性。

4. **离线预处理更符合 RAG 架构**：RAG 的优势在于"离线建库、在线检索"，图片理解天然适合离线阶段完成，在线时只需文本检索即可。

**建议的架构演进**：预处理管线覆盖 80% 标准图片类型（纯文字截图、表格、流程图），多模态大模型按需兜底——当管线识别出图片属于复杂类型（如手绘草图、复杂图表）时，触发多模态 LLM 补充分析，结果缓存后用于后续检索。

**加分项：** 对比 ColPali 等视觉-语言联合检索方案（直接用 ViT 对页面截图做 embedding，跳过 OCR）；了解 Meta 的 Nougat/Donut 等端到端文档理解模型；多模态预处理 Pipeline 的质量评估——图片描述的准确率和召回率如何量化；图片描述与原始文档文本的 semantic consistency 校验。

## Q23：多模态预处理中，图片在 RAG 系统里是如何向量化检索的？多模态预处理环节的技术难点是什么？

### 考察点
考察候选人对多模态 RAG 技术链路的完整理解，从图片的向量化方式到预处理环节的工程挑战，覆盖方案选型和落地细节。

### 解答思路
1. 先描述图片在 RAG 中的三种主流向量化检索方案。
2. 从精度、一致性、效率三个维度剖析预处理环节的技术难点。
3. 给出针对各难点的工程缓解措施。

### 参考答案
**图片的向量化检索方案（三种主流路径）：**

1. **文本桥接方案（最常用）**：先用 OCR + 视觉模型将图片内容转化为文本描述（Captioning），再对文本做 embedding 存入向量库。检索时 query 的文本向量匹配的是图片的"文本替身"。优点是兼容现有文本 RAG 基础设施，缺点是图片到文本的信息有损——复杂布局和视觉细节可能丢失。

2. **CLIP 多模态联合向量方案**：使用 CLIP/BLIP/SigLIP 等模型的 image encoder 直接将图片编码为向量，存入向量库。检索时用对应 text encoder 将 query 编码为同空间向量做相似度匹配。优势是保留了视觉语义信息（颜色、布局、风格也能匹配），但要求图文向量在训练时已对齐。

3. **混合索引（Multi-Vector）方案**：为每张图生成多个向量——CLIP 图像向量（捕捉视觉语义）+ 文本描述向量（捕捉文字内容）+ OCR 文本向量（捕捉精确文字），在检索时多路融合。LlamaIndex 的 Multi-Modal Vector Store 支持这种模式。这是覆盖率和精度最高的方案，但存储和计算开销最大。

**多模态预处理的技术难点：**

1. **图文对齐精度问题**：OCR 识别错误、Caption 描述偏差、表格/公式结构解析失败，都会导致"图片内容正确但文本描述失真"，下游 RAG 召回时找不到或找错。解决：引入 LLM 做描述质量核验 + 关键字段交叉验证；对表格/公式类型使用专用解析器而非通用 OCR。

2. **多模态内容的一致性维护**：一张图可能涉及多种信息维度（图表数据 + 标注文字 + 视觉布局意图），预处理需要同时保真这些维度。但不同解析模型的输出格式不同，如何统一组织成 chunk 结构是难点。解决：定义多模态文档的统一 `ContentBlock` 结构，包含 `text_section`、`table_section`、`image_description`、`layout_info` 等字段。

3. **处理效率与复杂度权衡**：解析一张复杂排版 PDF 页面可能需要调用 3-5 个模型（布局检测 + OCR + 表格识别 + Caption + LLM 纠错），在万级文档规模下预处理时间和成本可能不可接受。解决：对文档分级——简单文本页走轻量管线，复杂图表页走完整管线；建立解析结果缓存，避免重复处理。

4. **检索粒度不一致问题**：文本文档可以按段落切 chunk，但图片是一个不可分割的整体。如何让"图片级"的检索粒度和"段落级"的文本检索粒度在混合检索时协调？解决：为图片 chunk 生成多个"锚点描述"（不同角度的文本描述），分别对应整图概述、关键元素、数据结论等，提高命中概率。

**加分项：** 对比 ColPali（Vision-Language Late Interaction）与传统 Preprocessing 方案在图文档检索上的效果差异。多模态文档解析流水线的工程实现——Unstructured、LlamaParse、Marker 等开源工具的技术原理和选型对比。评测方法：图文对齐的准确率评测框架（判断提取的文本描述是否忠实于原始图片内容）。

## Q24：如何杜绝跨场景召回相似步骤的问题，具体实现方式是什么？

### 考察点
考察候选人对 RAG 检索精度优化的深入理解，特别是多场景、多领域知识库共存的工业级场景中，如何通过上下文约束和结构化过滤避免"张冠李戴"式的误召回。

### 解答思路
1. 先定义"跨场景召回相似步骤"的具体问题表现和根因。
2. 提出分层解决方案：metadata 过滤、上下文注入、query 约束。
3. 给出完整的实现链路和防止回退的设计要点。

### 参考答案
**问题定义**：当知识库中包含多个业务场景的相似操作步骤时（如"激活设备"在智能家居场景和工业物联网场景步骤完全不同），向量检索仅凭语义相似度无法区分场景，导致把场景 A 的操作步骤错误地用在了场景 B 的问答中。根因是：步骤类文本在语义空间中高度聚类，但它们的 **"适用上下文"信息（场景、设备型号、版本号）并未参与相似度计算**。

**解决方案：三层过滤防线**

**第一层：Metadata 过滤（粗暴但有效）**
在 chunk 入库时为每个片段打上场景标签：`{ "scene": "智能家居", "device": "温控器-T200", "version": "3.2" }`。检索时由上游的意图识别或路由模块先判定当前对话的场景归属，将场景标签作为 `filter` 参数传入向量检索。Milvus/Qdrant/Pinecone 均支持 metadata 过滤 + 向量检索的混合查询，在扫描候选集前就剔除不同场景的 chunk。

**第二层：Chunk 上下文预注入**
切片时将场景标识信息**显式写入 chunk 文本中**，而不是仅存在 metadata 里。例如原始文本是"步骤一：长按电源键 5 秒"，处理后变为 `[场景：智能家居-温控器T200] [版本 v3.2] 步骤一：长按电源键 5 秒`。这样即使 metadata 过滤失效（如上游路由误判场景），embedding 向量中也包含了场景区分信息，语义相似度计算时会天然倾向于同场景的内容。

**第三层：LLM Prompt 中的场景锚定**
在最终 Prompt 中明确标注当前场景上下文，并要求 LLM 在回答步骤类问题时验证来源的适用性：

```
当前对话场景：智能家居，设备型号：温控器-T200，固件版本：v3.2。
请仅使用标记为上述场景的文档片段回答问题。如果检索到的操作步骤来自其他场景或版本，即使步骤描述相似，也不得采用。
```

**完整实现链路：**
```
用户输入 → 意图识别/场景路由（判定当前场景）→ Query 改写（注入场景关键词）
→ 向量检索（带 metadata filter）→ Rerank（结合场景匹配度打分）
→ LLM 生成（Prompt 中锚定场景上下文）
```

**关键设计点**：
- 意图路由的准确率是整条链路的上游瓶颈——如果路由错判了场景，后续过滤全白费。需要在路由层做置信度兜底，低置信时走"宽松过滤 + LLM 自行判别"的容错模式。
- 场景划分粒度需要业务侧参与定义，粒度过粗（如只分"家居"和"工业"）仍可能产生子场景混淆；粒度过细则 metadata 过度碎片化，维护成本高。
- 版本号管理：如果同一个场景在不同版本中存在互斥的操作步骤（如 v2.0 和 v3.0 的升级步骤完全不同），版本号必须作为一级过滤条件。

**加分项：** 讨论 Graph RAG 在处理跨场景问题的优势——知识图谱天然用实体类型和关系约束了召回范围。多租户 SaaS 场景中的场景隔离实现（与权限过滤联动）。利用 Embedding 距离分布监控跨场景误召回——当同一个 Query 召回两个不同场景的高分 chunk 时触发告警，说明场景边界定义不足。

## Q25：介绍评估精度和召回率所采用的框架，以及召回率的具体计算细节？

### 考察点
考察候选人对 RAG 系统评测体系的系统掌握程度，能否区分检索端和生成端评测的不同框架选型，以及对 Context Recall 指标从原理到公式的完整理解。

### 解答思路
1. 先区分评测的两大维度（检索端与生成端），列举各自的代表性框架。
2. 以 RAGAS 为主线详解 Context Recall 的计算原理和公式推导。
3. 补充其他框架的竞品对比与选型建议。

### 参考答案
RAG 系统的精度和召回率评测采用分层框架，按评测对象分为两条线：

**检索端评测框架**：聚焦"检索到的文档是否包含答案"，常用指标为 Recall@K、MRR、NDCG@K、Hit Rate。工具层面，BEIR（Benchmarking IR）是检索领域最权威的基准评测框架，提供 18 个多样化数据集和统一评测协议；MTEB（Massive Text Embedding Benchmark）则用于评测 embedding 模型本身的检索能力。工程中常用 Ragas 的 Context Relevancy 和 Context Recall 指标做自动化评测。

**生成端评测框架**：以 **RAGAS**（RAG Assessment）为行业标准，此外 Deepeval 和 TruLens 也提供类似指标集。RAGAS 的核心思想是将评测拆分为原子化、可计算的子指标，每个指标通过 LLM-as-a-Judge 自动打分。

**Context Recall（召回率）的具体计算细节：**
RAGAS 的 Context Recall 衡量的是"标准答案中的信息，检索到的上下文覆盖了多少"。计算分三步：

1. **答案拆解（Claim Extraction）**：用 LLM 将标准答案拆分为独立的事实原子陈述。例如标准答案"猫咪抓沙发可以用猫抓板和驱避剂"被拆为 claim1="猫抓板可防止猫咪抓沙发"、claim2="驱避剂可防止猫咪抓沙发"。
2. **归因判定（Attribution）**：对每个 claim，用 LLM 判断是否能从检索到的上下文中推断出来。判定结果为"可归因"（attributed）或"不可归因"（not attributed）。
3. **公式计算**：`Context Recall = |attributed_claims| / |total_claims|`。值域 [0, 1]，1 表示标准答案所需的所有信息都已被成功召回。

RAGAS 的 Context Precision 则是衡量"检索到的上下文中，真正与答案相关的比例"，用 Precision@K 结合加权排名计算——相关文档排名越靠前权重越高。两者配合使用：Recall 看"找全了没有"，Precision 看"找的准不准"。

**与其他框架的对比**：Deepeval 的 Contextual Recall 使用相似逻辑但额外引入了权重机制；TruLens 的 Groundedness 指标侧重于答案是否基于上下文（忠实度视角而非召回率视角）；LangSmith 提供端到端的数据集管理和评测流水线，底层可接入 RAGAS 或自定义 evaluator。工程中常将 RAGAS 作为离线回归评测的指标集，Deepeval 用于 CI/CD 流水线集成。

**加分项：** 介绍 RAGAS Context Recall 的 LLM 判定 prompt 模板设计细节（如何提取 claims、如何做 entailment 判定、Few-shot 示例构造）；对比 Context Recall 与 Answer Correctness 的区别——前者只看覆盖，后者还看语义一致性；提及人工标注中 Cohen's Kappa 系数用于衡量标注一致性，以保证自动化指标可信度；工程实践中 Context Recall 阈值一般设在 0.7-0.8 以上才算合格。

## Q26：代码助手在代码检索时，如何高效找到与问题相关的依赖并提供给大模型？现阶段为何少有框架做代码依赖相关的优化工作？

### 考察点
考察候选人对代码 AI 场景的工程理解深度，能否从 AST 解析、依赖图构建、检索策略三个层面给出可落地的技术方案，并对当前行业现状做出理性归因分析。

### 解答思路
1. 先阐述代码依赖检索的技术方案（AST 解析 → 依赖图构建 → 智能剪枝与注入）。
2. 分析现阶段少有框架投入该方向的主要原因（技术复杂、ROI 不确定、LLM 能力兜底）。
3. 给出依赖检索的设计权衡与未来演进方向。

### 参考答案
**高效找到代码依赖的技术方案：**

1. **AST 解析与符号提取**：对代码仓库做静态分析，用 tree-sitter 或 Language Server Protocol（LSP）解析 AST，提取函数定义、类定义、import/require 语句、全局变量引用等符号信息。建立符号到文件位置的映射索引，支撑精确跳转。tree-sitter 支持 40+ 语言，是当前最通用的跨语言方案。

2. **依赖图构建**：基于符号引用关系构建有向依赖图（Dependency Graph），节点为函数/类/模块，边为调用关系。用拓扑排序或 BFS 从问题相关的入口函数开始，沿调用链向外扩展 N 层（通常 2-3 层），收集直接和间接依赖的代码片段。

3. **智能剪枝与上下文预算分配**：依赖链可能很长（入口函数的调用链包括几百个节点），需要剪枝策略。方案包括：按调用频率（高频调用优先保留）、按文件名/路径相似度（同模块内优先）、按最近修改时间（热点代码优先）、LLM 驱动的相关性粗筛（用小模型快速判断每个依赖节点是否与问题相关）。最终在有限 token 预算内，优先注入高价值依赖。

4. **分层注入策略**：将直接依赖（被提问函数调用的函数定义）作为第一层注入 prompt，间接依赖作为备选；让 LLM 在推理时按需请求展开更深层依赖，实现 Agent 式的按需检索。

**为何少有框架做依赖优化：**

- **多语言适配成本极高**：每种编程语言的语法、模块机制、依赖解析方式完全不同，要覆盖 Python/JS/Java/Go/Rust/C++ 等主流语言，开发和维护成本呈指数增长。仅依赖解析器层面，就需要为每种语言适配不同的 AST 工具和包管理机制。
- **LLM 自身能力提供了基线兜底**：现代强模型（如 Claude、GPT-4）对常见库和框架的 API 已有很强的参数知识，许多依赖信息模型已经"知道"，依赖检索的边际收益场景有限——真正因缺少依赖上下文导致错误的 case 占比不高。
- **工程 ROI 不清晰**：依赖检索带来的准确率提升可能只有几个百分点，但引入的延迟（AST 解析 + 图遍历 + LLM 相关性判断）和系统复杂度显著增加。团队倾向于优先解决更痛的幻觉、上下文窗口管理、多文件编辑等核心问题。
- **代码检索的粒度难题**：依赖链上哪些函数真正有用很难自动判定——有些函数虽然被调用，但往往是通用工具函数（如 logger、validator、error wrapper），注入反而浪费宝贵 token。
- **生态割裂**：代码助手领域各家（GitHub Copilot、Cursor、Sourcegraph Cody）都在封闭研发，依赖分析常作为核心壁垒而非开源共享，缺少统一的依赖分析标准和可复用组件。

**加分项：** 提及 GitHub Copilot 的相邻窗口策略（邻接文件作为隐式依赖上下文，通过文件 proximity 近似依赖关系）；Sourcegraph Cody 的上下文工程实践（依赖注入 + 手动 @-mention 机制）；Repo-level RAG 中使用 Graph RAG 编码代码依赖关系的学术探索；SWE-bench 评测中 repo-level context 构造策略对效果的决定性影响；Call Graph 的静态分析精度与动态分析（运行时调用链）的选择权衡。

## Q27：不同数据表量级下，Text2SQL 的技术选型差异是什么？

### 考察点
考察候选人对 Text2SQL 场景的分级工程思维，能否根据数据规模做出合理的技术栈取舍，而非一刀切地选择某种方案。

### 解答思路
1. 按表数量和数据量将场景分为三个量级，分别阐述技术选型。
2. 每个量级聚焦核心矛盾：schema 信息的组织方式、检索策略、生成方案。
3. 补充跨量级演进的迁移路径。

### 参考答案
Text2SQL 的技术选型与数据表量级强相关，按规模分为三个梯级：

**第一级：小规模（1-10 张表，每表 < 50 列）**
核心矛盾是 SQL 语法正确性和业务语义对齐。方案：**Prompt Engineering + Few-shot**。将全部 DDL（CREATE TABLE 语句）、字段注释、每表 3-5 行示例数据直接写入 prompt，配合 3-5 个同 schema 上的问答 SQL 对作为 few-shot 示例。GPT-4/Claude 等强模型可直接胜任，无需引入检索步骤，因为 schema 信息完全在上下文窗口内。这是 Demo 阶段和简单业务的最优解，延迟最低。

**第二级：中等规模（10-100 张表，含部分宽表）**
schema 总 token 量超过单次上下文窗口或推理成本很高。核心矛盾是 **Schema Linking——如何从 100 张表中快速定位与问题相关的那几张表**。方案：**检索增强 + 分步推理**。用 embedding 对每张表的 DDL + 注释做向量化建立表级索引，Query 来时先做表召回（Table Retrieval，Top-3~5 张表），再将候选表的 DDL + 少量相关行数据注入 prompt 生成 SQL。常用中间表示（Intermediate Representation，如 SemQL 或自定义 DSL）来降低 SQL 生成难度。DIN-SQL 的分步方案（schema linking → classification → SQL generation → self-correction）在这个量级效果最好。

**第三级：大规模（100+ 张表，千级列，企业数据仓库场景）**
核心矛盾是**信息过载 + 复杂关联**——表之间有复杂的 join 关系，用户问题常涉及多表联查。方案：**多级检索 + 微调 + Agent 编排**。流程分四层：(1) 表级检索（Table Retrieval）→ (2) 列级检索（Column Retrieval，用自然语言描述匹配具体字段）→ (3) Join 路径规划（用外键关系图做路径搜索）→ (4) SQL 生成。此量级必须引入微调（在领域 SQL 数据上微调 SQLCoder 类模型），因为 prompt 示例不足以覆盖复杂 join 模式。同时引入 SQL 执行后自纠错循环——执行 SQL，若报错或结果不合理，将错误信息反馈给 LLM 修正。Agent 编排实现多步推理：先查表结构 → 生成子查询 → 组合 → 执行 → 纠错。

**选型核心原则**：schema 能在 prompt 内完整展示 → 直接 prompt；需要选表 → 检索增强；表关系复杂且需领域知识 → 微调；需多步推理 → Agent。大多数企业场景处于第二级与第三级的过渡区。

**加分项：** 提及 DTS-SQL（Decomposed Tree-of-thought SQL）的树状分解思路；MAC-SQL 的多 Agent 协作方案（Selector → Decomposer → Refiner）；Vanna 的在线训练模式（基于历史问答对持续改进检索）；Schema Linking 的 Embedding vs Keyword vs LLM 三路对比；以及在 Text2SQL 中加入 SQL 执行反馈循环的 Self-Debugging 范式。

## Q28：为何要将数据表每一行数据向量化？行级向量化与表元数据（Metadata）检索的优劣对比是什么？

### 考察点
考察候选人对结构化数据在 RAG 场景中的表示粒度问题的理解，能否区分行级语义和元数据级语义的适用边界，并对两种方案做出理性的工程取舍。

### 解答思路
1. 先解释行级向量化的动机——解决"找内容"而非"找表"的问题。
2. 从检索粒度、语义丰富度、更新成本、查询类型四个维度做对比。
3. 给出两种方案的组合使用策略。

### 参考答案
**为何要行级向量化：**

将数据表每一行向量化的核心动机是**将结构化数据转换为可语义检索的最小单元**。表元数据（表名 + 列名 + 注释）只能回答"哪张表可能包含相关信息"，而行级向量化可以回答"具体哪一行数据与用户问题最相关"。例如用户问"上个月销售额最高的产品是什么"，表元数据能帮你找到 sales 表，但无法定位"上个月"对应的具体行。行级向量化将每一行数据（如 `{product: 'XX', month: '2026-04', amount: 120000}`）序列化为自然语言文本后做 embedding，让检索阶段就能定位到具体数据行，从而在 Text2SQL 生成时直接注入精确的示例值（而不是模糊的"sales 表有 month 列"），大幅提高 SQL 准确率。

**行级向量化 vs 表元数据检索的优劣对比：**

| 维度 | 行级向量化 | 表元数据检索 |
|------|-----------|-------------|
| 检索粒度 | 行级别，能精确定位具体数据 | 表/列级别，只能定位到表 |
| 语义丰富度 | 高，包含具体数值和实体名称 | 中等，只有字段名和注释 |
| 更新成本 | 高，数据变更需重新向量化对应行 | 低，表结构变化频率远低于数据变化 |
| 存储成本 | 大，行数 × 向量维度（百万行 × 1536 维 = GB 级） | 小，表数 × 向量维度（百级表 × 1536 维 = MB 级） |
| 适合查询类型 | 按具体内容查询（"张经理负责的客户""价格 > 1000 的商品"） | 按主题查询（"销售相关数据在哪""用户行为数据存在哪"） |
| 隐私风险 | 高，向量可能反向推断出原始数据 | 低，元数据不包含敏感值 |
| 检索延迟 | 较高，百万级向量索引 | 极低，百级向量索引 |

**最佳实践——双层组合使用：**
先做表元数据检索定位候选表（粗筛），再在候选表范围内做行级向量化检索（精筛），将精选的示例行注入 prompt。这样既避免了全库行级检索的巨大开销，又保留了精确定位的能力。对于频繁更新的表，行级向量化要考虑增量更新策略（只更新变更行的向量，而非全量重建）。

**放弃行级向量化的场景**：表的列值以编码/ID 为主且缺乏自然语义（如外键列 `user_id=38291` 的向量化几乎无意义），此时应该依赖传统倒排索引做精确值匹配而非语义检索。

**加分项：** 提及行级向量化的序列化模板设计（如何把一行转化为有意义的自然语言，如模板 `"{列名}为{值}"` 组合）；对比行级向量化与列级向量化的差异（列级保留字段级语义、适合按字段查找场景）；STaR、DeepDB 等将行级语义检索与 Text2SQL 融合的学术方案；向量数据库的标量过滤（scalar filtering）与行级向量的混合查询实现。

## Q29：Text2SQL 业界常用方案、技术框架与难点你了解哪些？

### 考察点
考察候选人对 Text2SQL 领域的技术全景认知，能否从 prompt 工程、微调、Agent 三条技术路线梳理业界方案，并对核心难点有清晰的分析框架。

### 解答思路
1. 按技术路线分类介绍业界方案与代表框架。
2. 从 Schema Linking、SQL 正确性、复杂查询三个维度梳理核心难点。
3. 展望前沿趋势（多轮、Agent 化、自纠错）。

### 参考答案
**业界常用方案与框架（三条技术路线）：**

**路线一：Prompt 工程（零样本/少样本）**
- **DIN-SQL**：将 Text2SQL 分解为 Schema Linking → 问题分类（简单/中等/复杂）→ SQL 生成 → 自纠错四个步骤，每步独立 prompt。Spider 榜单 SOTA 级方法，核心贡献是证明了分步推理的有效性。
- **DAIL-SQL**：对 few-shot 示例做动态选择（检索与当前 query 最相似的历史 SQL 对），融合了示例检索和 prompt 组装。
- **DTS-SQL / C3**：引入思维树（Tree of Thoughts）对复杂问题做多路径推理，每条路径生成候选 SQL，最后投票或校验选出最优。
- **MAC-SQL**：多 Agent 协作方案，各 Agent 分工负责表选择、问题分解、SQL 生成和结果精炼。

**路线二：微调路线**
- **SQLCoder**（Defog 开源）：基于 StarCoder/CodeLlama 在 Text2SQL 数据上微调，支持 PostgreSQL 等方言，是开源侧最流行的专门 Text2SQL 模型。
- **NSQL**（NumbersStation）：引入数字感知训练策略，解决"数量大于 X"这类条件中的数值精确问题。
- **T5/Flan-T5 微调**：将 Text2SQL 视为 Seq2Seq 任务，在 Spider/WikiSQL 等数据集上微调编码器-解码器架构。

**路线三：Agent 路线**
- **LangChain SQL Agent**：用 ReAct 范式，Agent 自主决定查哪些表、看哪些 schema、生成什么 SQL、执行后是否需要修正，适合企业级多表复杂查询。
- **Vanna**：基于历史问答对做训练，将 Text2SQL 与 RAG 结合——用用户问题检索最相似的历史成功 SQL，作为 few-shot 示例注入 prompt，持续学习提升。
- **Chat2DB / SQLChat**：数据库客户端嵌入 AI Agent，多轮交互式生成 SQL。

**核心难点：**

1. **Schema Linking（最核心难点）**：用户自然语言中模糊的实体指代（"上月的那个活动"）如何精确映射到具体表和字段（`marketing_campaigns.status = 'active'`）。尤其跨多表的复杂 join 场景，LLM 容易"表间迷路"。业界方案包括：表-列两级向量检索、外键关系图谱引导、LLM 动态决策链路。

2. **SQL 语法正确性与执行安全性**：LLM 生成的 SQL 经常出现表名/列名幻觉（编造不存在的列）、语法错误（不同 SQL 方言冲突）、JOIN 条件错误。DIN-SQL 的自纠错循环是典型解决方案，但增加延迟和成本。

3. **复杂查询分解**：包含嵌套、窗口函数、多层聚合的查询远难于单表 SELECT。需要将查询分解为子问题（如 DTS-SQL 的树状分解），逐个解决子查询后合成。

4. **数值精度与模糊条件处理**："便宜""贵""最近""大概"等模糊词需要在 SQL 中量化（`WHERE price < 100` 还是 `ORDER BY price LIMIT 10`），"上个月"应转为精确日期范围。

5. **多轮对话与上下文维护**：用户连续提问时需要维护当前选中的表范围、上一次执行的 SQL 结果等作为对话上下文，避免每次都重新做 schema linking。

6. **跨方言适配**：MySQL、PostgreSQL、SparkSQL、BigQuery 之间的语法差异（LIMIT vs TOP、日期函数、字符串处理方式），模型需要感知并适配目标方言。

**加分项：** 提及 Spider 2.0 的评测演进（从单轮到多轮、从单库到跨库）；RESDSQL 的 schema 排序剪枝方案；Self-Debugging 范式（Text2SQL + 执行反馈循环）；CHASE-SQL 的候选生成 + 选择策略；以及 Text2SQL 的幻觉特殊性——SQL 执行后会立刻暴露错误，这是双刃剑（既可用于纠错，也可能破坏用户体验）。

## Q30：结构化数据用固定分块的原因？什么场景不适合固定分块？标点分块如何解决语义割裂问题？

### 考察点
考察候选人对不同数据类型的切分策略选型能力，能否理解结构化数据的特殊性以及分块方案与数据特征的匹配逻辑，对标点分块（递归字符分割）的原理有清晰认知。

### 解答思路
1. 先解释结构化数据适合固定分块的根本原因（结构规整、语义单元固定）。
2. 列举不适合固定分块的异常场景及其根因。
3. 详解标点分块的原理及其解决语义割裂问题的机制。

### 参考答案
**结构化数据用固定分块的原因：**

结构化数据（数据库记录、JSON 字段、CSV 行、API 返回值）具有天然的规整性——每一条记录、每一个字段组已经是最小的语义单元。固定分块（按 token 数 256 或 512 切分）配合结构化边界保护（在记录边界处切分而非记录中间截断），恰好与这种规整性对齐：

1. **语义单元天然固定**：一条数据库记录 = 一个完整的语义单元。JSON 文档中同一层级的键值对是一个独立信息片段。不需要复杂算法，按记录边界 + token 预算双重约束即可高质量切分。

2. **检索效率最优**：固定分块的 embedding 向量维度相同，检索时语义单元粒度一致，便于相似度分数的横向公平对比。如果块大小差异过大，长块的 embedding 语义稀释更严重，与短块之间的相似度比较会失去公平性。

3. **工程成本最低**：不需要语义模型参与切分决策，不需要计算语义转折点，不需要维护复杂的切分逻辑。对于每天新增百万行记录的数据管道，这是唯一可规模化落地的方案。

**不适合固定分块的场景：**

- **嵌套层级很深的 JSON/XML**：固定切分在中途截断会丢失子对象的结构上下文，导致后续检索匹配不到完整对象，LLM 也只能看到不完整的嵌套结构。
- **字段语义长度差异极大的宽表**：有些字段是一句话，有些是几千字的长文，固定切分要么浪费短字段的 token 配额，要么切断长字段导致语义不完整。
- **需要跨多条记录做聚合推理的统计查询**：如"平均销售额""最高分的 3 条记录"，固定分块将相关记录散落到不同 chunk，LLM 需要合并多个 chunk 才能完成计算，增加推理难度。
- **表结构与数据高度纠缠的工业协议数据**：如 CAN 总线报文、二进制协议解析后的数据，列定义和数据值共享上下文，固定分块无法判断"结构定义"和"数据行"的逻辑边界。

**标点分块如何解决语义割裂问题：**

标点分块（Punctuation-based Chunking，又名递归字符分割 / Recursive Split）的核心策略是：**在固定 token 预算约束下，优先在标点处（句号、段落符、逗号等）切分，确保每个 chunk 在语法层面是完整的**。LangChain 的 RecursiveCharacterTextSplitter 是这种方案的标准实现——按 `\n\n → \n → 。→ ；→ ，` 的分隔符优先级递归切分，优先保证最大的语义边界（段落）完整。

这弥补了纯固定分块的核心缺陷：固定分块可能在句中被硬切断，导致前半句在 chunk A、后半句在 chunk B。embedding 后两个 chunk 的语义表达都不完整，检索时无论 query 匹配到哪一半，都无法获得完整的答案信息。标点分块则确保句子和段落尽可能不被截断——当 token 接近预算上限时，提前在最近的标点处切分（而非等到预算耗尽才硬切），本质上是在"语义完整性"和"token 预算"两个约束条件之间做了合理折衷。配合 overlap（通常 10%-20% 重叠），可进一步降低边界处的信息丢失风险。

**加分项：** 提及 RecursiveCharacterTextSplitter 的分隔符优先级链设计哲学（从粗粒度到细粒度的渐进式切分）；Jina AI 的 Semantic Chunker 用 embedding 相似度判定语义转折点，完全摆脱字符/Token 限制；语义分块对结构化数据是否过度设计——引入 ML 决策对规整数据可能是杀鸡用牛刀；结构化数据 RAG 中"行向量化 + 表元数据双层索引"的混合方案；嵌套 JSON 可先用 jq/JSONPath 展开叶子节点再分块。

## Q31：加重排后效果变差的原因是什么？

### 考察点
考察候选人对 Rerank 模型的工程认知深度，能否意识到重排序并非"万能银弹"，在特定条件下反而会引入噪声。面试官期望候选人从模型能力边界、数据分布、工程参数三个维度做系统性归因。

### 解答思路
1. 先定位效果变差的核心根因——Reranker 的排序偏好与业务相关性定义不一致。
2. 从 Reranker 训练数据偏差、候选集质量、截断策略失当三个方向具体展开。
3. 给出诊断方法和改进方案。

### 参考答案
加重排后效果变差，本质上是 **Reranker 对相关性的判断与业务真实需求出现了偏差**，导致经过向量召回原本正确的文档被 Reranker 降低了排名，而噪声文档被错误提权。具体原因可以归为以下四类：

**1. Reranker 训练数据与业务领域不匹配（最核心原因）**：通用 Reranker（如 Cohere Rerank、BGE-Reranker-v2）通常在 MS MARCO 等通用 QA 数据集上训练，学习到的"相关性"偏向于信息检索场景。当你用在高度专业化的垂直领域（如医疗诊断、法律条文、芯片规格书）时，Reranker 无法准确判断领域内的微妙语义差异——它可能认为某段"看起来通顺且包含关键词"的文本更相关，但实际上那是对业务完全错误的解读。

**2. 候选集中缺乏真正相关文档时，Reranker 强制排序产生"伪高分"**：Reranker 的设计目标是对给定候选集做相对排序，即使所有候选都与 query 无关，它也会输出一个排序（所谓"矮子里拔将军"）。如果向量召回阶段本身 recall 就低，Reranker 不仅无法补救，还可能将噪音文档排到前列，误导 LLM。

**3. Reranker 的截断阈值设置不当**：很多团队只取 Rerank 后的固定 Top-K 而忽略分数阈值。如果 Top-K 中包含 Rerank 分数极低（如 <0.3）的 chunk，这些低质内容进入 LLM 上下文反而干扰生成。正确的做法是结合分数阈值 —— 例如只保留 Rerank score > 0.5 的 chunk，不足 K 个也不要硬凑。

**4. Reranker 对长文档的截断处理丢失关键信息**：Cross-Encoder 类 Reranker 有最大输入 token 限制（通常 512/1024 token）。如果 chunk 很长，Reranker 只能看到前半部分，排序依据的信息不完整。此外，当 query 的答案线索分散在一个 chunk 的中后段时，Reranker 因截断无法捕获，导致该 chunk 被错误降权。

**诊断方法**：对比向量召回 Top-K 的排序与 Rerank 后的排序，人工检查被 Reranker 降权的 chunk 是否确实包含答案（假阴性），被提权的 chunk 是否真的相关（假阳性）。若假阴性率高，暂停 Rerank 或换用领域微调的 Reranker。

**加分项**：讨论 LLM-as-a-Reranker 在特定场景优于专用 Reranker 的原因（LLM 理解领域上下文能力强）。通过数据飞轮构建领域 Reranker 训练集——收集线上用户反馈（点赞/踩）作为正负例。介绍 RankGPT（用 GPT-4 做 Listwise 排序）与传统 Cross-Encoder 的效果对比。

## Q32：向量数据库检索出来的历史信息，如果语义相关但时间太久，能直接用吗？

### 考察点
考察候选人对 RAG 系统中信息时效性（Timeliness）的工程意识，能否意识到语义相关不代表事实有效，以及如何在检索管线中融入时间维度的判断逻辑。

### 解答思路
1. 先明确"时间太久"带来的两种核心风险：知识过期和逻辑过期。
2. 提出在检索、Rerank、Prompt 三个环节引入时效性控制的具体方案。
3. 强调时效性处理不可"一刀切"，需要根据知识类型做区分。

### 参考答案
**不能直接使用，需要经过时效性判断和处理。** 语义相关只解决了"内容匹配"问题，但完全没有考虑"内容是否依然有效"。时间太久带来的风险主要有两类：

**1. 知识过期（Knowledge Expiration）**：技术文档、产品手册、API 文档、政策法规等信息随时间推移会失效。比如 2022 年的 API 文档在 2025 年已经完全不适用，但 embedding 相似度依然很高，向量检索仍会将其排在前面。这比召不回相关内容更危险——LLM 看到"高相关度的权威来源"，更容易采信其中的过时信息。

**2. 逻辑过期（Logical Expiration）**：某些信息本身不会"过时"，但在当前上下文中已不适用。例如"2024 年 Q1 销售策略"在 2025 年 Q1 检索时，语义高度相关（策略框架相似），但具体的市场环境、KPI 指标、资源分配都已变化，直接引用会误导业务决策。

**时效性控制的三种方案：**

**方案一：检索阶段做时间过滤（Metadata Filtering）**。在 chunk 入库时记录 `created_at` 和 `valid_until` 字段，检索时按时间范围过滤。例如技术文档可设置有效期 6 个月，过期后降低检索权重或直接排除。对于不确定有效期的知识（如学术论文、历史记录），保留但不做过滤，靠下游处理。

**方案二：Rerank 阶段融入时效性特征**。在 Reranker 打分时，将文档的新鲜度（recency）作为额外特征与语义相关性综合计算。可设计衰减函数：`final_score = rerank_score * decay(t)`，其中 decay 随时间递增而平滑衰减。比硬过滤更灵活，避免了刚好过期的优质内容被完全屏蔽。

**方案三：Prompt 中显式标注时间并约束模型行为**。对于无法在检索侧过滤的内容，在 Prompt 中为每个 chunk 明确标注其发布时间/有效期，并要求 LLM 在回答时辨证使用："如果检索到的信息发布较早（超过 6 个月），请优先使用较新的信息，并在引用时注明日期，提醒用户该信息可能已过时。"

**区分处理原则**：不是所有领域都需要强时效性控制——科技/政策/价格类信息时效性要求高（天/周级），学术/历史/文学类信息时效性要求低（年级甚至无要求）。时效性策略应与知识类型绑定，而非一刀切。

**加分项**：建立时效性监控 Dashboard——按文档新鲜度分布统计查询覆盖度，若超过 X% 的查询返回平均年龄 > 6 个月的内容，触发知识库更新告警。时效性评测——在评测集中加入时间敏感的 query（如"2025 年的税率是多少？"），验证 RAG 是否能优先召回最新文档。

## Q33：如何评估 Rerank 的有效性？有什么指标吗？

### 考察点
考察候选人对 Rerank 环节的评测方法论掌握程度，以及能否区分"检索排序质量"和"最终答案质量"两个不同层面的评估。这是 RAG 管线精细化优化的重要技能。

### 解答思路
1. 先明确 Rerank 评估的定位——评估的是排序质量，而非最终生成质量。
2. 从离线评估（排序指标）和在线评估（生成影响）两个维度给出指标。
3. 补充对比实验和消融实验的设计方法。

### 参考答案
评估 Rerank 的有效性需要从**排序质量**和**对下游生成的最终影响**两个层面来考量：

**一、排序质量指标（离线评估，核心指标）**

这些指标衡量 Rerank 后将相关文档排到更靠前位置的能力，需要标注数据集（每个 query 对应的相关文档列表）：

- **NDCG@K（归一化折损累积增益）**：衡量排序质量的黄金指标。它同时考虑文档是否相关（0/1 或分级相关度）和排名位置权重（越靠前权重越大）。`NDCG@K = DCG@K / IDCG@K`，其中 DCG 累积排名位置上的相关度得分，IDCG 是理想排序下的 DCG。NDCG@K 越高，表示 Reranker 将相关文档排得越靠前。K 一般取 5/10/20。

- **MRR（平均倒数排名）**：`MRR = (1/|Q|) * Σ(1/rank_i)`，其中 `rank_i` 是第 i 个 query 的第一个相关文档的排名。MRR 关注的是"最佳答案排在第几位"，适合用户只看 Top-1 的场景（如 FAQ 精确匹配）。

- **Precision@K 和 Recall@K**：在 Rerank 后的 Top-K 中，相关文档的占比（Precision）和全部相关文档被覆盖的比例（Recall）。Rerank 的目标是高 Precision（Top-K 中少混入噪声）同时不显著降低 Recall。

- **MAP（Mean Average Precision）**：考虑所有相关文档的排名位置的平均精度，比 MRR 更全面地评估多文档相关场景。

**二、对比基线来量化提升幅度**

核心对比实验：
- **Recall@20 vs Recall@5**：向量召回 Top-20 的 Recall 作为"理论上限"，经过 Rerank 截断至 Top-5 后，Recall 下降了多少？下降越小说明 Rerank 排序越准。
- **Rerank Top-5 NDCG vs 无 Rerank Top-5 NDCG**：直接量化 Rerank 带来的排序增益。如果此差值接近 0，说明 Rerank 在此场景无效，可考虑下线以节省成本。
- **消融实验**：逐步去掉 Rerank → 观察 RAGAS Faithfulness 和 Answer Correctness 的变化。这是最务实的评估方式，直接衡量 Rerank 对最终答案质量的贡献。

**三、工程层面的评估维度**

- **延迟增幅**：Rerank 引入的额外耗时（通常 100-500ms），需评估响应时间是否仍在 SLO 内。
- **成本增量**：Reranker API 调用（Cohere Rerank 约 $2/1000 次）或自部署 GPU 推理成本，与生成质量提升幅度的 ROI 是否合理。
- **召回降级率**：Rerank 是否在某些 query 类型上系统性地排低了正确答案。可按 query 类型（事实型/推理型/多跳型）分组统计，找出 Reranker 的能力短板。

**四、在线评估（金标准）**

A/B 测试对比有/无 Rerank 两条链路：用户满意度评分、点赞/踩比例、答案修改率（用户如果频繁重新提问说明对答案不满意）、人工抽检通过率的差异。但线上实验成本高，应在离线指标达标后再上线验证。

**加分项**：使用 LLM-as-a-Judge 自动化生成评测标注——用强模型（如 GPT-4）判断每个 chunk 是否"包含足以回答 query 的信息"，替代昂贵的人工标注。介绍 BEIR Benchmark 中 Rerank 子任务的标准化评测流程。评测 Reranker 在不同 chunk 长度、不同领域文档上的鲁棒性（robustness）。

## Q34：检索策略有哪些？向量匹配的计算指标有哪些？

### 考察点
考察候选人对信息检索技术栈的系统性认知，能否从稀疏检索、稠密检索、混合检索三个层次梳理策略全景，同时精确掌握向量匹配的核心数学指标及其选择原则。这是 RAG 工程面试的基础必考题。

### 解答思路
1. 先分类枚举检索策略（按技术路线分三层），覆盖从传统到前沿。
2. 再逐一解释向量匹配的四种核心计算指标。
3. 总结不同指标的选择场景和向量归一化带来的等价性。

### 参考答案
**一、检索策略分类（从稀疏到稠密，从单路到多路）**

**第一类：稀疏检索（Sparse Retrieval）——基于词项匹配**
- **BM25**：TF-IDF 的改进版，引入词频饱和函数和文档长度归一化，是当前最主流的关键词检索算法。通过精确的词项重合召回，对专有名词、代码、型号等效果极佳。Elasticsearch 的默认算法。
- **TF-IDF**：经典的词频-逆文档频率加权，较 BM25 简单但对长文档偏差大。
- **Query Expansion / 同义词扩展**：在检索前对 query 做同义词替换和关键词扩展，缓解词项失配问题。

**第二类：稠密检索（Dense Retrieval）——基于语义匹配**
- **单塔 Bi-Encoder（双编码器）**：Query 和 Document 分别由两个 encoder 独立编码为向量后计算相似度。这是 RAG 中向量检索的标准范式，代表模型有 DPR、BGE、GTE。
- **Late Interaction（延迟交互）**：ColBERT 范式，Query 和 Document 各自保留 token 级向量，在检索阶段做细粒度的 token-to-token 交互，精度介于 Bi-Encoder 和 Cross-Encoder 之间。
- **Multi-Vector 检索**：每个 chunk 生成多个向量（如摘要向量 + 关键词向量 + 原文向量），多路融合检索。
- **HyDE（假设文档嵌入）**：用 LLM 生成假设答案后，用答案向量替代 query 向量做检索，缩小 query-document 语义鸿沟。

**第三类：混合检索（Hybrid Search）——多路融合**
- **向量 + BM25 混合**：最经典的组合，向量负责语义召回，BM25 负责精确匹配，结果通过 RRF 或加权求和融合。
- **多粒度检索**：同时用小 chunk 和大 chunk 做索引，小粒度用于精准定位，大粒度用于上下文扩展。
- **知识图谱辅助检索**：将实体关系嵌入到检索过程中，通过图谱中的路径扩展召回范围（Graph RAG）。

**二、向量匹配的计算指标**

| 指标 | 公式 | 取值范围 | 核心含义 |
|------|------|----------|----------|
| **余弦相似度** | cos(θ) = (A·B)/(‖A‖·‖B‖) | [-1, 1] | 只衡量方向一致度，消除向量长度干扰 |
| **欧氏距离** | d = √(Σ(A_i - B_i)²) | [0, +∞) | 空间直线距离，受方向和长度双重影响 |
| **内积/点积** | A·B = Σ(A_i × B_i) | (-∞, +∞) | 方向一致性 × 向量模长，某些模型训练时就以此为优化目标 |
| **曼哈顿距离** | d = Σ|A_i - B_i| | [0, +∞) | 各维度绝对差之和，高维稀疏场景下对异常值更鲁棒 |

**关键选择原则：**
- 如果 embedding 模型输出已做 L2 归一化（如 OpenAI text-embedding-3），余弦相似度与内积等价，余弦与欧氏距离存在单调关系（d² = 2(1-cosθ)），此时三者排序结果一致，选哪个没有实质差异。
- 如果 embedding 未归一化（如某些开源的 BGE 版本），优先用余弦相似度——它能消除部分文档天然更"长"（范数大）带来的偏差。
- 注意你的向量数据库索引支持什么度量：Milvus 的 IVF_FLAT 支持 L2 和 IP，HNSW 支持 L2 和余弦。选索引时不匹配会报错或退化为暴力搜索。

**加分项**：对比讨论 RRF（Reciprocal Rank Fusion）、线性加权、LambdaMART 等融合策略在不同检索场景的效果差异。MPNet 和 E5 等模型训练时使用的对比损失对相似度度量的隐含要求（用 cosine loss 训练的模型必须用 cosine 检索）。介绍 Learned Sparse（SPLADE）作为稀疏-稠密折衷方案。

## Q35：Embedding 模型怎么选？怎么微调？向量数据库怎么选？

### 考察点
考察候选人在 RAG 三大基础组件选型上的工程判断力，能否从业务需求出发做出理性决策而非盲目追求 SOTA，并具备 Embedding 微调的落地经验。

### 解答思路
1. Embedding 模型选型从评测基准、领域适配、推理成本三个维度给出决策框架。
2. Embedding 微调部分讲清数据准备、训练范式、评估闭环的完整流程。
3. 向量数据库选型从规模、性能、功能、运维四个维度做对比决策。

### 参考答案
**一、Embedding 模型选型**

选型需要从三个维度做权衡：

**维度 1：评测基准表现**
关注 MTEB（Massive Text Embedding Benchmark）排行榜，重点看与你的场景匹配的子任务分数：
- 语义相似度（STS）——衡量句子级语义匹配
- 检索（Retrieval）——衡量 query-document 匹配
- 聚类（Clustering）——衡量文本语义分组能力
- 分类（Classification）——衡量 embedding 的线性可分性

如果你的场景是中文知识库问答，优先关注 C-MTEB 排行榜上的检索子任务分数。当前第一梯队的中文模型包括 BGE-M3（支持稠密+稀疏混合）、GTE-Qwen2、stella-base 等；英文/多语言场景可选 text-embedding-3-large（OpenAI）、Cohere Embed v3、BGE-M3 等。

**维度 2：领域适配程度**
通用 embedding 在垂直领域通常有 15%-30% 的召回损失。选型时优先看模型是否在相近领域数据上做过预训练或微调。如果候选模型差异不大，用你自己的标注数据跑一轮 Recall@K 对比测试即可得出结论——不需要相信排行榜上的"通用分"。

**维度 3：推理成本与延迟**
开源模型（BGE/GTE/E5 系列）可本地部署，单次推理 5-20ms，但需要 GPU 资源。商业 API（OpenAI/Cohere）按 token 计费（约 $0.02-$0.13/百万 token），免运维但延迟受网络影响（50-200ms）。大规模文档入库（亿级）时推荐本地部署以控制成本。

**二、Embedding 模型微调**

**第 1 步：数据准备**
核心是构建正负例对：
- **正例**：(query, relevant_document) 对，来源包括用户点击日志、人工标注、或利用 LLM 生成合成数据。
- **负例**：Hard Negative（看起来相关但实际不相关的文档）比 Random Negative 更重要。可以从当前向量检索的 Top-20 中随机非相关文档采样。Hard Negative 的质量直接决定微调效果的上限。
- 数据量：一般来说 5K-50K 条高质量配对数据即可产生明显提升。

**第 2 步：训练范式选择**
- **Contrastive Learning（对比学习）**：最常见的方式。使用 InfoNCE Loss（或 MultipleNegativesRankingLoss），拉近正例对的距离，推远负例对。Sentence-Transformers 库提供了开箱即用的训练脚本。
- **知识蒸馏**：用 Cross-Encoder 或 LLM 给配对数据打分，用打分结果作为软标签训练 Bi-Encoder。适合已有高质量 Reranker 但缺少配对标注的场景。
- **继续预训练（TSDAE / RetroMAE）**：在领域无标注文本上做自监督预训练，让模型先适应领域语言分布，再做对比微调。适用于领域术语高度特化的场景（如生物医药、法律）。

**第 3 步：评估闭环**
在微调前后用同一批标注的 query 测试集跑 Recall@K / NDCG@K 对比，验证提升幅度。注意训练集和测试集的 query 不能重叠，否则评测结果虚高。

**三、向量数据库选型**

| 维度 | Milvus | Qdrant | Weaviate | Pinecone | Chroma |
|------|--------|--------|----------|----------|--------|
| 规模 | 十亿级（分布式） | 亿级 | 亿级 | 亿级（托管） | 百万级 |
| 部署 | 自托管为主 | 自托管/云 | 自托管/云 | 纯云托管 | 本地嵌入 |
| 混合检索 | 支持（BM25+向量） | 原生支持 | 原生 Hybrid | 需外部组合 | 有限 |
| 过滤能力 | 强（标量+向量混合查询） | 强（带 payload 过滤） | 强（GraphQL-like） | 强（metadata filter） | 基础 |
| 运维复杂度 | 高 | 中 | 中 | 低（托管） | 极低 |
| 适用阶段 | 生产/大规模 | 生产/中等规模 | 生产/中等规模 | 快速启动/免运维 | 原型/Demo |

**选型原则：**
- **快速原型/POC**：Chroma 或 Qdrant（本地嵌入式部署，5 分钟跑通）
- **中等规模生产（百万-千万级）**：Qdrant 或 Weaviate（性能好、运维成本适中）
- **大规模生产（亿级+）**：Milvus（分布式架构、索引算法成熟，但需要专业运维）
- **免运维优先**：Pinecone 或 Zilliz Cloud（Milvus 托管版）

**关键考量因素**：除了规模，还要看是否原生支持你需要的混合检索（向量+BM25）、metadata 过滤的表达能力、索引类型（HNSW/IVF/DiskANN）、增量更新的便利性、以及生态集成（LangChain/LlamaIndex 是否已支持）。

**加分项**：讨论 Matryoshka Embedding（支持灵活截断维度、以少量精度损失换取存储和检索速度提升）在向量库选型中的影响。Embedding 模型版本管理——微调后如何确保新旧 embedding 的兼容和灰度切换。Qdrant 的量化索引（Scalar/Product Quantization）在存储节省和精度损失之间的权衡。

## Q36：多跳检索（Multi-hop RAG）的实现思路？

### 考察点
考察候选人对复杂推理场景下 RAG 架构的进阶理解，多跳检索是 RAG 从"单次查文档"进化为"多步蛛网式推理"的关键能力，也是 Agentic RAG 的重要落地形态。面试官期望候选人能说出可落地的实现方案，而非停留在概念层面。

### 解答思路
1. 先定义多跳检索的核心问题——需要多次检索逐步拼接信息才能回答的复合/推理型问题。
2. 给出三种主流实现思路：迭代检索、图谱辅助、链式推理，并对比适用场景。
3. 补充多跳检索中的关键工程挑战和缓解策略。

### 参考答案
多跳检索（Multi-hop RAG）解决的核心问题是：**答案需要结合多个独立检索到的信息片段，且后续检索依赖于前面检索的结果**。典型场景如："去年收购 Slack 的那家公司现在的 CEO 是谁？"——需要先检索"谁收购了 Slack"（得到 Salesforce），再检索"Salesforce 的 CEO 是谁"（得到 Marc Benioff）。单轮 RAG 无法解决，因为第二个查询依赖第一个查询的答案。

**三种主流实现思路：**

**思路一：迭代检索 + CoT 推理（Iterative Retrieval with Chain-of-Thought）**
这是最通用的方案。利用 LLM 的推理能力将复杂问题逐步分解：

```
Step 1: 用户提问 → LLM 思考："我需要先知道 X，再基于 X 查询 Y"
Step 2: 第 1 轮检索（query="X"）→ 获得 context_1
Step 3: LLM 基于 context_1 推理，生成第 2 轮查询 → 检索 → 获得 context_2
Step 4: 依此类推，直到信息完整 → LLM 综合所有 context 生成最终答案
```

实现时需要：设计循环控制逻辑（最大迭代次数/置信度阈值）、维护上下文累积（每轮检索结果追加而非替换）、以及控制 token 预算（防止上下文溢出）。LangGraph 的 Agent 循环、LlamaIndex 的 SubQuestionQueryEngine 都支持这种模式。核心风险是**错误传播**——如果第 1 轮检索结果错误，后续所有推理都建立在这个错误基础之上。

**思路二：图谱增强多跳（Graph-Enhanced Multi-hop）**
将文档中的实体和关系预先抽取为知识图谱（或利用 Neo4j 等图数据库），多跳查询转化为图上的路径遍历：

```
查询："收购 Slack 的公司 CEO"
图遍历：
  1. 实体匹配："Slack" → 关系"被收购方" → "收购方"实体 → Salesforce
  2. 继续遍历：Salesforce → 关系"CEO" → Marc Benioff
```

优势是推理路径明确、可解释、效率高（图的跳数通常远少于迭代检索的轮次）。局限是图谱构建成本高、需要 NER+关系抽取的预处理管线、且无法覆盖知识库中未结构化建模的隐性关系。Graph RAG（微软的 GraphRAG）是其代表方案。

**思路三：IRCoT（Interleaving Retrieval with Chain-of-Thought）**
这是学术上较有影响力的方案。让 LLM 在生成思维链（Chain-of-Thought）的过程中，**交替插入检索步骤**：

```
Thought 1: "要回答这个问题，我需要了解 Salesforce 的收购历史"
Action: retrieve("Salesforce acquisitions Slack timeline")
Observation: [检索结果]

Thought 2: "根据结果，Salesforce 在 2021 年收购了 Slack。现在需要知道 Salesforce 当前的 CEO"
Action: retrieve("Salesforce current CEO 2025")
Observation: [检索结果]

Answer: "Salesforce 的 CEO 是 Marc Benioff，他自公司成立以来..."
```

IRCoT 的精妙之处在于将检索动作自然嵌入推理流——检索不是前置或后置的，而是与推理交替进行，LLM 在每一轮都基于前一跳的推理结果来生成下一轮的检索 query。这比固定步骤的迭代检索更加灵活，查询的生成质量也更高。

**工程实现要点与挑战：**
1. **错误传播机制**：多跳检索中前序步骤的错误会被后续放大。建议中间步骤检查检索结果的置信度，低于阈值时触发回溯（Backtracking）或换用不同的查询表述重试。
2. **循环终止条件**：设计明确的停止条件——最大跳数（通常 2-4 跳足够）、信息完整度判定（LLM 自我评估是否已有足够信息回答）、或 token 预算耗尽。
3. **延迟控制**：每多加一跳就增加一次 LLM 调用和一次检索。对简单问题（单跳可解）做快速路由，仅对复合问题触发多跳模式。可使用较小的模型（如 GPT-4o-mini）做中间跳的查询生成，降低延迟和成本。
4. **上下文管理**：各跳的检索结果需要在最终 Prompt 中合理组织，可以用结构化格式（如按跳分组）展示推理路径，帮助 LLM 更好地综合多跳信息。

**加分项**：讨论 Self-Ask（让 LLM 自问自答地分解问题）与 Multi-hop RAG 的关系。使用 DSPy 框架自动化多跳 RAG 的 prompt 优化。对比深度搜索（Deep Search）中 Tree-of-Thought 式的多分支探索与线性多跳的差异——复杂问题可能需要同时探索多条推理路径，最后合并结果。

## Q37：为什么需要父子索引？Re-rank 后一般返回几个块？为什么？

### 考察点
考察候选人对索引粒度分层设计和重排截断策略的工程理解，评估其在实际场景中平衡精度、完整性和成本的系统思维能力。

### 解答思路
1. 阐明父子索引要解决的核心矛盾——检索精度与上下文完整性的根本冲突。
2. 说明 Re-rank 后截断数量的工程经验值，并从信息论、模型能力和成本三个维度论证。
3. 补充在不同业务场景下截断数量的调整原则。

### 参考答案
父子索引（Parent-Child Index）解决的是一个根本性矛盾：小 chunk 语义聚焦度高，向量检索更精准，但信息不完整，LLM 难以理解上下文；大 chunk 信息完整但语义信号被稀释，检索精度下降。父子索引通过两层设计桥接这个鸿沟——子层用小粒度 chunk（如 128-256 tokens）做向量索引保证检索精度，父层保留每个子 chunk 所属的大粒度块（如完整段落或 1024 tokens），作为返回给 LLM 的上下文。检索时先用子 chunk 匹配，再返回其父 chunk，实现"小粒度精准命中、大粒度完整返回"。

Re-rank 后一般返回 3-5 个块。原因有四：（1）Cross-Encoder 的评分是单调递减长尾分布，5 名之后的语义相关性通常极低，引入它们只会增加噪声而非有效信息；（2）LLM 注意力机制在 3-5 个独立信息源时推理效果最佳，过多信息源会导致注意力分散，尤其在需要信息整合的推理任务中；（3）Token 经济性——每多一块就多几百 token，增加推理延迟和 API 成本，而边际收益趋近于零；（4）实际场景可按任务类型微调：事实型问答取 2-3 块即可覆盖答案，综合分析型取 5 块给 LLM 更全面的视野。

**加分项**：讨论 Small-to-Big 检索（LlamaIndex 的节点检索模式）和 Sentence Window Retrieval（以目标句子为中心取窗口）作为父子索引的变体。介绍 Multi-Vector 策略——一个文档可对应多个向量表示（摘要向量、关键词向量、不同粒度的 chunk 向量），进一步提升在不同 query 类型下的召回覆盖度。

## Q38：摘要生成用什么模型？摘要质量怎么保证？

### 考察点
考察候选人对摘要模型选型的实践经验以及构建摘要质量保障体系的工程能力，特别是自动评估与人工校验的闭环设计。

### 解答思路
1. 按场景分层推荐摘要模型，说明各模型的适用条件。
2. 从事实一致性、信息覆盖度、简洁性三个维度构建质量评估体系。
3. 给出工程化的质量保障流水线设计。

### 参考答案
摘要模型选型需按场景分层决策：（1）高质量长文档摘要——推荐 GPT-4o、Claude 3.5 Sonnet 或 DeepSeek-V3 等大模型，借助强指令遵循能力生成结构清晰、覆盖全面的摘要；（2）高吞吐低延迟场景——使用微调后的专用模型如 Pegasus、BART、LongT5，在特定领域可接近大模型效果，推理成本仅为 1/10-1/50；（3）中文场景——Qwen-Max、DeepSeek-V2 对中文语境的摘要连贯性和术语理解优于英文原生模型；（4）结构化摘要（提取关键实体/事件/观点）——用 JSON mode 约束 LLM 输出固定 schema。

摘要质量保证的三大维度：（1）事实一致性（避免幻觉）——用 NLI 模型（SummaC、AlignScore、UniEval）逐句检测摘要陈述是否可被原文支撑，不一致片段触发重生成或标注警告；（2）信息覆盖度（避免遗漏）——通过 ROUGE-L、BERTScore 衡量摘要与原文的语义覆盖，同时可用 LLM 扮演"逆向问答"角色——让 LLM 仅凭摘要回答原文中的关键问题，回答不上来说明摘要遗漏了关键信息；（3）冗余控制（避免啰嗦）——用自信息密度（Self-BLEU 或对同一 chunk 多次摘要的重叠率）监控。工程实践上建立"生成-校验-重试"的自动流水线：首次生成→自动评估→低于阈值则用不同 Prompt 或模型重试→仍不达标则标记人工审核。对于关键场景，定期采样做人工 A/B 盲评，积累 Bad Case 反馈驱动 Prompt 和模型迭代。

**加分项**：讨论 Chain-of-Density（CoD）提示策略——引导 LLM 多轮迭代地生成密度递增的摘要。介绍 LLM-as-Judge 的摘要评估方案：约定评分标准（1-5 分），让 GPT-4 担任评估官给出细粒度评分。提到 Long Context 模型直接生成摘要与分块摘要后拼接两种范式的优劣对比——前者保证跨块的逻辑连贯性，后者保证信息不遗漏。

## Q39：如果做 Code-RAG，应该怎么做？

### 考察点
考察候选人对代码这一结构化文本的 RAG 特化设计能力，评估其对 AST 解析、代码 Embedding、依赖追踪等关键技术的理解和落地思路。

### 解答思路
1. 明确 Code-RAG 与传统文本 RAG 的核心差异，建立问题域认知。
2. 分四步给出系统性方案：结构化解析、代码 Embedding、依赖增强、仓库级上下文。
3. 补充关键工程权衡和业界实践参考。

### 参考答案
Code-RAG 与传统文本 RAG 有三个根本差异：（1）代码有严格的语法结构，朴素固定大小切块会截断函数体或类定义，导致语法不完整的片段无法被 LLM 正确理解；（2）代码中函数名、变量名、类名等符号的语义密度极高，一个 token 就可能承载大量信息，需要 Embedding 模型具备代码语义理解能力；（3）代码之间有显式的依赖关系（import、调用链、继承），单个文件/函数往往不足以回答一个问题，必须关联其依赖。

完整方案分四步：（1）**AST 感知切分**：用 Tree-sitter 或 language-server-protocol 解析代码为 AST，按函数、类、方法级别切块，保证每个 chunk 是语法完整的代码片段；同时保留签名和 docstring 作为 chunk 的前缀增强语义。（2）**代码专用 Embedding**：查询侧用自然语言 Embedding，文档侧用代码专用模型（如 CodeBERT、StarCoder-Embed、Voyage-code-2）。通过对比学习将自然语言查询和代码片段映射到统一的向量空间，确保 NL-PL 跨模态检索效果。（3）**依赖图增强检索**：预先构建跨文件的代码依赖图（基于 import/调用关系），检索时不仅返回命中 chunk，还沿依赖边自动拉取被调用函数、被引用类的定义，一并作为上下文送给 LLM，解决"看到调用但看不到定义"的痛点。（4）**Repo-level 摘要**：用 repo-map 技术（Aider、Cody 实践）生成仓库级别的结构摘要——包括目录树、关键模块说明、核心类的签名列表，作为每次检索的固定前缀上下文，让 LLM 在全局视角下理解检索到的代码片段。

**加分项**：讨论 Fill-in-the-Middle（FIM）在 Code-RAG 生成阶段的应用——让 LLM 在代码片段上下文中补全。提到 BM25 + Code Embedding 混合检索在变量名精确匹配场景的互补优势。对比 Code Search（Sourcegraph/GitHub Code Search）和 Code-RAG 的区别：前者是符号级/文本级检索，后者追求语义级检索+生成。

## Q40：有关联关系的文档怎么做 RAG？行业黑话或内部术语文档怎么做 RAG？

### 考察点
考察候选人处理非理想文档场景的应变能力——关联文档涉及图结构建模，黑话术语涉及领域适配，这两者都是 RAG 从 Demo 到生产的关键鸿沟。

### 解答思路
1. 对关联关系文档，按关系类型分层给出三种方案。
2. 对黑话/术语文档，从查询侧、索引侧、模型侧三个方向给出解决路径。
3. 点明两个问题在深层是一致的——都是标准 Embedding 无法捕捉的特殊语义信号。

### 参考答案
**关联关系文档的 RAG 策略**——按关系强度分三层：（1）显式引用关系（如文档 A 引用文档 B）：构建引用图，检索时沿引用边扩散 1-2 跳，将引用链上的文档一并加入候选集。可用图的 PageRank 或 HITS 算法为高频被引文档赋予更高权重。（2）实体关系（如公司 A 收购公司 B、API A 调用 API B）：用 LLM 或 NER 模型从文档中抽取 SPO 三元组（主体-谓词-客体），存入图数据库（Neo4j/NebulaGraph），检索时向量检索+h图遍历双路融合——向量检索命中实体后，沿图边获取关联实体及其文档。（3）层次关系（主文档-子文档、父类-子类）：采用层级索引结构，子 chunk 索引关联父 chunk ID，检索命中子层时同时返回父层和兄弟节点，构建"局部语境包"。

**行业黑话/内部术语的 RAG 策略**——核心问题是通用 Embedding 模型的训练语料中不包含这些术语，导致语义向量偏移甚至失效。三条路径：（1）查询侧改写：构建术语-通用表达映射表（如"水位"="资源利用率"），在 query 阶段自动将黑话替换为通用表达，再做 Embedding 检索。这要求术语标准表达映射表持续维护。（2）索引侧增强——Contextual Retrieval（Anthropic 方案）：在 chunk 入库前，用 LLM 为每个 chunk 生成一段"情境说明"，说明这个 chunk 在什么上下文中、用到了哪些领域术语及其含义。将情境说明与原始 chunk 拼接后一起向量化。这样即使原始文本充满黑话，情境说明中的通用语言描述也能提供正确的语义锚点。（3）模型侧微调：收集领域内的（query, positive_doc, negative_doc）三元组，用对比学习在通用 Embedding 上做 LoRA 微调，让模型学会本领域的语义映射。推荐使用 BGE、E5 系列开源的通用 Embedding 作为基座，微调通常只需 5000-10000 条领域样本即可见效。

**加分项**：讨论 GraphRAG（微软）的全局/局部检索双重模式在关联文档场景的落地。分析 ColBERT 的 late interaction（Token-level 交互）为何对术语密集型检索更友好——因为术语本身作为 token 直接参与匹配。提到多义词术语消歧——同一术语在不同上下文中的不同含义，需要用上下文窗口辅助判断当前应映射到哪个标准表达。

## Q41：什么是查询改写？什么是查询扩展？什么是自查询？

### 考察点
考察候选人对 RAG 查询端优化的三个核心概念的精确区分能力，以及在实际场景中选择和组合使用这些策略的判断力。

### 解答思路
1. 用一句话精确定义每个概念，说明各自解决什么问题。
2. 用对比表格或关键差异描述清晰区分三者。
3. 给出组合使用的工程实践。

### 参考答案
这三个概念是 RAG 查询优化的三把利刃，各有专攻：

**查询改写（Query Rewriting）**：将用户的原始 query 转化为更适合检索的等价表达。解决的问题是用户输入与文档表达之间的"语言鸿沟"——用户用口语化、省略化、指代化的方式提问，但知识库文档用的是书面化、完整化的表达。常见操作包括：指代消解（多轮对话中"它的价格"→"iPhone 15 Pro 的价格"）、口语转书面语（"这玩意咋用"→"产品的使用方法"）、实体标准化。核心原则是"语义等价变换"——改写前后含义不变，只是表达方式更规范。

**查询扩展（Query Expansion）**：在原始 query 的基础上扩充相关词汇或生成子查询。解决的问题是"词汇匹配的表征不足"——用户 query 可能只覆盖了相关文档的部分关键词，需要扩展来扩大召回面。经典方法：同义词扩展（WordNet）、LLM 生成多个等价问题（Multi-Query）、第一轮检索的伪相关反馈（从 Top-N 文档中提取高频词）、HyDE 生成假设答案用其 Embedding 检索。核心原则是"语义泛化"——在保持语义不偏离的前提下扩大匹配范围。

**自查询（Self-Query Retrieval）**：LLM 从自然语言 query 中自动提取结构化过滤条件，将检索转化为"语义查询 + 元数据过滤"的组合。解决的问题是用户 query 中隐含的结构化约束——"2024年关于Transformer的视频"包含时间、主题、内容类型三个约束。LLM 输出类似 `{query: "Transformer", filter: {year: 2024, type: "video"}}` 的结构，向量数据库据此做带过滤的向量检索。

三者核心区别：改写是"去噪"（让 query 更规范）、扩展是"加宽"（让 query 覆盖面更大）、自查询是"分解"（把 query 拆成语义部分和结构化部分）。工程上三者通常组合使用——先用自查询提取元数据过滤，再用查询改写净化语义表达，最后用查询扩展增加召回广度。

**加分项**：讨论 Multi-Query Retrieval 作为查询扩展的工程实现（并行检索多条改写 query，合并去重）。提到意图识别在查询改写中的作用——事实型查询做精准改写，探索型查询做广泛扩展。Analyze 假设文档 Embedding（HyDE）与查询扩展的内在联系——本质上也是扩展的一种特殊形式。

## Q42：在构建知识库时，文本切块策略至关重要。你会如何选择合适的切块大小和重叠长度？这背后有什么权衡？

### 考察点
考察候选人对 Chunking 策略的工程实践能力和参数调优方法论，评估其是否理解切块大小与重叠长度背后的精度-完整性权衡，以及是否具备系统化的参数选型方法论。

### 解答思路
1. 分析切块大小选择的影响因素和推荐取值范围。
2. 阐明重叠长度的作用机制和设置原则。
3. 给出系统化的参数选型方法论和差异化策略矩阵。

### 参考答案
切块大小（chunk_size）的选择是检索精度与上下文完整性的核心权衡。影响因素：（1）Embedding 模型的有限上下文窗口——主流模型（text-embedding-3-small/large、bge-large）在 256-512 tokens 范围内编码质量最优，超过 8192 后尾部信息衰减严重；（2）文档内容结构——代码适合按函数边界（128-512 tokens），技术文档适合按章节（512-1024 tokens），FAQ 适合按 Q&A 对（256-512 tokens）；（3）用户 query 典型长度——短 query（5-15 tokens）配小 chunk 更精准，长 query（20+ tokens）配大 chunk 能捕获更丰富的上下文；（4）下游 LLM 上下文预算——chunk 越大单块信息越多，但能塞进 Prompt 的块数越少。推荐通用场景 256-512 tokens，需要综合推理的场景 512-1024 tokens，代码场景 128-512 tokens。极端值风险：过小（<128 tokens）导致语义碎片化，过大（>2048 tokens）导致向量表示的语义信号被稀释。

重叠长度（chunk_overlap）的核心作用是防止关键信息在切分边界处被截断——一个答案可能刚好跨越两个 chunk 的分界点，没有重叠就永远无法被完整召回。常用策略：（1）固定比例——chunk 大小的 10%-20%，如 512 token chunk 配 50-100 token 重叠；（2）句边界感知——重叠不跨句，保证每个 chunk 以完整句子起止；（3）滑动窗口——固定步长（chunk_size - overlap）滚动切分，保证每个 token 至少出现在 N 个 chunk 中。但重叠不是越大越好：过大会导致索引膨胀（存储和检索成本线性增加），且同一答案块可能以高重复率出现在多个 chunk 中，需在检索阶段做好去重。通常 10%-15% 是最佳平衡点。

系统化选型方法论：（1）准备领域标注评测集（30-50 个典型问题和标准答案）；（2）建立参数网格：chunk_size 取值 [128, 256, 512, 1024]，overlap 取值 [0, 10%, 20%, 30%]，分块策略取值 [固定大小、句边界、段落、语义]——共计 4×4×4=64 组；（3）机器批量构建索引-检索-生成，自动化计算 Recall@5 和 Answer-F1；（4）绘制参数-效果曲线，选择精度和成本的最佳平衡点；（5）最终输出按文档类型差异化的分块策略矩阵，写入系统配置，新文档自动应用对应策略。

**加分项**：讨论 Semantic Chunking 的原理——计算相邻句子的 Embedding 余弦相似度，在相似度下降幅度超过阈值的点切分，实现语义边界感知的动态切块。提到 Agentic Chunking——用 LLM 动态判断语义完整的切分位置，适合对质量要求极高的结构化文档。对比 LangChain RecursiveCharacterTextSplitter（基于字符分隔符的递归切分）和 LlamaIndex SentenceSplitter（基于句子 token 数的切分）的工程取舍。

## Q43：如何选择一个合适的嵌入模型？评估一个 Embedding 模型的好坏有哪些指标？

### 考察点
考察候选人对 Embedding 模型选型的工程判断力，以及是否建立系统化的评估指标框架，而非盲目跟风使用最新模型。

### 解答思路
1. 分析选择 Embedding 模型需要考虑的核心维度（任务类型、语言、维度、性能、成本）。
2. 列出评估 Embedding 模型的关键指标及其含义。
3. 给出模型选型的实操流程和常用基准榜单。

### 参考答案
选择嵌入模型需要从多个维度综合考虑：（1）任务匹配度——检索（Retrieval）场景需要模型在语义相似度上有良好表现，聚类/分类场景则更关注类内紧凑性。MTEB Leaderboard 提供了按任务类型（Retrieval、STS、Clustering、Classification、PairClassification、Reranking、Summarization）的分类评测，应优先参考与自身场景匹配的子榜单。（2）语言支持——中文场景推荐 bge-large-zh、stella-base-zh、text2vec-large-chinese 等中文优化模型，多语言场景可选 multilingual-e5-large 或 Cohere embed-multilingual-v3。（3）向量维度与推理速度——高维度（1024/1536）通常表达能力更强但计算成本更高，低维度（384/512）速度快、存储成本低。OpenAI text-embedding-3 支持 Matryoshka 表示学习，可从 3072 维截断到 256 维而保持 90%+ 性能。（4）上下文窗口——不同模型支持的最大 token 数差异大（bge 系列 512，e5 系列 512-8192），需与分块策略匹配。（5）部署方式——API 模型（OpenAI、Cohere）开箱即用但成本随规模线性增长，本地部署模型（bge、e5）前期投入高但长期成本可控且数据不出域。

评估指标方面：（1）NDCG（Normalized Discounted Cumulative Gain）——考虑排序位置权重的排序质量指标，最贴近检索场景真实效果；（2）Recall@K——前 K 个结果中包含正确答案的比例，K 通常取 5/10/20；（3）MRR（Mean Reciprocal Rank）——第一个正确答案排名的倒数均值，衡量系统找到答案的速度；（4）MAP（Mean Average Precision）——各查询平均精度的均值；（5）Spearman 相关系数——用于 STS 任务，衡量预测相似度与人工标注排名的相关性。实操中建议用领域标注数据构建评测集，对比候选模型的 NDCG@10 和 Recall@5，同时测量 P50/P99 推理延迟，在精度和延迟间找到平衡点。

**加分项**：了解 Matryoshka Embedding 原理——在训练时对不同截断维度的子向量同时施加损失函数，使模型学到多粒度的层级表示，推理时可按需截断维度而无需重新训练。了解 LLM-based Embedding（如直接用 GPT/Claude 生成嵌入向量）的趋势和适用场景——质量超高但延迟和成本是传统 Embedding 模型的 100-1000 倍，适合离线评测或对召回质量要求极高的场景。

## Q44：除了基础的向量检索，你还知道哪些可以提升 RAG 检索质量的技术？

### 考察点
考察候选人对 RAG 检索增强技术的广度了解，评估其是否掌握从 naive RAG 到 advanced RAG 的技术演进路线。

### 解答思路
1. 列举查询端增强技术（Query Rewriting、Query Expansion、HyDE 等）。
2. 列举检索端增强技术（Hybrid Search、Re-rank、Multi-hop Retrieval 等）。
3. 列举索引端增强技术（Hierarchical Index、Small-to-Big、ColBERT 等）。

### 参考答案
围绕 RAG 检索质量的提升，可从前端（Query）、中端（Retrieval）、后端（Index）三个层面展开：

查询端增强：（1）Query Rewriting——使用 LLM 将用户的模糊/口语化查询改写为更精确的检索查询，消除歧义、补充上下文。（2）Query Expansion——基于同义词库或 LLM 生成多个语义等价查询，合并多路检索结果。（3）HyDE——先生成一篇假设性答案文档，再用该文档的向量去检索，在 query 与文档不在同一语义空间时效果显著。（4）Multi-Query Retrieval——将原始查询分解为多个子查询并行检索后合并去重。（5）Step-back Prompting——先生成更高层次的抽象问题再检索，适合回答需要背景知识的复杂问题。

检索端增强：（1）Hybrid Search——混合稀疏检索（BM25/BM25S）和稠密检索（向量相似度），通过倒数排名融合（RRF）或加权求和合并结果，解决向量检索对关键词匹配不敏感的问题。（2）Re-rank——用 Cross-encoder 重排序粗召结果，将 top-100 精排到 top-5，显著提升精度。（3）Self-Query Retrieval——LLM 先解析查询中的元数据过滤条件（时间、作者、类别等），结合语义检索和结构化过滤。（4）Time-weighted Retrieval——对时间久远的结果降权，优先返回时效性更优的结果。

索引端增强：（1）Hierarchical Chunking——父子索引结构，父 chunk 存储上下文，子 chunk 用于检索；检索到子 chunk 后返回父 chunk 保证上下文完整。（2）Small-to-Big / Sentence Window——检索小粒度（句子级），返回大粒度（段落级）。（3）ColBERT 等 Late Interaction 模型——在 token 级而非 embedding 级计算交互，兼顾离线索引和在线交互的优势。（4）Graph Index——基于文档间的引用/超链接关系构建图索引，支持图遍历增强检索，适合结构化关联文档。（5）Multi-Representation Index——同一文档生成摘要向量、关键词向量、语义向量等多种表示，多路融合提高覆盖面。

**加分项**：介绍 RAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval）——对文档进行递归摘要聚类构建树状索引，支持跨粒度的多尺度检索，在 multi-hop 问题上效果突出。提到 Contextual Retrieval——Anthropic 提出的对每个 chunk 添加上下文前缀（文档标题、章节摘要）的方法，实验证明可显著降低检索失败率。

3. 系统化列举缓解策略，涵盖 Prompt 层、检索层、模型层。

### 参考答案
"Lost in the Middle"是指大语言模型在处理长上下文时，对位于上下文中间位置的信息关注度显著低于开头和结尾信息的现象。这是 Liu et al.（2023）在论文 "Lost in the Middle: How Language Models Use Long Contexts" 中系统验证的结论——当相关信息位于 Prompt 的开头（Primacy Effect）或结尾（Recency Effect）时，模型利用效果最好；位于中间时性能急剧下降，甚至低于没有该信息时的表现。这对 RAG 系统有直接冲击：当检索到 10 个 chunk 拼接成 Prompt 时，关键信息恰好落在中间 chunk 的概率很高，导致模型忽略正确答案。

原因分析：Transformer 的注意力机制在长序列上存在位置偏差，中间位置的 token 接收到的梯度信号和注意力权重天然弱于首尾位置；此外，预训练语料中信息分布也倾向于开头和结尾（文章首段和末段包含更多关键信息），强化了这种偏差。

缓解策略：（1）Re-rank 后截断——通过 Cross-encoder 将最相关的 chunk 排在前面，确保关键信息出现在 Prompt 的开头位置。通常只保留 top 3-5 个 chunk，控制上下文长度。（2）逆向重排——将相关性较低的 chunk 放在中间，最相关的放在首尾。（3）分块重组——将检索结果分成多个小组分别送入 LLM 生成部分答案，最后合并，避免单次 Prompt 过长。（4）Summary Buffer——对中间位置的 chunk 用摘要替代完整内容，缩小 Prompt 长度。（5）显式位置提示——在 Prompt 中标注"请注意，以下信息是回答问题的关键"等方式引导模型注意力。（6）Attention 机制层面的改进——使用 RoPE 等改进版位置编码，或选择在长上下文上表现更好的模型（Gemini 1.5 Pro、Claude 3.5 Sonnet 等对此问题有所缓解）。

**加分项**：了解 StreamingLLM 和 LongRoPE 等学术工作如何从架构层面解决注意力分布不均的问题。提到 LM-Infinite（Han et al., 2024）提出的 λ 形注意力掩码——在保留首尾 token 的同时，通过间隔采样中间 token 控制注意力分散，使模型在无限长输入上仍能保持推理能力。

## Q46：在什么场景下，你会选择使用图数据库或知识图谱来增强或替代传统的向量数据库检索？

### 考察点
考察候选人对图数据库/知识图谱与向量数据库的互补关系理解，以及能否根据实际业务场景做出合理的架构选型。

### 解答思路
1. 对比向量检索和图数据库检索的核心差异与互补性。
2. 列举适合使用图数据库/知识图谱的具体场景。
3. 提供混合架构（GraphRAG）的设计思路和工程实践。

### 参考答案
传统向量数据库基于语义相似度检索，擅长"这段文字讲的是什么"，但无法处理"A 和 B 之间是什么关系"这类需要结构化推理的查询。图数据库/知识图谱适合以下场景：

优先使用知识图谱的场景：（1）需要精确关系推理——如"某药物的副作用涉及哪些代谢通路"、"某人与某公司的控股关系链"——这些 query 需要沿着实体间关系链路进行多跳遍历，向量相似度无法完成。（2）结构化数据关联查询——企业内部的组织架构、产品零部件 BOM 表、供应链上下游关系。（3）逻辑一致性要求高——法律条款引用、合规审查场景，需要严格按关系抽取，不能依赖语义近似。（4）知识可解释性和可审计性——图路径本身可解释检索依据，而向量检索只能给出相似度分数。

混合架构（GraphRAG）的设计思路越来越受关注。微软 GraphRAG 的做法是先构建知识图谱（实体-关系-实体三元组），然后利用社区检测算法（Leiden）识别实体集群，再为每个社区生成摘要；检索时结合图遍历和社区摘要，实现全局性问题的回答——比如"数据集的主要主题是什么"这类需要概括全文而非检索片段的总结性问题。腾讯 GraphRAG（Edge-base）则在知识图谱中融入图嵌入（如 Node2Vec、R-GCN）实现级联检索——先通过向量检索快速定位起始实体节点，再做 1-2 跳图遍历扩展上下文，最后将图上下文和原始文档拼接送入 LLM 生成。

工程选型建议：如果 80% 以上的 query 是"XX 是什么"的知识点查询，向量数据库 + BM25 混合检索即可满足；如果频繁出现"XX 和 YY 的关系""从 A 到 B 的路径"等关系型查询，或者有高质量的结构化数据，应考虑引入图数据库增强。实际方案常以向量检索为入口（快速定位），图检索为扩展（补充关系上下文），形成"从语义到结构"的二阶段检索流程。

**加分项**：了解 Property Graph（Neo4j/LangChain GraphCypherQAChain）和 RDF 三元组（Apache Jena/Amazon Neptune）两种知识图谱存储模型的差异和选择。了解 LlamaIndex 的 KnowledgeGraphIndex 和 LangChain 的 GraphCypherQAChain 的工程化实践。提到 LLM + GNN（图神经网络）联合推理的前沿方向。

## Q47：传统的 RAG 流程是"先检索后生成"，你是否了解一些更复杂的 RAG 范式，比如在生成过程中进行多次检索或自适应检索？

### 考察点
考察候选人对 Advanced RAG 范式的系统性了解，评估其是否跟踪学术前沿并具备将新范式落地的工程判断力。

### 解答思路
1. 梳理从 Naive RAG 到 Advanced RAG 的演进路线图。
2. 分类详述 Self-RAG、CRAG、Adaptive RAG、Iterative RAG 等范式的核心机制。
3. 对比各范式的适用场景和工程权衡。

### 参考答案
Naive RAG 的"一次检索一次生成"模式在复杂场景中暴露出明显不足。学术界和工业界发展出了多种更复杂的范式：

（1）Self-RAG（Self-Reflective RAG）：在生成过程中引入自我反思机制——模型通过生成特殊的反思 token（如 `<Retrieve>`、`<Relevant>`、`<Supported>`、`<Partially>`、`<Irrelevant>`）来动态决定是否需要检索、检索结果是否相关、生成内容是否有据可查。每一步生成后模型自我评判，若发现不足则触发新的检索或修正。核心价值在于让模型"知道自己不知道"。工程实现上需训练 LLM 学会生成反思 token，推理成本比 Naive RAG 高 2-3 倍。

（2）CRAG（Corrective RAG）：在检索质量评估环节引入纠错机制——对检索到的文档首先做相关性评估（Auto-grading），若相关则继续生成；若不相关则触发 Query Rewriting 后重新检索；若仍未找到相关信息则降级为"纯模型知识回答"或 Web Search。通过 T5-large 等轻量模型做检索质量评估器（Retrieval Evaluator），避免将无关上下文送入 LLM 引发幻觉。

（3）Adaptive RAG：根据问题复杂度和检索质量自适应选择策略——简单事实查询走标准 RAG 单轮检索，复杂多步推理问题走多轮检索，主观/开放性问题减少检索依赖。使用分类器（LLM 或轻量模型）在检索前判断问题类型，动态路由到不同策略。

（4）Iterative RAG / FLARE（Forward-Looking Active REtrieval）：在生成过程中按句子或段落粒度主动预判是否需要检索，需要则实时检索并插入到后续生成中。适合需要综合多个信息来源的长篇生成任务，如研究报告、技术综述等。

（5）Agentic RAG：将检索建模为 Agent 的 tool-use 行为——模型自主决定何时调用检索工具、调用几次、如何综合多次检索结果。这是目前最灵活且工程落地最活跃的范式，GPT-4-tools、LangGraph Agent、LlamaIndex Agent 均可实现。

范式选择建议：事实型问答用 Naive/CRAG，长篇生成用 Iterative RAG，开放域复杂推理用 Self-RAG 或 Agentic RAG。Agentic RAG 目前是工程实践的主流方向，因其灵活性最高且与工具调用生态天然兼容。

**加分项**：了解 RQ-RAG（Retrieval-augmented Query-Rewriting RAG）——将复杂问题显式拆解为多个可检索的子问题，迭代检索后整合回答。提到 IRCoT（Interleaving Retrieval with Chain-of-Thought）——将 CoT 推理与检索交替进行，每步推理后检索相关知识验证，适合多跳推理。对比 DSPy 框架如何通过声明式编程优化 RAG Pipeline 中的检索策略编排。

## Q49：RAG 召回优化：你们 RAG 召回存在什么问题？怎么优化的？用的什么向量数据库？怎么保证召回的准确性避免 Agent 答非所问？

### 考察点
考察候选人在生产环境中对 RAG 召回质量问题的诊断、优化手段以及向量数据库选型的实战经验，重点看是否具备端到端的召回质量保障体系。

### 解答思路
1. 系统梳理召回问题的分类（召回不足/召回错误/召回偏差）及其根因。
2. 按优化层次递进介绍：Query 侧优化、索引侧优化、检索策略优化。
3. 说明向量数据库选型逻辑以及端到端质量保障机制（包括评测与监控）。

### 参考答案
我主导的 RAG 系统在初期面临三大召回问题：第一，召回偏差——用户的自然语言 Query 与文档库中的技术术语不匹配，比如用户说"怎么跑得更快"而文档中是"性能优化方案"，导致语义相似度偏低。第二，召回不足——单路向量检索的 Top-20 结果中有时完全没有正确答案，尤其在跨文档关联场景（如某个配置项的解释分散在多篇文档中）。第三，召回冗余——对于简单事实型查询，返回大量语义相关但内容重复的 chunk，挤占上下文窗口。

优化按三层推进：（1）Query 侧——引入 Query Rewriting 模块，用 LLM 将口语化/模糊查询转化为接近文档风格的精炼查询，同时做查询扩展（同义词、缩写展开、技术术语对齐）。对于需要多步推理的问题，使用子问题分解（Decomposed Retrieval）。（2）索引侧——从简单的固定大小分块转向语义感知分块（Semantic Chunking），引入父子索引（Parent-Child Index）——用小粒度 chunk 做检索，返回大粒度父文档给 LLM，兼顾召回精度与上下文完整性。同时对标题、摘要、正文建分层索引，支持按标题优先召回。（3）检索策略——从单路向量检索升级为混合检索（Hybrid Retrieval）：Dense Vector（BGE-large）+ Sparse BM25 + Multi-granularity，0.3:0.4:0.3 权重融合。增加 Rerank 模块（BGE-Reranker-v2-m3），Top-20 粗筛后重排取 Top-5。

向量数据库选型对比了 Milvus、Qdrant 和 Weaviate，最终选择 Milvus——主要考量：十亿级向量规模支持、GPU 索引加速（IVF_PQ + HNSW）、与 LangChain/LlamaIndex 生态集成成熟、中文社区的文档和案例丰富。

保证召回准确性的兜底机制：（1）设定相似度阈值 0.75，低于阈值的召回结果直接丢弃，触发"无相关知识"响应而非强行回答；（2）给 LLM 的 Prompt 中嵌入引用溯源要求，每句回答必须标注引用来源 id，便于人工审核追溯；（3）建立 Golden Dataset 做离线回归评测，每次索引变更或策略调整后自动跑评测，召回率波动超过 5% 则告警；（4）线上加入用户反馈闭环，对"踩"的回答自动入库复检。

**加分项**：了解 Multi-Vector Embedding（如 ColBERT 的 token-level embedding）与 Single-Vector 的差异，在需要细粒度匹配的场景（如法律条款检索）效果显著。提到反思机制（Reflection）——Agent 拿到召回结果后先自检"这些信息是否足以回答问题"，不足则触发二次检索或澄清询问，避免在信息不充分时强行回答。

## Q50：Dify 的 Knowledge Base（知识库）功能是如何工作的？它和 RAG 技术之间是什么关系？

### 考察点
考察候选人对 Dify 知识库技术原理的理解深度，能否区分"产品功能"与"底层技术"的层次关系，以及是否能将 Dify 的知识库实现映射到标准 RAG 流程中。

### 解答思路
1. 从产品视角说明 Dify 知识库的功能链路（上传→处理→检索→生成）。
2. 从技术视角拆解其底层 RAG 实现（分块、向量化、检索策略、重排）。
3. 阐述 Dify 知识库与标准 RAG 的关系——Dify 知识库是 RAG 的产品化封装。

### 参考答案
Dify 的知识库功能从产品角度看是一个完整的文档知识管理→问答 Pipeline，用户操作链路为：上传文档（PDF/Word/Markdown/网页等）→ 选择处理模式 → 等待处理完成 → 在对话型应用中以"上下文"的方式挂载知识库 → 系统自动完成检索增强生成。

从技术底层拆解，Dify 知识库本质是一个标准 RAG Pipeline 的产品化封装，包含以下核心环节：（1）文档解析：使用 Unstructured 或自研解析器处理多种格式，提取纯文本并识别文档结构（标题层级、表格、列表）。（2）分块策略：提供自动模式和自定义模式，自动模式下基于语义边界（段落、标题）进行分段，支持设置最大 chunk 长度（默认 800 tokens）和重叠区域。（3）向量化与索引：当前主力 Embedding 模型可选择 OpenAI text-embedding-ada-002 或通过 OneAPI 接入国产模型（如智谱 Embedding-2），向量数据库默认使用 Qdrant 或 Weaviate，索引存储于 Dify 服务端。（4）检索模式：支持三种——全文检索（基于关键词 BM25）、向量检索（语义相似度）、混合检索（融合两者），同时支持 Top-K 裁剪和相似度阈值过滤。（5）重排序：可配置 Rerank 模型（如 Cohere Rerank 或 BGE-Reranker），对粗筛结果精排后送入 LLM 上下文。（6）Prompt 编织：将检索到的文档片段 + 历史对话 + 用户 Query 组装成结构化的 System/Context/User Message，注入 LLM 生成答案。

Dify 知识库与 RAG 技术的关系：Dify 知识库是 RAG 技术的产品化应用，RAG 是 Dify 知识库的技术内核。二者是"产品-技术"的层次关系。Dify 的价值在于将 RAG 的技术复杂度（分块策略调优、向量数据库运维、Rerank 配比、Prompt 工程）封装为可视化配置项和最佳实践预设，降低 RAG 落地门槛。但这也意味着深度定制受限于平台框架——当遇到特殊场景（如代码索引、多模态检索、图数据库增强）时需要突破 Dify 原生能力。

**加分项**：了解 Dify 知识库的高级模式——"Q&A 分段模式"，允许用户将文档预拆分为问答对，检索时直接匹配问题返回答案，比传统 chunk 检索更精准。提到 Dify 的 Metadata Filtering 能力——通过对文档打标签（如版本号、产品线、语言等元数据），在检索时做前置过滤，缩小检索范围，在大型知识库场景下效果显著。

## Q51：当一个基于 RAG 的问答系统回答错误时，你会如何排查问题？可能的原因有哪些？

### 考察点
考察候选人对 RAG 系统的全链路故障诊断能力和系统化排查思维，同时评估其是否具备从"表象错误"反推"根因"的实战经验。

### 解答思路
1. 建立全链路排查框架（检索→生成→后处理三段式）。
2. 逐环节枚举常见根因和排查手段。
3. 给出系统化的 debug 工具链和监控体系。

### 参考答案
我遵循"输入→检索→生成→输出"的全链路排查框架，按优先级依次定位：

第一层：检索质量排查（最常见，约占 60% 错误根因）。（a）召回遗漏——正确答案所在文档没有被召回。排查方法：用 Query 单独调用 Embedding API 和向量库，检查 Top-K 结果中是否有正确答案。常见原因：分块过小导致关键上下文被割裂、Embedding 模型不适用（如英文 Embedding 处理中文文本）、Query 表述与文档风格差异大（用户说"崩了"文档写"服务异常终止"）。（b）召回错误——返回了语义相似但不相关的 chunk。排查方法：查看每次召回的 chunk 内容和其元数据（来源文档、分块位置）。常见原因：通用 Embedding 模型对专业领域语义理解不足、向量空间中的语义偏差、分块重叠区域过大导致内容稀释。（c）Top-K 排序问题——正确答案在召回列表中但排名靠后，被截断。排查方法：扩大 Top-K 观察正确答案的排名位置。常见原因：缺少 Rerank 阶段或 Rerank 模型与 Embedding 模型不匹配。

第二层：生成质量排查（约占 30%）。（a）上下文污染——LLM 被召回的错误或过时信息误导。排查方法：将实际注入 LLM 的 Prompt 日志 dump 出来，逐条检查召回的 chunk 内容是否含矛盾信息。（b）幻觉生成——正确答案在上下文中但 LLM 忽视或曲解。常见原因：上下文过长（Lost in the Middle 效应）、Prompt 结构混乱导致 LLM 关注偏移、模型自身能力不足（如小参数模型处理复杂推理）。（c）信息整合失败——正确答案分散在多个 chunk 中，LLM 无法完成跨片段推理。

第三层：数据与链路排查（约占 10%）。（a）知识过期——文档库未及时更新。（b）数据质量问题——原始文档含噪声、OCR 错误、格式异常。（c）工具调用错误——在 Agent 架构中，检索工具的参数（如 index_name、filter 条件）传递错误。

排查工具链：搭建 RAG 可观测平台（LangSmith / Phoenix / 自研），记录每次 Query 的完整链路信息——原始 Query、改写后的 Query、召回的 chunk 列表及分数、Rerank 后的排序、注入 LLM 的完整 Prompt、LLM 最终输出。支持单次 Trace 回放和批量分析。

**加分项**：提到"RAG 断点调试"概念——不是在回答错误后才排查，而是在开发阶段就构建好评测集（Golden Dataset），每次策略变更后自动跑回归评测，确保改动不会引入新问题。了解 RAGAS 等自动评测框架的指标（Context Precision、Context Recall、Faithfulness、Answer Relevancy）在故障排查中的使用——当 Faithfulness 低但 Context Recall 高时，问题在 LLM 生成侧而非检索侧。

## Q52：RAG 落地时，数据清洗与切分的核心要点和避坑方法有哪些？

### 考察点
考察候选人对 RAG 数据预处理环节的深入理解，数据质量直接影响 RAG 系统的检索效果上限，此问评估其是否踩过坑、是否有行之有效的预处理方案。

### 解答思路
1. 从数据清洗角度展开：格式归一化、噪声去除、元数据提取。
2. 从文本切分角度展开：切分策略选择、粒度控制、语义完整性保证。
3. 总结常见坑点与规避方法。

### 参考答案
数据清洗核心要点：（1）格式归一化——PDF/Word/HTML/Confluence 等多源异构数据需统一转为结构化文本。PDF 是最大挑战点：扫描件需走 OCR 管道（PaddleOCR 中文效果好），双栏排版需做布局分析（LayoutParser），表格需抽取为 Markdown 表格或 JSON 保留结构信息，否则表格数据进入向量库后完全不可检索。（2）噪声去除——非内容元素（页眉页脚、水印、页码、导航栏）必须剔除，它们被 chunk 化后会污染语义向量。通用做法是用 NLP 规则（正则匹配）或训练一个二分类模型（内容 vs 噪音）做过滤。（3）元数据提取——文档标题、章节、版本号、更新时间、作者、部门归属等元数据在切分前提取并随 chunk 存储到向量库的 payload 中，这是后续做 Metadata Filtering 的基础。（4）文本质量检查——空内容/乱码检测、去重（文档间和文档内）、敏感信息脱敏。

文本切分核心要点：（1）切分策略选择——固定大小切分最简单但最容易割裂语义，适合结构均匀的文本；基于分隔符（句号/换行）的递归切分兼顾简单性和语义；语义切分（基于 Embedding 相邻句子的余弦相似度变化检测语义边界）精度最高但成本最高。实践建议：长文档先按标题层级做 Section Split，每个 Section 再按段落做语义切分。（2）粒度选择——chunk_size 要与 Embedding 模型的 max_length 匹配（通常 512-1024 tokens），chunk 太小（<256 tokens）信息量不足难以独立理解，太大（>2048 tokens）语义被稀释导致检索精度下降。推荐 512 tokens 作为基准，长代码文档可放大到 1024。（3）重叠区域（Overlap）——一般设 chunk_size 的 10-20%，核心作用是避免关键句正好卡在两个 chunk 边界导致"两头都不够"。过大会增加冗余和存储成本，过小则边界问题依旧存在。

常踩的坑与避法：（1）坑：直接把 PDF 全文 dump 为一段文本切分。避法：先解析文档结构（toc/heading/table/figure），再按结构层级切分。（2）坑：切完就把来源文档名忘了。避法：每个 chunk 必须存储 source_doc、page_number、section_title、chunk_index 等元数据，方便排障和溯源。（3）坑：静态切分，不随着文档更新而调整。避法：文档有更新时，对比新旧文档的 hash，只重建变更部分对应的 chunk，避免全量重建索引。（4）坑：忽视多语言混合文档（中英文混排）。避法：选择支持多语言的 Embedding 模型（如 BGE-M3），切分时用 Universal Sentence Segmenter 而非简单按句号分割。

**加分项**：了解 Vision-Powered Parsing——对于复杂排版的 PDF（尤其是学术论文、财务报告），传统解析器效果差，可用多模态 LLM（如 GPT-4V、Qwen-VL）直接"看"页面图片输出结构化 Markdown，但成本较高，适合高质量要求的小规模场景。提到 Agentic Chunking——用 LLM Agent 动态决定每条内容"应该放在哪里、和什么相邻"，而非预设静态规则。

## Q53：多模态用户信息的存储与使用方案？

### 考察点
考察候选人对多模态数据（文本/图片/音频/视频）在 RAG 和 Agent 系统中的统一存储、索引和检索架构设计能力，重点评估跨模态融合的实践经验。

### 解答思路
1. 定义"多模态用户信息"的范围（用户上传的图片、语音、视频、文档中的图表等）。
2. 设计统一存储方案（原始文件存储 + 多模态向量索引）。
3. 阐述 Agent 如何使用这些多模态信息。

### 参考答案
多模态用户信息的存储与使用需要设计"原始存储 + 向量索引 + 跨模态桥接"三层架构：

第一层——原始文件存储：（1）图片/视频/音频等原始文件存入对象存储（OSS/S3/MinIO），生成唯一 file_id 并返回可访问 URL。（2）文本类（对话记录、上传的文档）存入结构化数据库（PostgreSQL）或文档存储（MongoDB），方便按用户/会话维度查询。（3）建立用户信息元数据表，记录 file_id、模态类型、上传时间、关联会话 id、业务标签等。

第二层——多模态向量索引：（1）为每种模态选择专用 Embedding 模型：文本用 BGE-M3 或 text-embedding-3-large；图片用 CLIP-ViT-L/14 或 SigLIP 生成视觉向量；音频先用 Whisper 转写为文本，再对转写文本生成文本向量，同时可对接 CLAP（Contrastive Language-Audio Pretraining）生成音频语义向量；视频采用关键帧采样（1fps）+ CLIP 编码各帧 + 时间戳标注，形成时序化视觉向量序列。（2）所有模态的向量统一存入支持多模态的向量数据库（Milvus 2.4+ 或 Qdrant），每个向量携带 modality 字段区分类型，支持按模态过滤检索。关键设计点：不同模态的向量维度可能不同（CLIP-768d vs BGE-1024d），Milvus 支持 Collection 级别的 schema 定制或创建多 Collection 按需查询。

第三层——Agent 使用方案：（1）Agent 接收到用户问题后，先通过意图识别判断是否需要检索多模态信息。（2）若问题涉及图片内容（如"我上次上传的截图里的那个错误码"），并行执行文本检索（在对话历史中找相关描述）+ 图片检索（CLIP 编码后用相似度匹配）。（3）检索到的多模态结果需要在 Prompt 中差异化处理：文本直接注入上下文；图片将 URL 传入支持多模态的 LLM（GPT-4V/Claude 3.5/Qwen-VL）由模型直接理解；音频先给转写文本，同时将原始音频 URL 提供给 LLM（如果模型支持音频输入）。（4）对于用户长期偏好等非实时信息，可预先抽取为结构化标签存入用户画像表，避免每次都做多模态检索。

**加分项**：了解 Magic Pocket 或 BridgeTower 等跨模态对齐模型，可将文本和图片映射到同一向量空间实现统一检索，省去多 Collection 的管理复杂度。提到多模态 RAG 的挑战——不同模态的语义 gap 仍然存在，纯向量相似度匹配有时不如"先转文字再检索"准确，需要设计回退策略（Fallback Strategy），向量检索分数低时自动降级为 OCR/ASR 转换后的文本检索。

## Q54：多模态知识检索的实现方式？

### 考察点
考察候选人对多模态知识检索（不仅限于文本）的系统设计能力，包括不同模态的 Embedding 对齐、混合检索、以及检索结果的跨模态融合策略。

### 解答思路
1. 梳理多模态知识检索的核心技术路径（统一嵌入空间 vs 跨模态桥接）。
2. 详述典型实现架构（索引层、检索层、融合层）。
3. 讨论不同场景下的技术选型与工程权衡。

### 参考答案
多模态知识检索的核心挑战在于不同模态（文本、图片、音频、视频、表格）数据天然存在于不同的语义空间中，无法直接用同一度量标准进行检索。业界有三条主流技术路径：

路径一：统一嵌入空间（Unified Embedding Space）。使用 CLIP 类模型（OpenCLIP、SigLIP、EVA-CLIP、Chinese-CLIP）将文本和图片映射到同一向量空间。CLIP 通过对比学习训练，使配对的图文在向量空间中靠近、非配对的疏远。实现时：对所有文本 chunk 用 CLIP Text Encoder 编码，所有图片用 CLIP Vision Encoder 编码，存入同一向量数据库 Collection。用户 Query 用 Text Encoder 编码后，即可在同空间内同时召回文本和图片。优点：实现简单、检索效率高。局限：CLIP 的对齐粒度是"整图-整句"，对于图中局部信息（如 PPT 中的一行小字）检索效果差。

路径二：跨模态桥接（Cross-modal Bridging）。当无法将不同模态映射到同一空间时，使用中间模态做桥接。最常见的做法是"先转文字再检索"：（a）图片：用 OCR（PaddleOCR/EasyOCR）+ 图片描述模型（BLIP-2/LLaVA）生成文字说明，将 visual content 转为 textual description，再走文本 RAG 管道。（b）音频/视频：先用 ASR（Whisper/FunASR）转写为文本，视频额外做关键帧抽取后用视觉理解模型生成帧描述文本。（c）表格/图表：用 Table Transformer 检测表格区域，或用多模态 LLM 直接生成表格的自然语言摘要。（d）所有模态转换后的文本统一走文本检索 + 文本 LLM 生成，无需多模态 LLM。优点：兼容现有文本 RAG 基础设施，检索精度高（因为用到了 OCR 级细粒度信息）。局限：转写环节引入级联误差，图片中不可名状的信息（如颜色、布局、情感氛围）会丢失。

路径三：混合式（Hybrid Multi-modal Retrieval）。结合上述两条路径，两路并行检索后融合。（a）Text-to-Text 路：Query → 文本 Embedding → 文本库检索文本 chunk（含 OCR/ASR 转写的文本）。（b）Text-to-Image 路：Query → CLIP Text Encoder → 共享向量空间检索图片。（c）结果融合：使用加权融合或学习型的融合模型（如训练一个小型 Cross-Attention 网络），综合两路分数给出最终排序。实践中通常文本路权重更高（0.7），因为当前阶段文本检索的精度仍高于图片语义检索。

工程落地架构：索引层按模态分 Collection（text/ image/ audio /video 各一个），统一通过 API Gateway 接收 Query → 路由层判断需要检索哪些模态 → 并行检索 → 融合排序层做跨模态归一化 → 结果按模态类型拼装 Prompt（文本直接注入、图片 URL 传给多模态 LLM、音频/视频传转写文本 + 原始链接）。

**加分项**：了解 Multi-Vector 多模态检索（如 ColPali），它不像 CLIP 那样为整张图生成一个向量，而是为 PDF 页面的每个 patch 生成一个向量（类似 ColBERT 的 token-level 思想），在图文混排的文档检索场景（如学术论文、设计文档）中效果远优于传统方案。提到 Agentic Multimodal Retrieval——让 Agent 自主决定"看到这张图后是否需要进一步放大局部"、"检索到的视频是否需要快进到关键帧"，而非一次性检索返回结果就结束。

## Q55：什么是难负例（Hard Negatives）？如何挖掘？

### 考察点
考察候选人对 Embedding 模型训练/微调中核心数据工程问题——难负例的概念理解及实战挖掘策略，反映对检索系统精排能力的认知深度。

### 解答思路
1. 先定义难负例，对比随机负例和易负例的区别。
2. 阐述难负例挖掘的主要方法（静态挖掘 vs 动态挖掘）。
3. 说明难负例在训练中的应用与潜在风险。

### 参考答案
难负例（Hard Negatives）是指与正样本（相关的查询-文档对）高度相似但与查询不相关的文档。与随机负例（random negatives，如从语料库中随机采样无关文档）不同，难负例在语义空间中与正例距离很近，极易被模型误判为相关文档，因此对模型判别能力的训练价值最高。例如：查询"苹果手机最新型号"，一篇关于"苹果公司财报中提及手机业务"的文档可能因语义高度重叠而成为难负例，但它并不直接回答用户问题。

难负例挖掘的主要方法分为三大类：

（1）密集检索挖掘（Dense Retrieval Mining）：使用当前 Embedding 模型或跨模态编码器（Cross-Encoder）对所有候选文档打分，将得分排名靠前（Top-10~Top-100）但人工标注为不相关的文档作为难负例。Cross-Encoder 的全注意力机制使其判别精度远高于 Bi-Encoder，是更精准的难负例筛选器。经典实践如 ANCE（Approximate Nearest Neighbor Negative Contrastive Estimation），在每个训练 epoch 中异步重新构建索引并重新挖掘难负例，使负例随模型更新而"动态变难"。

（2）BM25 + 模型混合挖掘：先用 BM25 做词汇级召回，再从召回结果中人工或模型筛选出"字面匹配但语义不相关"的文档。该方法针对 Dense Retriever 的弱点——对关键词高度匹配但答案缺失的文档区分能力弱——尤其有效。

（3）合成生成：利用 LLM（如 GPT-4）生成语义接近但不包含正确答案的伪文档，用于定向强化模型对特定类型错误的判别能力。

应用注意事项：难负例比例不宜过高（通常总负例池中 10%-30% 为难负例），过多会导致训练不稳定或模型过于保守降低召回率。常见的训练策略是在一个 batch 内，除正例对外，将其他正例的文档作为该查询的 in-batch negatives，并补充少量难负例。训练时配合温度系数（temperature scaling）和难负例加权损失函数（如加权 InfoNCE Loss）可进一步提升效果。

**加分项**：了解难负例的"假阳性风险"——在自动化挖掘中，可能误将实际上相关的文档标为难负例（标注噪声），需引入人工校验环节或用多模型投票机制降低误标率。提到 Curriculum Learning 策略——训练初期用简单负例建立基本判别能力，中后期逐步引入难负例进行精细调优，避免早期训练崩溃。

## Q56：ColBERT 的 Late Interaction 机制是什么？

### 考察点
考察候选人对 ColBERT（Contextualized Late Interaction over BERT）核心机制的深入理解，以及其对检索效率与精度平衡的设计哲学。

### 解答思路
1. 对比 Early Interaction（Cross-Encoder）、No Interaction（Bi-Encoder）、Late Interaction 三类范式。
2. 详解 ColBERT 的 Query-Document Token-Level 交互计算流程。
3. 分析 Late Interaction 的效率优化方法（离线索引、近似搜索）。

### 参考答案
ColBERT 的 Late Interaction 机制是介于 Cross-Encoder（全交互，精度高但速度慢）和 Bi-Encoder（无交互，速度快但精度低）之间的折中方案。其核心思想是：将查询和文档分别独立编码为多个 Token-Level 向量（每个 token 一个向量），在检索的最后阶段才进行细粒度的 Token 级交互计算。

具体计算流程分为三步：

（1）查询编码：将用户查询 Q 输入 BERT，取最后一层所有 token 的输出，得到 |Q| 个 d 维向量，每个向量代表查询中一个 token 的上下文表示 $E_q = [q_1, q_2, ..., q_N]$。同时对特殊标记 [Q] 的输出用于后续高效初筛。

（2）文档离线编码：将所有文档 D 输入 BERT，同样取每个 token 的上下文表示 $E_d = [d_1, d_2, ..., d_M]$，存储所有 token 向量到索引。注意文档编码可完全离线完成，这是 ColBERT 实现在线检索效率的关键前提。

（3）Late Interaction 评分（MaxSim）：查询时，对查询的每个 token 向量 $q_i$，在文档的所有 token 向量中找余弦相似度最大的那个（即 MaxSim），再将所有查询 token 的 MaxSim 值求和，作为查询-文档的最终相关性分数：$S(Q, D) = \sum_{i=1}^{N} \max_{j=1}^{M} q_i \cdot d_j^T$。这个"迟到"的交互操作仅涉及轻量的向量点积和求和，无需重新通过 Transformer 推理。

实践中的两级检索策略：第一阶段用 [Q] 标记向量做粗筛（ANN 检索 Top-K），第二阶段对粗筛结果做完整的 MaxSim 精排。由于文档 Token 向量数量巨大（一篇文档可能有 512 个 token），ColBERT 使用向量量化（PQ，Product Quantization）压缩存储，并借助 PLAID 引擎对 MaxSim 计算做剪枝加速（跳过不重要的 token，仅保留匹配度最高的部分 token 参与求和）。

**加分项**：了解 ColBERT v2——通过残差压缩（Residual Compression）进一步将索引空间缩小 6-10 倍，同时引入去噪训练增强鲁棒性。了解 ColPali——将 ColBERT 的 Late Interaction 思想推广到视觉领域，为 PDF 页面的每个图像 patch 生成向量，实现图文混排文档的多模态 Token 级检索。

## Q57：RAG 如何处理多文档冲突信息？

### 考察点
考察候选人对 RAG 系统在信息冲突（矛盾）场景下的鲁棒性设计能力，包括冲突检测、消解策略和生成控制。

### 解答思路
1. 定义多文档冲突的典型场景（事实冲突、时效冲突、视角冲突）。
2. 从检索后处理角度说明冲突检测方法。
3. 从 LLM 生成角度说明冲突消解 Prompt Engineering 和 Agentic 策略。

### 参考答案
RAG 中的多文档信息冲突是指检索到的多个文档对同一问题给出了相互矛盾或不一致的答案。典型场景分三类：（1）事实冲突——不同来源对同一事实（如某产品参数）描述不同；（2）时效冲突——新旧版本文档信息矛盾（如旧文档说"不支持某功能"，新文档已支持）；（3）视角冲突——不同作者对同一事件的观点或评价截然相反。

处理多文档冲突的系统性方案分为三层：

层一：检索后的冲突检测
- 内容相似度 + 关键信息抽取比对：对检索到的 Top-K 文档，两两计算语义相似度或用 NLI（Natural Language Inference，自然语言推理）模型判断是否存在矛盾关系（Contradiction）。可用 DeBERTa-NLI 等轻量模型做快速推理。
- 元数据优先级标注：在入库时为文档打上时间戳、来源权威度、版本号等标签，检测到冲突时基于元数据做初步裁决（如优先信新文档而非旧文档）。

层二：Prompt Engineering 消解
- 冲突显式呈现：在 Prompt 中不做隐藏，而是将冲突信息分组列出，明确告知 LLM："以下信息来源对同一问题给出不同回答，请你判断"，并要求模型给出综合结论。
- 引证溯源：要求 LLM 在回答中标注每条信息的来源（Citation），让用户自行判断可信度。对冲突项特别标注"If Conflict"。
- 置信度提示：让 LLM 为每个答案候选给出置信度评分，低置信度信息或明确冲突信息需在输出中向用户说明不确定性。

层三：Agentic 多步消解
- 当检测到高冲突时，触发 Agent 进行二次检索或验证搜索（Verification Search），自动寻求权威来源（如官网、百科）作为仲裁依据。
- 使用 Decomposition（问题分解）将原问题拆分为多个子问题，分别检索和验证，降低全局冲突的概率。
- 设计 Fallback 策略：当冲突无法消解时，系统明确告知用户"不同来源信息矛盾"并列出各方说法，而不是强行输出一个可能错误的"确定答案"。

**加分项**：提到 LLM-as-Judge 用于冲突消解——用另一个独立 LLM 作为仲裁者，读取冲突文档和候选答案，输出裁决结果和理由。了解 RAFT（Retrieval Augmented Fine-Tuning）中的冲突感知训练——在微调数据中故意加入冲突文档对，训练模型在"看到矛盾信息时学会说不知道"而非盲目选一个。

## Q58：如何优化长文档的 RAG 检索效果？

### 考察点
考察候选人对长文档（如百页 PDF、技术手册、法律合同）场景下 RAG 召回质量的系统性优化能力，涉及切分、检索和多级召回的工程实践。

### 解答思路
1. 分析长文档 RAG 的特殊挑战（信息分散、上下文断裂、切分难点）。
2. 从文档切分角度展开优化策略。
3. 从检索架构角度展开（多级检索、父子文档、Small-to-Big）。

### 参考答案
长文档（通常超过 50 页或 20,000 字）的 RAG 面临三大核心挑战：（1）全局信息丢失——切分后每个 chunk 仅含局部上下文，关于整体结构（如"第三章讲了哪些主题"）的问题无法回答；（2）跨 chunk 语义链断裂——一个概念的定义在 chunk A，用法在 chunk B，检索时只能召回其一；（3）Top-K 竞争——相关段落可能间隔很远，检索分数相近但只能截断 top-K，后段关键信息被丢弃。

优化策略从四个维度展开：

维度一：智能切分策略
- 按文档层级结构切分（H1/H2/H3 标题作为分割边界），保留 Section 标题作为每个 chunk 的上下文前缀。
- 语义切分：基于相邻段落 Embedding 的余弦相似度变化率，在语义转折点切分，而非简单滑窗。
- Agentic Chunking：让 LLM Agent 阅读文档后动态决定切分边界，确保每个 chunk 语义自包含。

维度二：父子文档（Parent-Child）架构
- 小 chunk 用于检索（高精度匹配），大 chunk 或完整 section 用于喂给 LLM（保证上下文完整）。
- 实现方式：每个小 chunk（如 256 token）存储向量用于 ANN 检索，同时在元数据中记录其"父文档"ID；检索命中后，不返回小 chunk 而是返回其父文档（如完整章节，1500 token）。

维度三：Small-to-Big / 句子窗口检索
- 将文档切分为极小单元（句子级），但检索返回的是以该句为中心的扩展窗口（前后各扩展 1-2 段）。该方法确保"锚点精度"同时不丢失周围上下文。

维度四：多级检索与重排序
- 第一阶段粗筛（Hybrid Search：BM25 + Dense）：用两种互补方式各召回 50-100 个候选。
- 第二阶段重排序（Cross-Encoder Reranker）：如 Cohere Rerank / BGE-Reranker 对候选做精排，压缩至 Top-5~10。
- 第三阶段：对精排结果按原始文档顺序还原排列，确保 LLM 接收的内容保持文档的逻辑叙述顺序，而非相似度倒序。

额外策略：摘要辅助检索（Summary-Augmented Retrieval）。为每个文档 Section 预生成摘要，将摘要与正文 chunk 一起索引。用户查询先与摘要匹配（粗定位到相关章节），再在章节内做精细检索，这本质上是"目录式检索"。

**加分项**：了解 RAPTOR 的递归摘要树——对长文档建立层次化摘要树（叶子是原始 chunk，上层是 chunk 组成的 cluster 的摘要），检索时自顶向下遍历树，可同时回答"细节查询"和"概要查询"。提到 Long-Context LLM 的挑战——即使 Gemini 1.5 Pro 支持百万 Token 上下文，"大海捞针"问题依然存在，精准检索 + 精准上下文比盲目塞全文更可靠。

## Q59：RAG 如何适配实时更新的知识库？

### 考察点
考察候选人对动态知识库场景下 RAG 系统数据同步、索引更新和一致性保障的架构设计能力。

### 解答思路
1. 定义实时知识库的场景特点（高频增量更新、软删除、版本管理）。
2. 从数据管道角度设计流式更新架构。
3. 讨论增量索引更新的工程实现与一致性保障。

### 参考答案
实时更新的知识库指知识源持续变化（如 Wiki、内部文档库、新闻流、代码库）的场景，RAG 系统需要近乎实时地反映最新信息，而非按天/周做全量重建。核心工程挑战在于：（1）如何快速感知变更；（2）如何高效增量更新索引；（3）如何保证检索结果的一致性。

整体架构分为三个层次：

层一：变更感知与管道
- 变更数据捕获（CDC）：对接知识源的变更事件流。数据库侧使用 Debezium + Kafka 捕获 INSERT/UPDATE/DELETE 操作；文件系统侧使用 inotify/S3 Event Notification 监听文件的增删改；API 侧定时轮询或 Webhook 触发。
- 变更事件进入消息队列（Kafka/Pulsar），按文档 ID 哈希分区保证同一文档的变更有序处理。由消费者程序解析变更内容，计算新旧文档的哈希差异，仅对有变化的段落/章节触发重新入库。

层二：增量索引更新
- 向量数据库侧：现代向量库（Milvus/Qdrant/Weaviate）均支持 Upsert 操作（有则更新、无则插入）和 Delete by Filter（按文档 ID 删除旧 chunk）。更新时先 delete 旧 chunks 再 insert 新 chunks，避免出现新老版本混合的脏数据。
- 索引同步策略：全量重建（Rebuild）周期长但索引质量最佳；增量追加（Append-Only）速度快但旧数据堆积。推荐"增量更新 + 定时 Compaction"——日常增量 upsert，凌晨低峰期触发索引压缩（合并分段、清理墓碑数据），平衡实时性和索引质量。
- 软删除 + 延迟生效：删除操作先标记为"已删除"（在元数据中设置 status=deleted），由 LLM 生成时通过 metadata filter 过滤掉，而非立刻从向量库物理删除（物理删除可延迟到 Compaction 时执行），以防误删和回滚需求。

层三：缓存失效与一致性
- 检索缓存（如 Redis 缓存的 Query→Top-Chunks 映射）需要在知识库更新时主动失效。精细做法：用 doc_id 作为缓存键的 tag，文档变更时失效所有关联该 doc 的缓存项。
- 一致性模型：采用最终一致性（Eventual Consistency），允许检索结果在 5-10 秒窗口内略有过时。如需强一致性（如金融/医疗场景），在更新期间对该文档的查询走同步等待逻辑（但会大幅增加延迟）。
- 变更可视化：在返回给用户的检索结果中标注文档的"最后更新时间戳"，让用户感知信息新鲜度。

**加分项**：提到 Near-Real-Time RAG 的双写架构——检索请求同时查询"主索引"和"近实时增量索引"（小规模热数据），合并去重后返回，达到秒级新鲜度。了解索引 A/B 切换方案——在后台构建新版本索引，构建完成后通过别名（Alias）原子切换，实现"用户无感知"的索引更新。

## Q60：RAGAS 评估框架四大指标是什么？

### 考察点
考察候选人对 RAG 系统主流评估框架 RAGAS 的理解，及其四个核心指标的计算原理和适用场景。

### 解答思路
1. 简述 RAGAS 框架的定位和设计理念。
2. 逐一解释四个指标的定义和计算方式。
3. 说明各指标的局限性与互补关系。

### 参考答案
RAGAS（Retrieval Augmented Generation Assessment）是目前最主流的 RAG 系统开源评估框架，它不需要人工标注的标准答案（Ground Truth），而是基于 LLM 自动对 RAG 输出的三个质量维度进行评估，定义了四大核心指标：

（1）Faithfulness（忠实度）：衡量 LLM 生成的回答是否严格基于检索到的上下文，即"回答中的每句话是否都能在检索文档中找到支持证据"。计算方式：先用 LLM 将回答拆分为原子声明（Atomic Claims），再逐一检查每个声明是否能从 context 中推导出来。Faithfulness = 能验证的声明数 / 总声明数。这是防止幻觉（Hallucination）的核心指标，低忠实度意味着模型在"编造"信息。

（2）Answer Relevancy（回答相关性）：衡量回答与用户问题之间的相关程度，即"回答有没有跑题"。计算方式：让 LLM 基于原始回答反向生成多个可能的用户问题（Reverse Question Generation），再计算这些生成问题与原始问题的语义相似度。分数低意味着回答虽然可能事实正确但答非所问。

（3）Context Precision（上下文精度）：衡量检索到的上下文中，实际有用的信息占比，即"召回的文档中有多少是真正相关的"。计算方式：对 Top-K 检索结果逐条用 LLM 判断与 ground truth 相关性，结合排名位置加权计算 Precision@K，排名靠前的相关文档得分更高。该指标聚焦检索质量，鼓励相关文档排在顶部。

（4）Context Recall（上下文召回率）：衡量检索到的上下文是否覆盖了回答所需的全部信息，即"标准答案中的关键信息是否都被检索到了"。计算方式：让 LLM 将 Ground Truth 拆分为独立信息点（Sentences），再检查每个信息点是否能从检索 context 中找到。Context Recall = 能找到的信息点数 / 总信息点数。

四个指标的关系：Faithfulness 和 Answer Relevancy 评估生成端质量（Generation）；Context Precision 和 Context Recall 评估检索端质量（Retrieval）。实际应用中，四个指标需要综合看待：高召回率低精度意味着检索太广引入噪音；高精度低召回率意味着检索太窄遗漏关键信息；低忠实度意味着 LLM 没有真正使用检索上下文。

**加分项**：了解 RAGAS 的指标可组合为自定义评估 pipeline，支持通过 RAGAS Metrics 接口扩展自定义指标（如 Summarization Score、Harmfulness）。提到其他评估框架的互补维度：TruLens 的 Groundedness 评估、DeepEval 的 Contextual Relevancy，以及人工评估的不可替代性（尤其是在垂直领域专业知识场景下）。

## Q61：设计一个多租户 RAG 系统，竞对之间数据必须完全隔离。

### 考察点
考察候选人对多租户 SaaS 架构下 RAG 系统安全隔离、资源管理和性能优化的综合设计能力，重点评估租户间数据泄露风险的防范意识。

### 解答思路
1. 明确多租户 RAG 的隔离需求和威胁模型。
2. 从存储层、索引层、检索层、生成层逐层设计隔离方案。
3. 讨论资源分配和成本控制。

### 参考答案
多租户 RAG 系统中竞对数据完全隔离，意味着必须确保"一个租户的数据在任何环节都不可能泄露给另一个租户"，包括向量检索泄露、LLM 上下文污染、缓存投毒等潜在风险场景。

分层隔离设计方案：

第一层：向量数据库隔离
- 物理隔离方案（最强安全）：为每个租户创建独立 Collection/Namespace（如 Milvus Partition Key 或 Qdrant Collection per tenant）。不同租户的向量存储在不同的逻辑/物理分区中，向量检索时必须在查询层面强制传入租户 ID 作为过滤条件。优点：隔离彻底、查询时天然限定了搜索范围。缺点：租户数过多时 Collection 管理复杂。
- 行级过滤方案（弹性更好）：所有租户共享一个 Collection，但每个 vector entry 的 metadata 中存入 tenant_id 字段。所有检索请求 API 层强制注入 tenant_id filter（metadata.tenant_id == "${current_tenant}"），ANN 检索在索引遍历阶段就过滤掉不匹配的向量。该方案要求检索网关层做硬编码过滤，绝不能依赖上游传入的参数（防越权攻击）。审计层面：记录每次检索的 tenant_id 和返回结果，定期抽样检查。
- 混合方案：大租户独立 Collection（资源隔离 + 性能保障），小租户共享 Collection + row-level filter（经济性）。

第二层：LLM 调用隔离
- 每条 LLM 请求的上下文仅注入当前租户的检索结果，严禁跨租户信息混入 Prompt 模板。
- LLM API Key 按租户或按租户组隔离，不同租户使用独立的 API 账号，防止 LLM 服务商侧的预训练数据与租户数据交叉污染。
- 记录 LLM 请求/响应的审计日志（存储 tenant_id、timestamp、prompt 摘要、response），用于合规审查。

第三层：存储与数据层隔离
- 文档源文件按租户分桶存储（OSS Bucket per tenant 或按 tenant_id 前缀分区），设置严格的 IAM 策略禁止跨租户访问。
- 数据库层面：MySQL/PostgreSQL 中所有数据表必须包含 tenant_id 列，ORM 层使用 Row-Level Security（如 PostgreSQL RLS Policy）或 Application-Level Filter 确保 SQL 查询自动带 tenant_id 条件。
- 关键数据字段（如租户上传的文档内容）使用租户独立的加密密钥（Tenant-Specific Encryption Key），即使存储层泄露数据也无法被其他租户的密钥解密。

第四层：网关与审计层
- 统一 API Gateway 集成租户认证与鉴权（JWT token 中绑定 tenant_id），所有下游服务从 token 中提取 tenant_id 而非接收请求参数。
- 审计系统记录所有跨服务调用的 tenant_id 链路，定期执行 Cross-Tenant Query 模拟测试（用租户 A 的 token 尝试读取租户 B 的数据），自动化验证隔离有效性。
- 数据残留风险控制：当租户注销时，自动触发数据清理 Job——删除该租户的所有 Vector、文档文件、数据库记录和缓存条目。

**加分项**：提到 Confidential Computing（机密计算）方案——对安全要求极高的场景（如金融行业竞对隔离），可使用 Intel SGX/TDX 或 AMD SEV 在可信执行环境中运行 Embedding 和检索逻辑，即使基础设施运维人员也无法访问明文数据。了解向量数据库的 Partition Key 功能（如 Milvus 2.3+ 的 Partition Key + Clustering Key）来实现租户级物理隔离与高性能检索的统一。

## Q62：向量数据库的 ANN（近似最近邻）是什么？HNSW 和 IVF 索引原理是什么？HNSW 和 IVFFLAT 的区别是什么？

### 考察点
考察候选人对向量数据库核心索引算法（ANN）的底层原理理解，以及在实际选型中 HNSW 与 IVF 系列的差异对比与适用场景判断能力。

### 解答思路
1. 先解释 ANN 的概念、为什么需要它，以及与 KNN 精确搜索的对比。
2. 分别详述 HNSW 和 IVF 的原理。
3. 对比 HNSW 和 IVFFLAT 的核心差异（内存、速度、精度、场景）。

### 参考答案
ANN（Approximate Nearest Neighbor，近似最近邻）是一种以牺牲少量检索精度换取大幅速度提升的向量搜索算法。在高维空间（如 768/1024/1536 维 Embedding）中，精确 KNN 搜索（逐一计算查询向量与所有数据点的距离）的时间复杂度为 O(N*d)（N 为数据量，d 为维度），当 N 达到百万至十亿级别时完全不可行。ANN 通过构建索引结构，将搜索复杂度降至 O(log N) 级别，精度损失通常控制在 1%-5% recall 以内。

HNSW（Hierarchical Navigable Small World）原理：
HNSW 基于 NSW（Navigable Small World）图理论，构建多层跳表式图结构。底层（Layer 0）包含所有数据点，每往上一层节点数量指数递减。每个节点存储其近邻节点列表（边）。检索过程：（1）从最顶层的入口点开始，使用贪心搜索在当前层找到距离查询最近的节点；（2）下降到下一层，以该层最近节点为起点继续贪心搜索；（3）重复直到 Layer 0，最终找到 Top-K 结果。HNSW 的插入策略：新节点被分配一个随机层级（指数分布），然后从顶层开始逐层找最近邻并建立连接。核心优势：搜索极快（O(log N)）、精度高、支持动态插入删除无需重建。代价：内存开销大（需存储图结构的所有边，通常为原始向量的 1.5-3 倍内存）。

IVF（Inverted File Index）原理：
IVF 借鉴倒排索引思想，将向量空间划分为若干聚类区域。构建过程：（1）使用 K-Means 对所有向量聚类，生成 K 个聚类中心（Centroids）；（2）每个向量分配到最近的聚类中心，形成 K 个倒排列表。（3）检索时，查询向量先与 K 个聚类中心计算距离，仅在最接近的 N 个聚类（nprobe 参数控制，通常 1-10% K）内做精确距离搜索。复杂度降为 O(K + N/K * nprobe)。IVF_FLAT 是 IVF 的基础变体——聚类内向量不做进一步压缩，以原始向量形式存储，聚类内做 Flat（暴力）搜索。优势：内存占用小（仅额外存储聚类中心），构建速度快。代价：检索时需先遍历聚类中心，查询延迟略高于 HNSW；新增数据到一定量后需重建聚类（不支持高效动态更新）。

HNSW 与 IVFFLAT 的核心区别：

| 维度 | HNSW | IVFFLAT |
|------|------|---------|
| 索引结构 | 多层图 | 倒排列表 + 聚类中心 |
| 构建速度 | 较慢（需建图） | 较快（K-Means） |
| 查询速度 | 极快 | 较快 |
| 内存占用 | 大（原始+图边，1.5-3x） | 小（仅原始+centroids，~1x） |
| 动态插入 | 原生支持，插入即建边 | 不友好，需定期重建聚类 |
| 精度（同等参数） | 通常更高 | 略低 |
| 适用场景 | 数据相对稳定、追求极致 QPS | 数据量大、内存敏感、允许重建 |

选型建议：追求低延迟高 QPS 且内存充足选 HNSW；数据量极大（亿级）且内存受限选 IVF 系列；如需频繁增删数据选 HNSW；如需支持标量过滤 + 向量混合搜索，两种都支持，但 IVF 的 Scalar Quantization 变体（IVF_SQ8）在混合场景下表现更稳定。

**加分项**：了解 Milvus 2.x 的 DiskANN（磁盘索引）方案——HNSW 图结构存磁盘 + NVMe SSD 高速读，实现"内存级别性能 + 磁盘级别成本"，适合百亿级以上向量规模。提到 HNSW 的"高速公路效应"——高层节点度高的少数"枢纽节点"成为检索瓶颈，极端情况下退化为 O(N) 复杂度，可通过限制节点最大度数（M）和启发式边选择策略缓解。
